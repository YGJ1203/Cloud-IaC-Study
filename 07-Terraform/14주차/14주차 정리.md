# 1. 10월 6일 - AWS CloudFormation

## 1.1 CloudFormation이란?

AWS에서 제공하는 **IaC(Infrastructure as Code)** 서비스이다.

AWS 리소스를 YAML 또는 JSON 파일로 정의한 뒤 Stack을 생성하면 AWS가 해당
템플릿을 기반으로 리소스를 생성한다.

``` text
Template
   ↓
CloudFormation Stack
   ↓
VPC
Subnet
Route Table
Security Group
EC2
...
```

### 핵심 장점

-   인프라 자동 생성
-   동일 환경 반복 구축
-   구성 변경 이력 관리
-   사람이 콘솔에서 일일이 생성하면서 발생하는 실수 감소
-   인프라 구성을 코드로 Git에서 관리 가능

------------------------------------------------------------------------

# 2. CloudFormation 기본 구조

실습에서 사용한 핵심 구조는 다음과 같다.

``` yaml
Parameters:

Resources:
```

실무에서는 추가로 다음 섹션도 자주 사용한다.

``` yaml
AWSTemplateFormatVersion:
Description:
Parameters:
Mappings:
Conditions:
Resources:
Outputs:
```

이 중 **Resources가 핵심**이며 실제 AWS 리소스를 정의한다.

------------------------------------------------------------------------

# 3. Parameters

실습에서는 EC2 KeyPair와 AMI 정보를 Parameter로 받았다.

``` yaml
Parameters:
  KeyName:
    Description: EC2 KeyPair
    Type: AWS::EC2::KeyPair::KeyName
    ConstraintDescription: EC2 KeyPair

  LatestAmiId:
    Description: EC2 AMI
    Type: 'AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>'
    Default: '/aws/service/ami-amazon-linux-latest/amzn2-ami-hvm-x86_64-gp2'
```

### 의미

`Parameters`를 사용하면 템플릿 내부에 값을 무조건 고정하지 않고 Stack
생성 시 값을 선택하거나 전달할 수 있다.

즉,

``` text
하드코딩
KeyName: mykey
```

보다

``` text
Parameter
   ↓
사용자가 Stack 생성 시 선택
```

구조가 재사용성 측면에서 유리하다.

------------------------------------------------------------------------

# 4. VPC 생성

실습 예시:

``` yaml
MyVPC04:
  Type: AWS::EC2::VPC
  Properties:
    CidrBlock: 10.0.0.0/16
    EnableDnsSupport: 'true'
    EnableDnsHostnames: 'true'
    Tags:
      - Key: Name
        Value: MyVPC04
```

### 핵심 포인트

``` text
Type
```

은 생성할 AWS 리소스 종류를 의미한다.

``` text
Properties
```

는 해당 리소스의 설정값이다.

예를 들어 VPC의 경우:

-   CIDR
-   DNS Support
-   DNS Hostname
-   Tag

등을 지정할 수 있다.

------------------------------------------------------------------------

# 5. Internet Gateway

``` yaml
MyIGW:
  Type: AWS::EC2::InternetGateway
  Properties:
    Tags:
      - Key: Name
        Value: MyIGW
```

IGW만 생성했다고 인터넷 통신이 가능한 것은 아니다.

반드시 다음 연결이 필요하다.

``` text
VPC
 │
Internet Gateway
 │
Route Table
 │
0.0.0.0/0 → IGW
```

즉 AWS 네트워크에서는 **리소스 생성과 연결(Association/Attachment)을
구분**해야 한다.

------------------------------------------------------------------------

# 6. CloudFormation의 리소스 참조

CloudFormation에서는 리소스끼리 연결할 때 직접 ID를 하드코딩하기보다
참조 기능을 사용한다.

대표적인 것이:

``` yaml
!Ref
```

그리고

``` yaml
!GetAtt
```

이다.

### Ref

대부분 해당 리소스의 ID 또는 Parameter 값을 가져온다.

``` yaml
VpcId: !Ref MyVPC04
```

개념적으로:

``` text
MyVPC04 생성
   ↓
VPC ID 확보
   ↓
다른 리소스에서 참조
```

### GetAtt

리소스의 특정 Attribute를 가져올 때 사용한다.

``` yaml
!GetAtt MyEC2.PublicIp
```

------------------------------------------------------------------------

# 7. CloudFormation 의존성

CloudFormation은 리소스 참조 관계를 통해 상당수 의존성을 자동 판단한다.

예:

``` text
VPC
 ↓
Subnet
 ↓
EC2
```

Subnet이 VPC를 `!Ref`하고 있다면 CloudFormation은 VPC가 먼저 필요하다는
것을 알 수 있다.

필요한 경우 명시적으로:

``` yaml
DependsOn:
```

을 사용할 수도 있다.

### 면접 포인트

> CloudFormation에서 리소스 생성 순서를 어떻게 결정합니까?

**답변 핵심**

리소스 간 `Ref`, `GetAtt` 등의 참조 관계를 통해 CloudFormation이
의존성을 자동 판단하며, 자동 판단이 어려운 경우 `DependsOn`으로 명시적인
의존성을 지정할 수 있다.

# 9. Terraform 기본 개념

Terraform은 HashiCorp에서 만든 IaC 도구이다.

CloudFormation과 가장 큰 차이는 다음과 같다.

  CloudFormation   Terraform
  ---------------- ------------------------------
  AWS 서비스       HashiCorp 도구
  AWS 중심         Multi Cloud
  YAML / JSON      HCL
  Stack            State
  Ref / GetAtt     resource attribute reference

Terraform의 핵심 흐름:

``` text
.tf 작성
   ↓
terraform init
   ↓
terraform plan
   ↓
terraform apply
   ↓
AWS Resource 생성
```

삭제:

``` bash
terraform destroy
```

실습에서는 자동 승인 옵션까지 사용했다.

``` bash
terraform apply -auto-approve
terraform destroy -auto-approve
```

> `-auto-approve`는 확인 절차를 생략하므로 실무에서는 특히 `destroy`
> 사용 시 주의해야 한다.

------------------------------------------------------------------------

# 10. Terraform 주요 블록

## resource

실제 리소스를 생성한다.

``` hcl
resource "aws_vpc" "MyVPC05" {
}
```

구조:

``` text
resource "Provider_ResourceType" "Terraform 내부 이름"
```

------------------------------------------------------------------------

## data

Terraform이 직접 생성하지 않고 이미 존재하는 정보를 조회한다.

실습에서는 최신 AMI 정보를 참조하는 형태를 사용했다.

``` hcl
data.aws_ami.LatestAmi.id
```

### resource vs data

``` text
resource = Terraform이 생성/관리
data     = 기존 정보 조회
```

시험과 면접에서 매우 자주 구분하는 개념이다.

# 13. Security Group

실습에서는 Public Security Group에서 다음 트래픽을 허용했다.

``` text
HTTP
HTTPS
SSH
ICMP
```

즉:

``` text
80/TCP
443/TCP
22/TCP
ICMP
```

### 핵심

Security Group은 **Stateful Firewall**이다.

Inbound에서 허용된 연결의 응답 트래픽은 별도의 Outbound 규칙 없이도 상태
기반으로 허용된다.

반대로 Network ACL은 Stateless이다.

### 면접 단골

  Security Group      NACL
  ------------------- -----------------------
  Stateful            Stateless
  Instance/ENI 수준   Subnet 수준
  Allow 규칙          Allow / Deny
  응답 자동 허용      응답 방향 규칙도 고려

# 14. EC2 고정 Private IP

실습 EC2:

``` text
MyWeb1
Private IP : 10.0.1.101
AMI        : data.aws_ami.LatestAmi.id
KeyPair    : aws_key_pair.tf_keypair.name
Type       : t3.micro
```

Terraform에서는 다른 리소스의 값을 다음처럼 참조할 수 있다.

``` hcl
ami      = data.aws_ami.LatestAmi.id
key_name = aws_key_pair.tf_keypair.name
```

이 참조 관계가 Terraform의 **Implicit Dependency**를 만든다.

# 15. Terraform 의존성

Terraform의 중요한 개념 중 하나이다.

예:

``` hcl
vpc_id = aws_vpc.MyVPC05.id
```

이 코드가 있다면 Terraform은:

``` text
aws_vpc.MyVPC05
        ↓
현재 Resource
```

순서가 필요하다는 것을 자동으로 판단한다.

이를 **암시적 의존성(Implicit Dependency)**이라고 한다.

필요하면:

``` hcl
depends_on = [
  aws_internet_gateway.MyIGW
]
```

처럼 명시적 의존성을 설정할 수 있다.

### 중요

Terraform 소스를 위에서 아래로 작성했다고 해서 반드시 그 순서대로
생성되는 것이 아니다.

Terraform은 **Dependency Graph**를 기반으로 실행 순서를 결정한다.

# 16. NAT Gateway

Private Subnet의 서버가 인터넷으로 나가야 하지만 외부에서 직접
접근되어서는 안 되는 경우 사용한다.

구조:

``` text
Private EC2
   ↓
Private Route Table
   ↓
NAT Gateway
   ↓
Public Subnet
   ↓
Internet Gateway
   ↓
Internet
```

### 매우 중요

NAT Gateway는 **Public Subnet**에 배치한다.

그리고 Public NAT Gateway에는 Elastic IP가 필요하다.

실습 리소스:

``` text
MyNatGWEIP
MyNat
```

Private Route:

``` text
0.0.0.0/0 → NAT Gateway
```

------------------------------------------------------------------------

# 17. Public vs Private Subnet 핵심

### Public Subnet

``` text
Route Table
0.0.0.0/0 → IGW
```

### Private Subnet

``` text
Route Table
0.0.0.0/0 → NAT Gateway
```

핵심은 단순히 Public IP의 존재 여부가 아니라 **Route Table이 어디를
향하는가**이다.

# 18. VPC Endpoint

VPC 내부 리소스가 AWS 서비스에 접근할 때 인터넷 경로를 사용하지 않고 AWS
내부 네트워크를 이용할 수 있게 한다.

``` text
EC2
 ↓
VPC Endpoint
 ↓
AWS Service
```

장점:

-   인터넷 게이트웨이 불필요
-   NAT Gateway 불필요한 경우 존재
-   Private Network 통신
-   보안 강화
-   NAT 데이터 처리 비용 절감 가능

------------------------------------------------------------------------

# 19. VPC Endpoint 종류

## Gateway Endpoint

대표 서비스:

``` text
Amazon S3
DynamoDB
```

Route Table에 Endpoint 경로가 추가된다.

``` text
Private EC2
   ↓
Route Table
   ↓
Gateway Endpoint
   ↓
S3 / DynamoDB
```

Gateway Endpoint 자체에는 일반적인 시간당 사용 요금이 없다.

------------------------------------------------------------------------

## Interface Endpoint

AWS PrivateLink 기반이다.

VPC 내부 Subnet에 ENI가 생성된다.

``` text
EC2
 ↓
Private IP
 ↓
Interface Endpoint ENI
 ↓
AWS Service
```

특징:

-   PrivateLink 사용
-   ENI 생성
-   Security Group 적용 가능
-   다양한 AWS 서비스 지원
-   시간 및 데이터 처리 비용 발생 가능

------------------------------------------------------------------------

# 20. Endpoint Service

Endpoint Service는 서비스 **제공자(Provider)** 측에서 PrivateLink
서비스를 제공하기 위한 기능이다.

대표 구조:

``` text
Consumer VPC
     │
Interface Endpoint
     │
AWS PrivateLink
     │
Endpoint Service
     │
NLB
     │
Provider Application
```

### 핵심

Endpoint Service 앞에는 일반적으로 **Network Load Balancer(NLB)**가
사용된다.

이를 이용하면 서로 다른 VPC나 계정 사이에서도 인터넷에 노출하지 않고
Private하게 서비스를 제공할 수 있다.

------------------------------------------------------------------------

# 21. VPC Endpoint vs Endpoint Service

  구분             VPC Endpoint            Endpoint Service
  ---------------- ----------------------- ---------------------
  관점             서비스 소비자           서비스 제공자
  역할             서비스에 Private 접근   Private 서비스 제공
  대표 기술        Gateway / Interface     PrivateLink
  Interface 연결   Endpoint ENI            NLB 기반 서비스

# 22. 10월 8일 - VPC Peering

VPC Peering은 두 VPC를 Private Network로 직접 연결하는 기능이다.

``` text
VPC A
  │
Peering
  │
VPC B
```

Peering 생성만으로 통신이 되는 것은 아니다.

각 VPC Route Table에 상대 VPC CIDR에 대한 Route를 추가해야 한다.

예:

``` text
VPC A : 10.0.0.0/16
VPC B : 172.16.0.0/16
```

A Route:

``` text
172.16.0.0/16 → Peering Connection
```

B Route:

``` text
10.0.0.0/16 → Peering Connection
```

그리고 Security Group/NACL 역시 통신을 허용해야 한다.

------------------------------------------------------------------------

# 23. Peering의 핵심 제한 - Transitive Routing X

다음 구조가 있다고 하자.

``` text
VPC A ↔ VPC B ↔ VPC C
```

A-B Peering과 B-C Peering이 존재한다고 해서:

``` text
A → B → C
```

통신이 자동으로 가능한 것은 아니다.

즉 **VPC Peering은 Transitive Routing을 지원하지 않는다.**

VPC가 많아지면 Peering 연결이 복잡해지는 이유이다.

------------------------------------------------------------------------

# 24. Transit Gateway

많은 VPC와 네트워크를 중앙에서 연결하기 위한 AWS 네트워크 허브이다.

``` text
             VPC A
               │
VPC B ─── Transit Gateway ─── VPC C
               │
             VPC D
```

### 장점

-   중앙 집중형 연결
-   VPC 간 연결 단순화
-   Peering Mesh 문제 감소
-   On-Premise 연결 가능
-   VPN / Direct Connect 연계 가능
-   Transit Routing 지원

------------------------------------------------------------------------

# 25. Peering vs Transit Gateway

  항목                 VPC Peering   Transit Gateway
  -------------------- ------------- -----------------
  구조                 1:1           Hub & Spoke
  Transitive Routing   X             O
  소규모 VPC           적합          다소 과함
  대규모 네트워크      복잡          적합
  중앙 관리            어려움        쉬움

### 면접 답변

> VPC가 2\~3개 정도라면 Peering이 단순할 수 있지만, VPC가 많아지면 연결
> 수와 Route 관리가 복잡해지므로 Transit Gateway를 사용하여 중앙
> 집중형으로 구성할 수 있습니다.

# 29. ALB 분산 확인

실습에서는 다음 명령으로 100번 요청을 보내 각 Web Server에 요청이

# 30. ALB Path Based Routing

실습에서는 다음 경로도 확인했다.

``` bash
curl http://MyALB-1430824240.ap-northeast-2.elb.amazonaws.com/dir1/index.html
```

``` bash
curl http://MyALB-1430824240.ap-northeast-2.elb.amazonaws.com/dir11/index.html
```

ALB는 Layer 7 Load Balancer이므로 HTTP 요청의 내용을 기반으로 라우팅할
수 있다.

대표 조건:

``` text
Host Header
Path
HTTP Header
HTTP Method
Query String
Source IP
```

예:

``` text
/dir1/*  → Target Group A
/dir11/* → Target Group B
```

이것이 **Path-Based Routing**이다.

------------------------------------------------------------------------

# 31. ALB 핵심 특징

ALB는 OSI Layer 7에서 동작한다.

지원:

``` text
HTTP
HTTPS
```

특징:

-   URL Path 기반 라우팅
-   Host 기반 라우팅
-   여러 Target Group 사용
-   Web Application에 적합

------------------------------------------------------------------------

# 32. Network Load Balancer

실습 NLB:

``` text
MyNLB-ff3cc86a23e76732.elb.ap-northeast-2.amazonaws.com
```

NLB는 Layer 4 Load Balancer이다.

주로:

``` text
TCP
UDP
TLS
```

트래픽을 처리한다.

특징:

-   매우 높은 처리량
-   낮은 지연시간
-   고정 IP 관련 요구에 유리
-   TCP/UDP 기반 서비스에 적합

------------------------------------------------------------------------

# 33. ALB vs NLB

  항목                           ALB                NLB
  ------------------------------ ------------------ ------------------
  OSI                            L7                 L4
  주요 프로토콜                  HTTP/HTTPS         TCP/UDP/TLS
  Path Routing                   O                  X
  Host Routing                   O                  X
  고성능 TCP                     일반적 선택 아님   강점
  Web 서비스                     매우 적합          경우에 따라 사용
  PrivateLink Endpoint Service   직접 기반 아님     대표적으로 사용

### 기억법

``` text
ALB = Application = HTTP 내용을 본다
NLB = Network = IP/Port 중심으로 본다
```

# 36. Load Balancer + Endpoint Service 연결 개념

10/7의 Endpoint Service와 10/8의 NLB는 서로 연결되는 개념이다.

``` text

    │
Interface Endpoint
    │
PrivateLink
    │
Endpoint Service
    │

    │

```

따라서 NLB는 단순 Load Balancing뿐 아니라 **AWS PrivateLink 서비스 제공

이 연결을 이해하면 10/7과 10/8의 실습이 하나로 이어진다.

> 관계를 코드로 표현하는 능력이다.

# 39. Network → Load Balancer

네트워크가 정상적으로 구성되어야 Load Balancer도 정상 동작한다.

``` text
 ↓

```

# 41. 시험/면접 초핵심 Q&A

## Q1. IaC란?

Infrastructure as Code의 약자로 인프라를 콘솔에서 수동 구성하는 대신
코드로 정의하고 자동 생성/관리하는 방식이다.

------------------------------------------------------------------------

## Q2. CloudFormation과 Terraform 차이는?

CloudFormation은 AWS Native IaC 서비스이고 Terraform은 HashiCorp의 Multi
Cloud IaC 도구이다.

------------------------------------------------------------------------

## Q3. Terraform에서 resource와 data 차이는?

`resource`는 Terraform이 리소스를 생성하고 관리하며, `data`는 이미
존재하는 리소스나 외부 정보를 조회한다.

------------------------------------------------------------------------

## Q4. Terraform은 코드 작성 순서대로 리소스를 생성하는가?

아니다. 리소스 참조 관계를 분석하여 Dependency Graph를 만들고 이를
기반으로 생성 순서를 결정한다.

------------------------------------------------------------------------

## Q5. NAT Gateway는 왜 사용하는가?

Private Subnet의 인스턴스가 Public IP 없이 외부 인터넷으로 Outbound
통신할 수 있도록 사용한다.

------------------------------------------------------------------------

## Q6. NAT Gateway는 어디에 위치하는가?

Public Subnet에 위치한다.

------------------------------------------------------------------------

## Q7. VPC Endpoint를 사용하는 이유는?

VPC 내부 리소스가 인터넷/NAT를 거치지 않고 AWS 서비스에 Private하게
접근할 수 있게 하기 위해 사용한다.

------------------------------------------------------------------------

## Q8. Gateway Endpoint 지원 대표 서비스는?

S3와 DynamoDB.

------------------------------------------------------------------------

## Q9. Interface Endpoint는 어떤 기술을 사용하는가?

AWS PrivateLink.

------------------------------------------------------------------------

## Q10. Endpoint Service 앞에서 대표적으로 사용하는 Load Balancer는?

Network Load Balancer.

------------------------------------------------------------------------

## Q11. VPC Peering은 Transitive Routing을 지원하는가?

지원하지 않는다.

------------------------------------------------------------------------

## Q12. VPC가 많아지면 Peering 대신 무엇을 고려할 수 있는가?

AWS Transit Gateway.

------------------------------------------------------------------------

## Q13. ALB와 NLB의 가장 큰 차이는?

ALB는 Layer 7에서 HTTP/HTTPS 내용을 기반으로 라우팅하며, NLB는 Layer
4에서 TCP/UDP/TLS 트래픽을 고성능으로 처리한다.

------------------------------------------------------------------------

## Q14. ALB에서 `/api/*`, `/image/*`를 서로 다른 서버로 보낼 수 있는가?

가능하다. Path-Based Routing을 사용한다.

------------------------------------------------------------------------

## Q15. Security Group과 NACL의 차이는?

Security Group은 Stateful이며 ENI/Instance 수준에서 적용되고, NACL은
Stateless이며 Subnet 수준에서 적용된다.

# 43. 실무 관점에서 반드시 기억할 것

### 1. IaC 소스 전체를 외우려고 하지 않는다

중요한 것은:

``` text
어떤 Resource가 필요한가?
어떤 Resource와 연결되는가?
어떤 Attribute를 참조해야 하는가?
```

이다.

필요한 문법은 공식 문서에서 확인하면 된다.

------------------------------------------------------------------------

### 2. AWS 네트워크는 Route를 항상 확인한다

통신 문제 발생 시:

``` text
Source
 ↓
Route
 ↓
Gateway / Peering / TGW / NAT
 ↓
Destination
```

경로를 따라가며 확인한다.

------------------------------------------------------------------------

### 3. Security Group까지 확인한다

Route가 존재해도 SG에서 차단하면 통신되지 않는다.

------------------------------------------------------------------------

### 4. Load Balancer는 Health Check가 핵심이다

Target Group의 서버가 `Unhealthy`라면 Load Balancer는 정상적으로
트래픽을 전달할 수 없다.

------------------------------------------------------------------------

### 5. Public/Private 판단의 핵심은 Routing

``` text
Public Subnet
0.0.0.0/0 → IGW
```

``` text
Private Subnet
0.0.0.0/0 → NAT Gateway
```

이라는 구조를 기억한다.
