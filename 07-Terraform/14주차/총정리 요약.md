# AWS 토요일 심화 총정리 — 실무 트러블슈팅 & 아키텍처 판단

> 2026-10-10 | 기존 실습 명령어 반복 대신 **원인 분석, 설계 판단, 면접 답변**에 집중

## 1. 장애를 보는 기본 순서

1. **증상 구분**: DNS 실패 / 연결 타임아웃 / 연결 거부 / HTTP 4xx·5xx / 느린 응답
2. **영향 범위**: 단일 인스턴스인가, 특정 AZ인가, 전체 서비스인가?
3. **최근 변경**: 보안 그룹, 라우팅, 배포, 대상 그룹, 인스턴스 상태
4. **경로 추적**: 클라이언트 → DNS → ALB/NLB → 대상 → 애플리케이션
5. **증거 수집**: CloudWatch 지표·로그, ALB 액세스 로그, VPC Flow Logs, Reachability Analyzer
6. **복구와 재발 방지**: 즉시 복구와 근본 원인 제거를 분리

> 타임아웃은 반드시 보안 그룹 문제라는 뜻이 아니다. 라우팅, NACL, 프로세스, 헬스 체크, 응답 경로 등도 확인한다.

## 2. 장애 시나리오 8선

### A. EC2 공인 IP로 접속되지 않는다
- 퍼블릭 IP/탄력적 IP 존재 여부
- 인터넷 게이트웨이 연결 및 서브넷 라우팅 `0.0.0.0/0 → IGW`
- 보안 그룹 인바운드 허용 및 NACL 양방향 허용
- 웹 서버 실행 여부와 0.0.0.0:80 리스닝 여부
- OS 방화벽, 인스턴스 상태 확인
- **주의**: 퍼블릭 서브넷에 있다는 사실만으로 외부 접속이 보장되지는 않는다.

### B. 프라이빗 EC2에서 패키지 설치가 안 된다
- NAT Gateway 상태와 **퍼블릭 서브넷** 위치 확인
- NAT Gateway가 있는 서브넷의 IGW 경로 확인
- 프라이빗 서브넷 `0.0.0.0/0 → NAT Gateway` 확인
- DNS 해석과 외부 HTTPS 접속을 각각 검사
- **설계 판단**: S3/DynamoDB는 Gateway Endpoint로 NAT 데이터 처리 비용을 줄일 수 있다.

### C. ALB 주소는 열리는데 502가 발생한다
- 대상 애플리케이션이 유효하지 않은 HTTP 응답을 보내는지 확인
- 대상 프로세스 종료, 연결 재설정, keep-alive 타임아웃 불일치 확인
- ALB 지표 및 액세스 로그로 원인을 좁힌다.
- **502와 503과 504를 구분**: 503은 사용 가능한 대상 부재 등, 504는 대상 응답 지연 등과 관련될 수 있다.

### D. ALB 대상 그룹이 Unhealthy이다
- 대상 그룹 포트/프로토콜/헬스 체크 경로 확인
- 헬스 체크 성공 코드 범위와 앱 반환 코드 확인
- 대상 SG에서 ALB SG의 트래픽 허용
- 서버 리스닝 주소와 포트 확인
- **실무 팁**: `/health` 같은 경량 엔드포인트를 별도 구성하면 좋다.

### E. NLB를 통한 TCP는 되는데 애플리케이션은 실패한다
- L4 연결 성공과 애플리케이션 정상 동작은 별개
- TCP/TLS/HTTP 헬스 체크 설정과 실제 프로토콜 확인
- 클라이언트 IP 보존 설정 및 대상 SG/NACL 고려
- SNMP(UDP 161) 테스트라면 리스너 프로토콜과 보안 정책도 따로 확인

### F. VPC Peering 후 다른 VPC에 연결되지 않는다
- Peering 상태 Active 확인
- **양쪽** 서브넷 라우팅 테이블에 상대 CIDR 경로 확인
- SG/NACL 확인, CIDR 중복 여부 확인
- **핵심**: VPC Peering은 전이적 라우팅을 제공하지 않는다.

### G. Transit Gateway 연결 후 일부 서브넷만 통신된다
- VPC 서브넷 라우트 테이블과 TGW 라우트 테이블을 **각각** 확인
- Attachment 상태, association/propagation 확인
- 응답 경로까지 점검
- **핵심**: TGW를 붙였다는 것과 경로가 완성되었다는 것은 다르다.

### H. Terraform apply는 성공했는데 서비스가 안 된다
- Terraform은 리소스 생성 성공을 보장할 수 있어도 앱 정상 동작까지 보장하지 않는다.
- `terraform plan`, `terraform state list`, `terraform show`로 구성 확인
- AWS 실제 상태, User Data 로그(`/var/log/cloud-init-output.log`) 확인
- 불필요한 수동 변경(드리프트) 여부 확인
- 민감한 값이 state 파일에 들어갈 수 있으므로 접근 통제와 암호화 필요

## 3. 아키텍처 설계 의사결정 표

| 요구사항 | 우선 검토 | 이유 / 주의 |
|---|---|---|
| HTTP 경로별 분기 | ALB | L7 경로·호스트 기반 라우팅 |
| TCP/UDP 고성능 서비스 | NLB | L4 처리, 고정 IP 요구도 검토 |
| 프라이빗 서브넷의 일반 인터넷 아웃바운드 | NAT Gateway | 인바운드 공개 없이 외부 접속 |
| S3에 사설 경로로 접근 | Gateway VPC Endpoint | 해당 리전의 S3 트래픽을 NAT 없이 라우팅 가능 |
| 소수 VPC 간 직접 연결 | VPC Peering | 비전이적, 양방향 경로 관리 |
| 다수 VPC 중앙 허브 | Transit Gateway | 연결·라우팅 중앙화, 비용 검토 |
| 반복 가능한 인프라 관리 | Terraform / CloudFormation | 변경 이력, 재현성, IaC 운영 |

## 4. 면접에서 한 단계 높은 답변

**Q1. ALB가 있는데도 EC2에 직접 접속하는 테스트가 필요한가요?**  
A. 장애 범위를 분리하기 위해서입니다. EC2 직접 요청은 정상이고 ALB 요청만 실패하면 대상 그룹, 헬스 체크, 리스너 규칙, ALB 보안 정책을 우선 확인합니다. 단, 프라이빗 EC2는 배스천/SSM 등 적절한 관리 경로를 이용합니다.

**Q2. 보안 그룹과 NACL 차이는?**  
A. 보안 그룹은 ENI 수준의 상태 저장(Stateful) 방화벽이고, NACL은 서브넷 수준의 상태 비저장(Stateless) 필터입니다. NACL에서는 왕복 트래픽과 임시 포트를 함께 고려해야 합니다.

**Q3. NAT Gateway를 두면 외부에서 프라이빗 EC2로 접속할 수 있나요?**  
A. 아닙니다. NAT Gateway는 프라이빗 리소스의 아웃바운드 연결과 이에 대한 응답을 위한 구성이지, 외부에서 시작하는 임의의 인바운드 접속 수단이 아닙니다.

**Q4. VPC Peering과 Transit Gateway의 가장 큰 설계 차이는?**  
A. Peering은 VPC 간 직접 연결에 적합하지만 전이적 라우팅이 불가능합니다. TGW는 허브형 구조로 다수 네트워크의 경로를 중앙에서 관리할 수 있습니다.

**Q5. IaC를 쓰는데 왜 배포 검증이 필요한가요?**  
A. 리소스 생성과 서비스 가용성은 다른 문제이기 때문입니다. 인프라 배포 후 헬스 체크, 실제 HTTP 요청, 모니터링, 롤백 절차까지 검증해야 합니다.

## 5. 실무형 미니 과제

### 과제 1 — 원인 추적
상황: ALB DNS는 해석되지만 요청이 504로 끝난다. 대상 EC2는 Running 상태다.

**답변해 볼 것:** 대상 그룹 상태, 앱 응답 시간, SG/NACL, ALB 지표 중 무엇부터 확인할지와 이유를 설명한다.

### 과제 2 — 설계 선택
상황: 8개 VPC가 서로 통신해야 하며 앞으로 VPC가 늘어날 예정이다.

**답변해 볼 것:** Peering 풀메시 연결과 TGW를 운영 복잡도·라우팅·비용 관점에서 비교한다.

### 과제 3 — 비용 최적화
상황: 프라이빗 EC2들이 S3 데이터를 자주 읽으며 NAT Gateway 비용이 높다.

**답변해 볼 것:** S3 Gateway Endpoint 도입 시 라우트 테이블, Endpoint 정책, S3 버킷 정책을 어떻게 검토할지 설명한다.

### 과제 4 — Terraform 운영
상황: 누군가 콘솔에서 SG를 변경했다.

**답변해 볼 것:** 드리프트 탐지, 계획 검토, 변경 복구, 팀 차원의 예방책을 제시한다.

## 6. 실전 점검 명령어 치트시트

```bash
# DNS 해석
getent hosts example.com

# HTTP 응답 헤더와 상태 확인
curl -I --max-time 5 http://example.com

# 연결·응답 시간 확인
curl -sS -o /dev/null -w 'status=%{http_code} connect=%{time_connect} total=%{time_total}\n' http://example.com

# 서버 리스닝 확인
sudo ss -lntup

# cloud-init 사용자 데이터 실행 로그
sudo tail -n 100 /var/log/cloud-init-output.log

# Terraform 배포 전 검토
terraform fmt -check
terraform validate
terraform plan
```

## 7. 오늘의 최종 암기 문장

- **리소스 Running ≠ 애플리케이션 정상**
- **경로는 요청 방향뿐 아니라 응답 방향까지 확인**
- **ALB는 L7, NLB는 L4 중심**
- **NAT Gateway ≠ 외부 인바운드 허용**
- **Peering ≠ 전이적 연결**
- **TGW Attachment 생성 ≠ 라우팅 완료**
- **Terraform apply 성공 ≠ 운영 검증 완료**
