# 2026-10-17 토요일 클라우드·Ansible 주간 총정리

> 범위: 2026-10-12~16 학습 기록 기반. 실제 확인된 실습과 추가 학습 개념을 구분합니다.

## 1. 이번 주 학습 흐름

- AWS Site-to-Site VPN: Openswan을 이용한 고객 게이트웨이 측 IPsec 설정과 통신 확인
- CloudFront: EC2 및 S3 오리진을 이용한 CDN 배포
- Route 53 / DNS: 도메인과 레코드, 네임서버 개념
- ECR / EKS: 컨테이너 이미지 레지스트리와 관리형 Kubernetes 실습
- WAF / Shield: 웹 요청 필터링과 DDoS 방어의 역할 비교, 403 Forbidden 확인
- Ansible: 인벤토리, 플레이북, Facts, 변수, 멱등성, 체크 모드, 파일 복사, Handler 학습

## 2. AWS 핵심 복습

### 2.1 Site-to-Site VPN

- 고객 측 네트워크와 AWS VPC를 암호화 터널로 연결합니다.
- 구성 요소: Customer Gateway(CGW), Virtual Private Gateway(VGW) 또는 Transit Gateway(TGW), VPN Connection, 라우팅, 보안 그룹 및 방화벽.
- 실습: Amazon Linux 2 기반 Openswan 설정에서 `ipsec whack --trafficstatus`와 `ping`으로 통신 확인.
- 중요: ping 성공만으로 암호화 협상 설정의 적절성, 이중 터널 가용성, 장애 전환까지 검증되지는 않습니다.

**면접 포인트:** Site-to-Site VPN은 네트워크 간 연결, Client VPN은 개별 사용자 접속을 위한 서비스입니다.

### 2.2 CloudFront / CDN

- 사용자의 요청을 엣지 로케이션에서 처리하여 콘텐츠 전달 지연과 오리진 부하를 줄입니다.
- 오리진은 EC2 기반 웹 서버, ALB, S3 등으로 구성할 수 있습니다.
- 캐시 키, TTL, Cache-Control, 무효화(Invalidation)를 이해해야 합니다.
- S3 오리진은 가능하면 OAC(Origin Access Control)로 비공개 버킷 접근을 구성합니다.
- EC2 웹 서버를 오리진으로 쓸 경우 접근 제어와 HTTPS 오리진 연결도 별도로 설계합니다.

**면접 포인트:** CloudFront는 CDN이며, Route 53은 DNS 서비스입니다. DNS가 CloudFront 도메인을 가리킬 수 있지만 역할은 다릅니다.

### 2.3 ECR / EKS

- ECR: Docker/OCI 컨테이너 이미지 저장소.
- EKS: Kubernetes 컨트롤 플레인을 AWS가 관리하는 서비스.
- 실습: 이미지 빌드·푸시·풀, Windows `kubectl`에서 EKS 연결, nginx replicas=4, LoadBalancer Service.
- `kubectl get pods -o wide`, `kubectl get svc`, `kubectl describe pod`로 상태를 확인합니다.
- LoadBalancer Service 생성은 AWS 로드 밸런서 리소스 및 비용 발생으로 이어질 수 있으므로 삭제 여부를 확인합니다.

### 2.4 WAF / Shield

| 기술 | 주 역할 | 예시 |
|---|---|---|
| AWS WAF | HTTP(S) 요청 필터링 | IP 차단, 관리형 규칙, 속도 기반 규칙 |
| AWS Shield | DDoS 방어 | 네트워크·전송 계층 공격 완화 |
| Security Group | 인스턴스 등 리소스 트래픽 허용 규칙 | TCP 80/443 허용 |
| Network ACL | 서브넷 경계의 허용·거부 규칙 | CIDR 기반 제어 |

실습에서 403 Forbidden을 확인했다면, 요청이 차단되었다는 현상과 WAF 규칙이 실제 원인이었다는 증거를 구분해야 합니다. WAF 로그 및 요청 메트릭을 함께 확인하세요.

## 3. Ansible 아키텍처

```text
Control Node (master)
  ├── inventory.ini
  ├── ansible.cfg
  ├── playbooks/*.yml
  ├── group_vars/
  ├── host_vars/
  └── files/
       │ SSH
       ├── node1 192.168.2.61 (webservers)
       ├── node2 192.168.2.62 (webservers)
       └── node3 192.168.2.63 (dbservers)
```

- 컨트롤 노드: 플레이북을 실행하고 대상 노드에 접속합니다.
- 관리 대상 노드: SSH로 접속해 모듈 작업을 수행합니다. 일반적인 Linux 관리에 상주형 Ansible 에이전트가 필요하지 않습니다.
- Inventory: 대상 호스트와 그룹 정의.
- Playbook: 작업 순서와 원하는 상태를 YAML로 기술.
- Module: 실제 동작을 수행하는 단위(`command`, `copy`, `file`, `dnf`, `service` 등).
- Handler: 알림을 받았을 때 실행하는 작업(보통 서비스 재시작).

### 3.1 인벤토리

```ini
[testnode:children]
webservers
dbservers

[webservers]
192.168.2.61
192.168.2.62

[dbservers]
192.168.2.63
```

```bash
ansible-inventory -i inventory.ini --graph
ansible -i inventory.ini webservers -m ping
ansible-playbook -i inventory.ini 02-hostname.yml --limit webservers
```

`ansible.builtin.ping`은 ICMP ping이 아니라 Ansible이 대상 호스트에서 모듈을 실행할 수 있는지 확인합니다.

### 3.2 Playbook 구조

```yaml
---
- name: Check managed hostnames
  hosts: testnode
  gather_facts: false
  tasks:
    - name: Run hostname
      ansible.builtin.command: hostname
      register: hostname_result
      changed_when: false

    - name: Print hostname
      ansible.builtin.debug:
        var: hostname_result.stdout
```

- `hosts`: 대상 그룹.
- `gather_facts`: 시스템 정보 자동 수집 여부.
- `tasks`: 순서대로 실행할 작업.
- `register`: 모듈 실행 결과 저장.
- `changed_when: false`: 조회 전용 명령의 변경 표시를 방지. **멱등성을 자동으로 보장하는 기능은 아닙니다.**

### 3.3 Facts와 변수

```yaml
- name: System information
  hosts: testnode
  gather_facts: true
  tasks:
    - name: Print system details
      ansible.builtin.debug:
        msg: >-
          {{ ansible_facts['hostname'] }} /
          {{ ansible_facts['distribution'] }} /
          {{ ansible_facts['kernel'] }}
```

실습 변수:

- `group_vars/webservers.yml`: `server_role: web`, `service_port: 80`
- `group_vars/dbservers.yml`: `server_role: database`, `service_port: 3306`
- `host_vars/192.168.2.61.yml`: `server_role: web-primary`, `service_port: 8080`

**주의:** 디렉터리 이름은 `group_vars`(언더스코어)입니다. `group-vars`로 만들면 자동 로딩되지 않습니다. 인벤토리 호스트 이름과 `host_vars` 파일 이름이 일치해야 합니다. 변수 우선순위는 다양한 단계가 있으므로 단순히 '호스트 변수는 항상 최우선'이라고 외우지 마세요. 일반적인 CLI `-e` extra vars는 높은 우선순위를 갖습니다.

### 3.4 멱등성

```yaml
- name: Create directory
  hosts: testnode
  tasks:
    - name: Ensure directory exists
      ansible.builtin.file:
        path: /tmp/ansible-idempotency-test
        state: directory
        mode: '0755'
```

첫 실행에 `changed`, 같은 상태로 재실행 시 `ok`가 나오는 것이 대표적인 멱등성 예시입니다. `command`/`shell`은 사용 방법에 따라 멱등성을 직접 설계해야 합니다.

### 3.5 Check / Diff 모드

```bash
ansible-playbook -i inventory.ini 06-check-mode.yml --check --diff
ansible-playbook -i inventory.ini 07-file-copy.yml --check --diff
```

- `--check`: 가능한 모듈에서 변경을 적용하지 않고 예상 결과를 확인.
- `--diff`: 지원 모듈에서 변경 전후 차이를 표시.
- 모든 모듈이 Check/Diff를 완전하게 지원하는 것은 아닙니다.
- `vi 11-handler.yml --check --diff`는 플레이북 테스트 명령이 아닙니다. `ansible-playbook 11-handler.yml --check --diff`를 사용해야 합니다.

### 3.6 파일 배포

```yaml
- name: Deploy notice
  hosts: testnode
  tasks:
    - name: Copy notice
      ansible.builtin.copy:
        src: files/notice.txt
        dest: /tmp/ansible-notice.txt
        mode: '0644'
```

`copy`는 컨트롤 노드 파일을 관리 대상 노드에 복사합니다. 파일 내용이나 속성이 달라졌을 때 변경을 감지합니다. 변수를 삽입한 텍스트를 배포할 때는 `template`과 Jinja2를 사용합니다.

### 3.7 Handler 예시 (개념 보강)

```yaml
- name: Configure web servers
  hosts: webservers
  become: true
  tasks:
    - name: Install Apache
      ansible.builtin.dnf:
        name: httpd
        state: present

    - name: Deploy configuration
      ansible.builtin.copy:
        src: files/httpd.conf
        dest: /etc/httpd/conf/httpd.conf
        mode: '0644'
      notify: Restart Apache

  handlers:
    - name: Restart Apache
      ansible.builtin.service:
        name: httpd
        state: restarted
```

- `notify`를 호출한 작업이 `changed`인 경우에만 Handler가 큐에 등록됩니다.
- 동일 Handler에 여러 알림이 발생해도 일반적으로 해당 처리 시점에 한 번 실행됩니다.
- 기본적으로 Handler는 작업 구간 종료 시 실행되며, `meta: flush_handlers`로 앞당길 수 있습니다.
- 위 예제는 학습용으로, 실제 적용 전 `files/httpd.conf` 파일과 대상 OS 환경이 준비되어야 합니다.

## 4. Terraform vs Ansible vs Docker vs Kubernetes

| 기술 | 주된 책임 | 선언 대상 |
|---|---|---|
| Terraform | 인프라 프로비저닝 | VPC, EC2, LB, DNS 등 |
| Ansible | OS·미들웨어 구성 및 운영 자동화 | 패키지, 파일, 서비스, 계정 등 |
| Docker | 컨테이너 이미지 생성·실행 | 이미지, 컨테이너 |
| Kubernetes | 컨테이너 워크로드 오케스트레이션 | Deployment, Service, ConfigMap 등 |

실무 연결 예시:

1. Terraform으로 VPC, 서브넷, EC2를 생성합니다.
2. Ansible로 EC2에 패키지와 설정 파일을 배포합니다.
3. Docker로 애플리케이션 이미지를 빌드합니다.
4. ECR에 이미지를 푸시합니다.
5. EKS에서 Deployment로 배포하고 Service/Ingress로 노출합니다.
6. 모니터링, 권한 제어, 백업, 롤백을 별도 설계합니다.

Terraform도 일부 구성 작업을 할 수 있고 Ansible도 클라우드 리소스를 만들 수 있습니다. 위 표는 배타적인 기능 구분이 아니라 대표적인 역할 분담입니다.

## 5. 실무 트러블슈팅 체크리스트

### Ansible 접속 실패

```bash
ansible -i inventory.ini all -m ping -vvv
ssh user@192.168.2.61
ansible-config dump --only-changed
```

확인 순서: 대상 IP/포트 → 네트워크 연결 → SSH 인증 → 원격 Python/권한 → Inventory 및 설정 파일.

### 변수 적용이 이상할 때

```bash
ansible-inventory -i inventory.ini --host 192.168.2.61
ansible-playbook -i inventory.ini 04-group-vars.yml --limit webservers
```

확인 순서: 파일 경로(`group_vars`, `host_vars`) → 인벤토리 호스트명 → 변수 중복 → `-e` 적용 여부.

### 서비스가 재시작되지 않을 때

- 알림을 발생시키는 Task가 실제로 `changed`였는지 확인.
- `notify` 문자열과 Handler 이름이 일치하는지 확인.
- Handler 실행 시점 및 `--check`의 동작을 확인.
- 서비스 이름과 권한(`become`)을 확인.

## 6. 면접 예상 질문 12개

1. **Ansible이 Agentless라는 뜻은?** 일반적인 Linux 관리 시 상주 에이전트 없이 SSH 등으로 관리합니다.
2. **Inventory와 Playbook 차이는?** 전자는 대상 정의, 후자는 작업 및 상태 정의입니다.
3. **Facts는 언제 필요한가?** OS 종류나 메모리 등 시스템 정보에 따른 분기와 템플릿 처리에 필요합니다.
4. **register는 무엇인가?** 작업 실행 결과를 변수로 저장합니다.
5. **멱등성이 중요한 이유는?** 재실행해도 원하는 상태를 유지해 반복 운영 위험을 줄입니다.
6. **changed_when은 멱등성 기능인가?** 아닙니다. 결과의 변경 판정만 조절합니다.
7. **Check Mode는 완전한 시뮬레이션인가?** 아닙니다. 모듈별 지원 범위가 다릅니다.
8. **copy와 template 차이는?** template은 Jinja2 변수를 렌더링할 수 있습니다.
9. **Handler는 언제 실행되나?** 변경이 발생해 notify되었을 때 지정된 처리 시점에 실행됩니다.
10. **Terraform과 Ansible을 함께 쓰는 이유는?** 인프라 생성과 서버 내부 구성을 역할 분리해 자동화하기 위해서입니다.
11. **CloudFront와 Route 53의 차이는?** 콘텐츠 전달 네트워크와 DNS입니다.
12. **WAF와 Shield의 차이는?** HTTP 요청 필터링과 DDoS 방어가 주요 역할입니다.

## 7. 다음 주 실습 제안

- 12번 플레이북부터 이어서 진행하되, 실제 파일 내용 확인 후 순서를 정합니다.
- `dnf` + `service`로 웹 서버 설치 및 실행 자동화.
- `template`로 Jinja2 변수 기반 설정 배포.
- `when`으로 OS별 분기.
- `loop`로 여러 사용자·패키지 관리.
- `block`/`rescue`/`always`로 실패 처리.
- `roles`로 플레이북 재사용 구조화.
- `ansible-vault`로 비밀 값 관리. Vault만으로 모든 비밀 노출 위험이 사라지는 것은 아니므로 `no_log`, 권한 및 저장소 정책도 함께 고려.
