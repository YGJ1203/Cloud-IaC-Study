# PART 1. 기초 핵심 (20%)

## Q1. VPC의 Public Subnet과 Private Subnet은 무엇으로 구분하나요?

**모범 답변:** 서브넷 이름이나 공인 IP 자동 할당 옵션만으로 구분하지 않습니다. 핵심은 연결된 **라우팅 테이블에 인터넷 게이트웨이(IGW)로 향하는 기본 경로가 있는지**입니다. 일반적으로 `0.0.0.0/0 → IGW`가 있으면 Public Subnet으로 봅니다. Private Subnet의 외부 발신은 보통 Public Subnet의 NAT Gateway를 통해 처리합니다. 단, 실제 인터넷 통신에는 퍼블릭 IP, 보안 그룹, NACL 등 조건도 필요합니다.

**꼬리 질문:** Private Subnet에 NAT Gateway를 배치해도 되나요?  
**핵심:** 일반적인 퍼블릭 NAT Gateway 구성에서는 NAT Gateway를 Public Subnet에 두고 Elastic IP와 IGW 경로를 사용합니다.

## Q2. Security Group과 NACL의 차이는?

| 구분 | Security Group | Network ACL |
|---|---|---|
| 적용 단위 | ENI/리소스 | 서브넷 |
| 상태 추적 | Stateful | Stateless |
| 규칙 | 허용 규칙 중심 | 허용 및 거부 |
| 평가 | 허용 규칙 종합 | 번호 순서대로 평가 |
| 응답 트래픽 | 자동 허용 | 양방향 규칙 필요 |

**꼬리 질문:** HTTP 80 포트를 허용했는데 연결이 안 되면?  
**답:** 대상 서비스 리스닝, 라우팅, SG/NACL, OS 방화벽, 퍼블릭 IP, 타깃 상태를 순차적으로 확인합니다.

## Q3. Docker Image와 Container의 차이는?

**모범 답변:** 이미지는 애플리케이션과 실행 환경을 패키징한 읽기 전용 레이어 집합이고, 컨테이너는 이미지를 바탕으로 생성된 실행 인스턴스입니다. 이미지는 레지스트리에 push/pull할 수 있고, 컨테이너에는 실행 중 쓰기 가능한 계층이 추가됩니다. 영속 데이터는 볼륨 등으로 분리해야 합니다.

```bash
docker images
docker ps -a
docker inspect <container>
docker logs --tail 100 <container>
```

## Q4. Kubernetes Deployment와 Service의 역할은?

**모범 답변:** Deployment는 선언한 복제 수와 배포 상태를 유지하도록 ReplicaSet/Pod를 관리합니다. Service는 Pod 교체와 무관하게 안정적인 접근 지점을 제공하고 레이블 셀렉터로 백엔드 Pod를 연결합니다. Service가 Pod를 직접 생성하지는 않습니다.

```bash
kubectl get deploy,rs,pod,svc -A
kubectl describe deploy <name> -n <namespace>
kubectl get endpointslice -n <namespace> -l kubernetes.io/service-name=<service>
```

# PART 2. 중급 아키텍처·자동화 (40%)

## Q5. ALB와 NLB를 어떻게 선택하나요?

**모범 답변:** ALB는 L7 HTTP/HTTPS 트래픽에서 호스트·경로 기반 라우팅, HTTP 관련 기능이 필요할 때 적합합니다. NLB는 L4 TCP/UDP/TLS 중심으로 높은 처리량, 낮은 지연, 고정 IP 요구 등에 적합합니다. 프로토콜과 기능 요구사항을 먼저 파악하고 선택합니다.

**실습 연결:** ALB DNS를 대상으로 여러 번 `curl`을 호출해 응답 분산을 확인하고, `/dir1/index.html` 및 `/dir11/index.html` 경로를 검사했습니다.

**주의:** 100회 요청 결과가 균등하지 않다고 즉시 장애라고 판단하지 않습니다. 연결 재사용, 알고리즘, 대상 가중치, 타깃 상태를 확인해야 합니다.

## Q6. CloudFront의 캐시 적중률이 낮다면?

**답변 흐름:** ① 캐시 정책과 TTL 확인 ② Cache Key에 포함된 헤더·쿠키·쿼리 문자열 확인 ③ Origin의 Cache-Control 응답 확인 ④ 요청 패턴과 객체 크기 분석 ⑤ 배포 변경 후 실제 응답 헤더로 검증.

```bash
curl -I https://<distribution-domain>/<path>
# x-cache, age, cache-control 등의 헤더 확인
```

**꼬리 질문:** CloudFront를 쓴다고 모든 요청이 캐시되나요?  
**답:** 아닙니다. 정책, 메서드, 응답 헤더, TTL 및 요청 특성에 따라 캐시 동작이 달라집니다.

## Q7. Route 53, ACM, CloudFront를 함께 사용할 때 HTTPS 경로는?

**모범 답변:** Route 53의 Alias 레코드로 도메인을 CloudFront 배포에 연결하고, CloudFront의 대체 도메인 이름과 ACM 인증서를 설정합니다. **CloudFront에 연결하는 ACM 인증서는 us-east-1 리전에 있어야 합니다.** Origin과 CloudFront 간 TLS도 별도 검토합니다.

## Q8. Ansible의 멱등성(Idempotency)이 왜 중요하나요?

**모범 답변:** 동일한 Playbook을 반복 실행해도 원하는 최종 상태가 유지되도록 하는 성질입니다. 재실행이 안전해야 구성 드리프트 수정과 반복 배포가 쉬워집니다. `shell`로 무조건 파일을 추가하는 방식보다 상태 기반 모듈(`package`, `service`, `file`, `template`)을 우선 사용합니다. 모든 태스크가 자동으로 멱등적인 것은 아닙니다.

```yaml
- name: Ensure httpd is installed and running
  hosts: web
  become: true
  tasks:
    - name: Install httpd
      ansible.builtin.package:
        name: httpd
        state: present
    - name: Start and enable httpd
      ansible.builtin.service:
        name: httpd
        state: started
        enabled: true
```

## Q9. Ansible Handler는 일반 Task와 어떻게 다른가요?

**모범 답변:** Handler는 `notify`를 통해 호출되며 일반적으로 변경(`changed`)이 발생했을 때 실행됩니다. 예를 들어 설정 파일이 실제로 바뀌었을 때만 웹 서버를 재시작해 불필요한 중단을 줄입니다. 기본적으로 해당 플레이의 일반 태스크 이후 실행되며 `meta: flush_handlers`로 앞당길 수 있습니다.

```yaml
- name: Deploy config
  ansible.builtin.template:
    src: httpd.conf.j2
    dest: /etc/httpd/conf/httpd.conf
    mode: '0644'
  notify: Restart httpd

handlers:
  - name: Restart httpd
    ansible.builtin.service:
      name: httpd
      state: restarted
```

**꼬리 질문:** 설정이 변경되지 않았다면?  
**답:** 정상적인 상태 기반 태스크라면 `changed=false`가 되어 Handler가 호출되지 않습니다.

## Q10. Terraform과 CloudFormation의 차이는?

**모범 답변:** 둘 다 IaC 도구입니다. Terraform은 여러 제공자의 리소스를 선언형으로 관리하고 일반적으로 State 파일로 관리 상태를 추적합니다. CloudFormation은 AWS 네이티브 스택 중심으로 리소스를 관리합니다. 팀의 클라우드 범위, 상태 관리, 모듈화, 운영 체계를 고려해 선택합니다.

```bash
terraform fmt -check
terraform validate
terraform plan
terraform apply
terraform destroy
```

**꼬리 질문:** `terraform apply -auto-approve`를 운영에서 남용하면?  
**답:** 변경 검토 단계를 생략해 잘못된 삭제·변경 위험이 커집니다. PR 기반 검토와 plan 확인, 정책 검사, 승인 절차가 중요합니다.

## Q11. Terraform 리소스 의존성은 어떻게 결정되나요?

**모범 답변:** `aws_subnet.public.id`처럼 다른 리소스 속성을 참조하면 Terraform이 암시적 의존성을 추론합니다. 참조만으로 관계를 표현하기 어려운 경우에 한해 `depends_on`을 명시합니다. 무분별한 `depends_on`은 실행 순서를 불필요하게 제한할 수 있습니다.

## Q12. EKS와 직접 구축한 Kubernetes 클러스터의 차이는?

**모범 답변:** EKS는 AWS가 Kubernetes 컨트롤 플레인 운영을 관리하는 서비스입니다. 다만 워커 노드 또는 Fargate 설정, 네트워크, IAM, 워크로드, 비용 및 보안 책임은 여전히 사용자가 검토해야 합니다. 직접 구축한 클러스터는 컨트롤 플레인까지 설치·업그레이드·백업 책임이 커집니다.

# PART 3. 고급 장애 대응·압박 면접 (40%)

## Q13. `kubectl get pods`에 `Pending`이 보이면 무엇부터 보나요?

**진단 순서:**
1. `kubectl describe pod <pod> -n <ns>`의 Events에서 스케줄링 실패 원인을 확인합니다.
2. 노드의 `Ready`, taint, allocatable 자원 및 Pod 요청량을 확인합니다.
3. PVC 바인딩, nodeSelector/affinity, toleration 조건을 확인합니다.
4. 원인에 따라 자원 확보, 노드 복구, 스토리지 설정 수정 등을 진행합니다.

```bash
kubectl get nodes -o wide
kubectl describe node <node>
kubectl describe pod <pod> -n <ns>
kubectl get pvc -A
kubectl get events -A --sort-by=.lastTimestamp
```

**압박 질문:** "메모리가 부족하니 Pod를 무조건 삭제하면 되죠?"  
**답:** 아닙니다. 요청량, 실제 사용량, 스케줄러 이벤트, 재생성 정책을 확인하지 않으면 동일 문제가 반복됩니다.

## Q14. `CrashLoopBackOff`와 `OOMKilled`를 구분해 설명하세요.

**모범 답변:** `CrashLoopBackOff`는 컨테이너가 반복 종료되어 재시작 백오프 상태인 현상입니다. `OOMKilled`는 메모리 부족으로 프로세스가 종료된 구체적 이유 중 하나입니다. 따라서 CrashLoopBackOff의 원인은 OOM 외에도 설정 오류, 애플리케이션 예외, 프로브 실패 등이 될 수 있습니다.

```bash
kubectl describe pod <pod> -n <ns>
kubectl logs <pod> -n <ns> --previous
kubectl top pod -n <ns>
kubectl get pod <pod> -n <ns> -o jsonpath='{.status.containerStatuses[*].lastState}'
```

**실습 연결:** VMware 환경에서 메모리 부족으로 프로세스가 종료된 경험을 설명할 때, **호스트/게스트 OS OOM과 Kubernetes 컨테이너 OOM을 구별**해 말합니다.

## Q15. NodePort에 접속되지 않으면 어떻게 좁혀가나요?

**진단 순서:** Service 포트와 `nodePort` 확인 → Service selector와 EndpointSlice 확인 → Pod Ready 확인 → 노드 IP·라우팅·방화벽 확인 → kube-proxy/CNI 및 노드 상태 확인.

```bash
kubectl get svc -n <ns> -o wide
kubectl describe svc <svc> -n <ns>
kubectl get endpointslice -n <ns> -l kubernetes.io/service-name=<svc>
kubectl get pods -n <ns> -o wide --show-labels
curl -v --connect-timeout 3 http://<node-ip>:<nodeport>
```

**압박 질문:** "Pod가 Running이면 서비스는 무조건 정상 아닌가요?"  
**답:** 아닙니다. Running은 프로세스 상태의 일부일 뿐이며 readiness, 포트 매핑, 셀렉터, 네트워크 경로를 확인해야 합니다.

## Q16. NFS 기반 PV/PVC에서 Pod가 파일을 못 쓰면?

**답변 흐름:** PVC `Bound` 여부 → Pod 볼륨 마운트 이벤트 → NFS 서버 export 및 접근 가능 여부 → UID/GID·권한 → SELinux 및 네트워크 정책 → 실제 마운트 경로를 점검합니다.

```bash
kubectl get pv,pvc -A
kubectl describe pvc <pvc> -n <ns>
kubectl describe pod <pod> -n <ns>
# NFS 서버에서
exportfs -v
```

**꼬리 질문:** `ReadWriteMany`만 설정하면 모든 스토리지에서 공유 쓰기가 되나요?  
**답:** 아닙니다. 실제 스토리지와 CSI 드라이버가 해당 접근 모드를 지원해야 합니다.

## Q17. ALB 뒤 EC2가 정상인데 502 또는 503이 발생하면?

**모범 답변:** 우선 정확한 상태 코드와 발생 주체를 구분합니다. ALB의 502는 백엔드 연결·응답 형식 등 문제를, 503은 사용 가능한 대상 부재 등 문제를 의심할 수 있지만 코드만으로 단정하지 않습니다. 대상 그룹 헬스 체크, 대상 포트, SG, 애플리케이션 로그, ALB 액세스 로그 및 CloudWatch 지표를 함께 확인합니다.

## Q18. CloudFront에서 403이 발생하면 무조건 WAF 차단인가요?

**모범 답변:** 아닙니다. WAF 규칙 차단 외에도 S3 Origin 접근 정책, OAC 설정, 객체 권한, 경로, 지리적 제한 등 여러 원인이 있습니다. WAF 로그와 CloudFront 응답, Origin의 직접 응답을 비교해 구분해야 합니다.

**실습 연결:** WAF 규칙 적용 후 403 응답을 확인했던 경험을 말하면서, **403이라는 결과만으로 모든 403의 원인을 WAF라고 판단하지 않는다**고 강조합니다.

## Q19. Ansible Playbook 실행 도중 일부 호스트만 실패했다면?

**답변 흐름:** 실패 호스트·태스크 식별 → SSH/권한/패키지 저장소·배포판 차이 확인 → `--check`, `--diff`, `--limit` 등으로 영향 범위 축소 → 안전하게 수정 후 재실행 → 최종 상태 검증.

```bash
ansible-playbook -i inventory site.yml --syntax-check
ansible-playbook -i inventory site.yml --check --diff
ansible-playbook -i inventory site.yml --limit web1 -vv
```

**주의:** Check Mode는 모듈별 지원 범위가 달라 실제 실행을 완전히 대체하지 못합니다. `--diff` 출력에 민감한 설정값이 포함되지 않도록 주의합니다.

## Q20. Terraform State를 팀원이 동시에 변경하려 하면?

**모범 답변:** 공동 작업에서는 원격 State 저장과 잠금 체계, 접근 권한, 버전 관리, 백업 전략이 중요합니다. 잠금 없이 동시 변경하면 상태 충돌이나 잘못된 리소스 변경이 발생할 수 있습니다. 사용하는 Terraform 버전과 백엔드에 맞는 잠금 방식을 확인합니다.

**압박 질문:** "State에 비밀 값이 있을 수 있나요?"  
**답:** 있습니다. `sensitive` 표시가 CLI 노출을 줄일 수 있어도 State 자체의 보안 저장과 접근 통제가 필요합니다.

| NAT Gateway vs Internet Gateway | IGW는 VPC와 인터넷의 경로, NAT Gateway는 사설 자원의 주로 외부 발신 연결을 지원 |
| Horizontal vs Vertical Scaling | 수평은 인스턴스/Pod 수 증가, 수직은 개별 인스턴스 자원 증가 |
| Liveness vs Readiness Probe | Liveness는 재시작 판단, Readiness는 서비스 트래픽 수신 준비 판단 |
| Rolling Update vs Recreate | 점진적 교체 vs 기존 Pod 종료 후 신규 Pod 생성; 가용성·호환성 요구에 따라 선택 |
| Ansible vs Terraform | 구성 관리·절차 자동화에 강점 vs 인프라 리소스 선언·상태 관리에 강점; 함께 사용 가능 |

# PART 5. 실전 모의 면접 시나리오

### 시나리오 A — 배포 직후 장애

**상황:** EKS에 새 이미지를 배포했더니 Pod는 Running인데 ALB로 접속하면 503이 발생합니다.

**답변 골격:**
1. 장애 범위와 배포 시각을 확인하고 이전 정상 버전과 비교합니다.
2. ALB 대상 그룹에 정상 대상이 있는지 확인합니다.
3. Kubernetes Service, EndpointSlice, Pod readiness를 확인합니다.
4. 헬스 체크 경로, 포트, 보안 그룹, Ingress/컨트롤러 구성을 점검합니다.
5. 영향이 크면 사전에 정한 기준에 따라 롤백하고 원인 분석을 이어갑니다.

### 시나리오 B — 반복 배포 후 서버가 계속 재시작

**상황:** Ansible을 재실행할 때마다 httpd가 재시작됩니다.

**답변 골격:**
1. 태스크의 `changed` 여부를 확인합니다.
2. `shell`/`command` 또는 매번 바뀌는 템플릿 결과가 원인인지 확인합니다.
3. 상태 기반 모듈과 `notify`/Handler로 변경 시에만 재시작하도록 수정합니다.
4. 두 번 연속 실행해 두 번째 실행에서 불필요한 변경이 없는지 검증합니다.

### 시나리오 C — 비용 급증

**상황:** AWS 실습을 마쳤는데 예상보다 청구 금액이 큽니다.

**답변 골격:**
1. Cost Explorer 및 청구서로 서비스·리전별 비용을 확인합니다.
2. EC2뿐 아니라 NAT Gateway, Load Balancer, EIP, EBS, EKS, CloudFront 등 잔존 자원을 확인합니다.
3. Auto Scaling Group, Launch Template 및 연결된 리소스의 실제 상태를 확인합니다.
4. 필요 없는 리소스를 의존성에 맞춰 삭제하고 비용 알림·예산을 설정합니다.
