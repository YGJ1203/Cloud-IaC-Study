# 1. Docker 핵심 개념

## 1.1 Image와 Container

``` text
Image = 실행 환경을 만들기 위한 읽기 중심의 템플릿
Container = Image를 실제 프로세스로 실행한 인스턴스
```

예:

``` bash
docker image pull nginx
docker container run -d --name web1 nginx
```

``` text
nginx Image
    │
    ├── web1 Container
    ├── web2 Container
    └── web3 Container
```

같은 Image에서 여러 Container를 만들 수 있다.

------------------------------------------------------------------------

## 1.2 Docker의 핵심 객체

  객체         역할
  ------------ --------------------------------------
  Image        Container의 원본
  Container    실제 실행되는 프로세스 환경
  Network      Container 간 통신
  Volume       Container 데이터 영속화
  Registry     Image 저장/배포
  Dockerfile   Image 제작 설계서
  Compose      여러 Container/Service를 YAML로 선언

# 4. Container의 생명주기와 PID 1

Docker Container는 내부의 **PID 1 프로세스가 살아 있는 동안 실행 상태를
유지**한다.

``` text
PID 1 실행
   ↓
Container Running

PID 1 종료
   ↓
Container Exited
```

따라서 nginx 같은 서버를 Dockerfile에서 직접 실행할 때는 foreground
실행이 중요하다.

``` dockerfile
CMD ["nginx", "-g", "daemon off;"]
```

------------------------------------------------------------------------

# 5. `attach` vs `exec` ★★★

## attach

현재 Container의 **기존 PID 1 프로세스 입출력에 연결**한다.

``` bash
docker container attach test7
```

Container를 종료하지 않고 빠져나오기:

``` text
Ctrl + P
Ctrl + Q
```

> `Ctrl+C`, `exit`는 상황에 따라 Container의 메인 프로세스까지 종료시킬
> 수 있으므로 주의한다.

## exec

실행 중인 Container 내부에 **새 프로세스를 추가 실행**한다.

``` bash
docker container exec -it testweb /bin/bash
```

실무/실습에서 Container 내부를 점검할 때는 보통 `exec`가 편하다.

``` bash
docker exec testweb ps -ef
docker exec testweb cat /etc/os-release
```

# 7. Port Mapping

Container의 포트는 Host의 포트와 자동으로 연결되지 않는다.

``` bash
docker container run -d \
  --name myweb \
  -p 8080:80 \
  nginx
```

의미:

``` text
Browser
   │
   ▼
Host :8080
   │
   ▼
Container :80
   │
   ▼
nginx
```

확인:

``` bash
docker container ls
curl http://localhost:8080
```

### 이번 주 트러블슈팅 포인트 ☠️

``` bash
docker run -d --name test-nginx nginx
curl localhost
```

이 경우 Container의 `80/tcp`가 존재해도 **Host의 80번 포트와 publish된
것은 아니다.**

따라서 외부/Host에서 접근하려면:

``` bash
docker run -d \
  --name test-nginx \
  -p 8080:80 \
  nginx
```

``` bash
curl localhost:8080
```

# 9. Volume과 Bind Mount ★★★

Container의 writable layer에만 데이터를 저장하면 Container 삭제 시
데이터 관리가 불편하다.

그래서 외부 저장소를 연결한다.

## Named Volume

``` bash
docker volume create testvol
docker volume ls
docker volume inspect testvol
```

실행:

``` bash
docker container run -itd \
  --name myweb \
  -v testvol:/usr/share/nginx/html \
  -p 8080:80 \
  nginx
```

구조:

``` text
Docker Volume
     │
     ▼
Container
/usr/share/nginx/html
```

## Bind Mount

``` bash
docker run -d \
  -v /host/path:/container/path \
  IMAGE
```

차이:

``` text
Named Volume
Docker가 저장 위치를 관리

Bind Mount
사용자가 Host 경로를 직접 지정
```

# 11. Portainer

Portainer는 Docker Engine을 웹 GUI에서 관리하는 도구이다.

``` bash
docker container run -itd \
  --name portainer \
  --restart=always \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v portainer_data:/data \
  -p 9000:9000 \
  portainer/portainer-ce
```

핵심:

``` text
Browser
   │
   ▼
Portainer Container
   │
   │ /var/run/docker.sock
   ▼
Docker Engine
   │
   ├── Container
   ├── Image
   ├── Network
   └── Volume
```

`/var/run/docker.sock`이 특히 중요하다.

Portainer가 Docker를 대체하는 것이 아니라:

> **Docker Engine을 GUI로 관리하는 Front-end**

이다.

문제 확인:

``` bash
docker container logs portainer
docker container restart portainer
```

실습에서는 Portainer의 HTTP `9000`, HTTPS `9443`, 설정 보존용
`portainer_data` Volume도 확인했다.

# 12. Container 자원 관리

Docker는 Linux Kernel 기능을 활용한다.

``` text
Namespace
= 무엇을 볼 수 있는가?
= 격리

cgroup
= 얼마나 사용할 수 있는가?
= 자원 제한
```

Host 자원 확인:

``` bash
free
lsmem
lscpu
lsblk
```

Container 자원 사용 확인:

``` bash
docker stats
```

CPU / Memory / Block I/O 등을 제한할 수 있다.

### ☠️ 이번 주 대형 사고

`stress` 실습 중 Disk I/O를 극단적으로 제한하여 **100 B/s 수준**으로
설정하면서 Container/shim 및 Docker/containerd 처리까지 지연되는 상황을
경험했다.

복구 흐름:

``` text
Container 이상
   ↓
Docker/containerd 재시작 시도
   ↓
처리 지연
   ↓
VM reboot
   ↓
docker run --rm hello-world
   ↓
nginx Container 실행
   ↓
정상 여부 검증
```

여기서 얻을 교훈:

> 자원 제한 실습에서는 단위를 반드시 확인하고, 특히 Disk I/O를 지나치게
> 낮게 설정하면 서비스 자체가 멈춘 것처럼 보일 수 있다.

# 14. `export/import` vs `save/load` ★★★

## Container → export/import

``` bash
docker container export testweb1 -o testweb1.tar
```

복원:

``` bash
cat testweb1.tar | docker image import - myimage:1.0
```

``` text
Container
   ↓ export
Filesystem TAR
   ↓ import
Image
```

## Image → save/load

``` bash
docker image save -o image.tar ubuntu:latest
docker image load -i image.tar
```

``` text
Image
  ↓ save
Image Archive
  ↓ load
Image
```

### 무조건 기억

  출발점      내보내기   복원
  ----------- ---------- ----------
  Container   `export`   `import`
  Image       `save`     `load`

``` text
Container = export / import
Image     = save / load
```

# 15. Dockerfile ★★★★★

Dockerfile은 **Image를 어떻게 만들지 정의하는 설계서**이다.

``` text
Dockerfile
   ↓
docker image build
   ↓
Image
   ↓
docker container run
   ↓
Container
```

주요 명령:

  명령           역할
  -------------- --------------------------
  `FROM`         Base Image
  `RUN`          Build 시 명령 실행
  `COPY`         Host 파일 복사
  `ADD`          COPY + 일부 추가 기능
  `WORKDIR`      작업 디렉터리
  `ENV`          환경변수
  `EXPOSE`       사용 포트 정보
  `VOLUME`       데이터 저장 경로
  `CMD`          기본 실행 명령/인자
  `ENTRYPOINT`   주 실행 프로그램
  `ONBUILD`      자식 Image Build 시 실행

# 16. Debian + nginx Dockerfile 실습

이번 주 후반부에는 수동 작업을 Dockerfile로 바꾸는 흐름을 직접 실습했다.

먼저 Container에서 수동으로:

``` bash
docker container run -itd \
  --name test1 \
  -p 8081:80 \
  debian

docker container exec -it test1 /bin/bash
```

패키지 설치:

``` bash
apt update && apt -y install \
  vim procps curl \
  iputils-ping bind9-dnsutils \
  iproute2 net-tools nginx
```

Debian 최소 Image에서는 처음부터 `ping`, `nslookup`, `ip` 등이 모두
존재한다고 가정하면 안 된다.

예:

``` text
ping      → iputils-ping
nslookup  → bind9-dnsutils
ip        → iproute2
```

이를 Dockerfile로 자동화:

``` dockerfile
FROM debian

RUN apt update && \
    apt install -y \
    vim procps curl \
    iputils-ping bind9-dnsutils \
    iproute2 net-tools nginx

COPY hyundai_index.html /var/www/html/index.html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
```

Build:

``` bash
docker image build \
  -t debian-nginx \
  . \
  -f Dockerfile1
```

# 17. Build Context ★★★

``` bash
docker image build -t debian-nginx . -f Dockerfile1
```

여기서 `.`은 매우 중요하다.

``` text
.
└── 현재 Directory를 Build Context로 전달
```

예:

``` text
/root/docker/
├── Dockerfile1
└── hyundai_index.html
```

Dockerfile의:

``` dockerfile
COPY hyundai_index.html /var/www/html/index.html
```

은 **Build Context 내부의 파일**을 대상으로 한다.

흔한 실수:

``` bash
docker image build -t myimage
```

Build Context가 빠짐.

교정:

``` bash
docker image build -t myimage .
```

# 18. Image Layer

Docker Image는 여러 Layer가 쌓여 만들어진다.

``` dockerfile
FROM nginx
COPY testfile /tmp/
COPY index.html /usr/share/nginx/html/
```

개념적으로:

``` text
Layer 3 : COPY index.html ...
Layer 2 : COPY testfile ...
Layer 1 : nginx Base Image
```

이 구조 덕분에 Docker는 변경되지 않은 Layer를 재사용/cache할 수 있다.

Dockerfile 작성 시 불필요한 Layer와 불필요한 파일을 줄이는 것이
중요하다.

# 20. Single-stage / Multi-stage Build

Go 실습:

``` go
package main

import "fmt"

func main() {
    fmt.Println("Hello, World!")
}
```

Single-stage 예:

``` dockerfile
FROM golang:1.16

WORKDIR /go/src/github.com/test/hello

RUN go get -d -v github.com/urfave/cli

COPY main.go main.go

RUN GOOS=linux go build -a -o hello main.go

ENTRYPOINT ["./hello"]
```

Build:

``` bash
docker image build \
  -t singlestage \
  . \
  -f Dockerfile1
```

문제점:

``` text
실행 파일 하나만 필요해도
Go Compiler / Build Tool / Dependency가
최종 Image에 함께 남을 수 있다.
```

Multi-stage의 목적:

``` text
Stage 1
Compiler + Source
      │
      │ build
      ▼
Binary
      │
      │ COPY --from
      ▼
Stage 2
작은 Runtime Image
```

장점:

-   최종 Image 크기 감소
-   Build 도구 제거
-   공격 표면 감소
-   배포 Image 단순화

# 21. Docker Compose / YAML

Dockerfile이 **Image 하나의 설계서**라면 Compose는 **여러 Service의 실행
구성을 정의하는 설계서**라고 보면 된다.

``` text
Dockerfile
= Image 제작

Compose YAML
= Application 구성
```

대표 구조:

``` yaml
services:
  web:
    image: nginx
    ports:
      - "8080:80"

  db:
    image: mysql:5.7
    environment:
      MYSQL_ROOT_PASSWORD: example
```

주요 요소:

``` text
services
 ├─ image
 ├─ build
 ├─ container_name
 ├─ ports
 ├─ volumes
 ├─ networks
 ├─ environment
 └─ depends_on
```

YAML은 들여쓰기가 구조 그 자체이므로 **Tab보다 Space 사용**이 안전하다.

이번 실습에서는 Sublime Text로 `.yml` 파일도 작성했다.

주요 명령:

``` bash
docker compose config
docker compose up -d
docker compose ps
docker compose logs
docker compose exec SERVICE COMMAND
docker compose stop
docker compose start
docker compose restart
docker compose down
```

특히:

``` bash
docker compose config
```

은 YAML을 파싱하고 실제 Compose 구성을 확인하는 데 매우 유용하다.

# 22. Compose로 여러 Container 관리

CLI만 사용하면:

``` bash
docker run ...
docker run ...
docker network create ...
docker volume create ...
```

처럼 각각 관리해야 한다.

Compose에서는:

``` text
compose.yml
    │
    ├── Service A
    ├── Service B
    ├── Network
    └── Volume
```

을 한 파일에서 선언하고:

``` bash
docker compose up -d
```

로 전체 환경을 올릴 수 있다.

이번 실습 흐름은 DB와 관리 UI를 묶는 형태까지 확장되었다.

``` text
MongoDB ↔ Mongo Express

PostgreSQL ↔ Adminer
```

즉 Compose의 핵심은:

> **여러 Container를 하나의 Application Stack으로 선언하고 관리하는 것**

# 23. 환경변수와 DB Container

DB Image는 실행 시 환경변수를 요구하는 경우가 많다.

예:

``` bash
docker run -d \
  --name mysql \
  -e MYSQL_ROOT_PASSWORD=example \
  mysql:5.7
```

Compose에서는:

``` yaml
services:
  db:
    image: mysql:5.7
    environment:
      MYSQL_ROOT_PASSWORD: example
```

핵심:

``` text
-e KEY=VALUE
      ↓
Container 환경변수
      ↓
Application 초기 설정
```

MongoDB 등도 같은 방식으로 계정/비밀번호 같은 초기값을 전달할 수 있다.

# 24. MySQL과 Volume

DB Container에서 가장 중요한 것 중 하나가 **데이터 영속성**이다.

``` text
Container 삭제
     │
     ├─ Container 내부 데이터만 사용 → 데이터 손실 가능
     │
     └─ Volume 사용 → 데이터 유지
```

따라서 DB에서는 Volume을 특히 중요하게 봐야 한다.

``` bash
docker volume ls
docker volume inspect VOLUME
```

Docker Image가 `VOLUME`을 선언한 경우 명시적 Named Volume을 지정하지
않아도 익명 Volume이 만들어질 수 있다.

# 25. Private Registry 개념

이번 주 후반부에는 Image를 Docker Hub 같은 외부 Registry만이 아니라 직접
운영하는 Registry에 저장하는 흐름까지 확장했다.

``` text
Docker1
  │
  │ build
  ▼
Image
  │
  │ tag
  ▼
Private Registry
  │
  │ pull
  ▼
Docker2
```

핵심 흐름:

``` text
build → tag → push → pull
```

보안까지 적용하면:

``` text
Private Registry
   ├── TLS 인증서
   ├── CA 신뢰
   └── htpasswd 인증
```

Docker를 단순한 로컬 Container 실행 도구가 아니라 **Image 배포 체계**로
이해하기 시작하는 단계다.

# 27. 이번 주 시험/면접 핵심 Q&A

### Q1. Image와 Container 차이는?

Image는 Container를 생성하기 위한 템플릿이고, Container는 Image를 실제
프로세스로 실행한 인스턴스다.

### Q2. `docker run`과 `docker exec`의 차이는?

`run`은 Image에서 새 Container를 생성하고 실행하며, `exec`는 이미 실행
중인 Container에서 추가 명령/프로세스를 실행한다.

### Q3. `EXPOSE 80`이면 외부에서 접속 가능한가?

아니다. `EXPOSE`는 Image의 포트 정보를 기록하는 의미이며 Host에 실제
publish하려면 `-p HOST:CONTAINER`가 필요하다.

### Q4. Volume을 사용하는 이유는?

Container의 생명주기와 데이터를 분리하여 Container를 삭제/재생성해도
데이터를 유지하기 위해서다.

### Q5. `export`와 `save` 차이는?

`export`는 Container filesystem을 내보내며 `import`와 연결된다. `save`는
Image 자체를 보관하며 `load`와 연결된다.

### Q6. Dockerfile의 `RUN`과 `CMD` 차이는?

`RUN`은 Image Build 과정에서 실행되고, `CMD`는 Container가 시작될 때
사용할 기본 명령/인자를 정의한다.

### Q7. Dockerfile과 Compose 차이는?

Dockerfile은 Image를 만드는 방법을 정의하고, Compose는 여러
Service/Container와 Network, Volume 등의 실행 구성을 정의한다.

### Q8. Multi-stage Build를 쓰는 이유는?

Build 환경과 Runtime 환경을 분리하여 최종 Image에서 Compiler나 Build
Tool을 제거하고 Image 크기와 공격 표면을 줄이기 위해서다.

### Q9. Portainer란?

Docker Engine을 웹 GUI에서 관리할 수 있게 해주는 Front-end 관리 도구다.

### Q10. Container가 갑자기 종료되는 대표적인 이유는?

Container의 PID 1, 즉 메인 프로세스가 종료되었기 때문이다.

# 31. 이번 주 학습 평가

이번 주는 Docker를 처음 접한 주였지만 학습 범위는 꽤 깊었다.

``` text
Docker 기본 구조
   ↓
Container 운용
   ↓
Network / Volume
   ↓
Portainer
   ↓
자원 제한
   ↓
Image 생성/백업
   ↓
Dockerfile
   ↓
Layer / Build Context
   ↓
Multi-stage
   ↓
Compose / YAML
   ↓
DB 연동
   ↓
Private Registry
```

특히 중요한 것은 명령어 개수가 아니다.

**Linux에서 배운 Process / Network / Storage 개념이 Docker에서 다시
등장하고 있다.**

``` text
Linux Process  → Container
Linux Network  → Docker Network
Linux Mount    → Docker Volume
Linux Resource → cgroup
Server Config  → Dockerfile
여러 Server 구성 → Docker Compose
```

따라서 Docker는 완전히 새로운 분야라기보다, 지금까지 배운 Linux 인프라
개념을 **Container 방식으로 다시 조립하는 과정**으로 보면 이해가 훨씬
쉬워진다.

           ↓
