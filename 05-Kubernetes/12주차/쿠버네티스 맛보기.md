# ☸️ Kubernetes 수업 전 사전 핵심 정리

> **목표:** Kubernetes 명령어를 외우는 것이 아니라  
> **“왜 Docker 다음에 Kubernetes가 필요한가?”​**를 이해하고 수업에 들어가기

---

# 1. Kubernetes가 뭐죠?

**Kubernetes(K8s)** 는 여러 서버에 존재하는 ​**컨테이너를 자동으로 배포하고 관리하는 컨테이너 오케스트레이션 플랫폼**이다.

Docker가 주로

```text
컨테이너를 만든다
컨테이너를 실행한다
```

에 집중한다면,

Kubernetes는

```text
컨테이너를 어디에 실행할지 결정
필요한 개수 유지
장애 발생 시 복구
네트워크 연결
트래픽 분산
업데이트
스토리지 연결
```

등을 자동화한다.

즉,

```text
Docker
→ 컨테이너 실행

Kubernetes
→ 수많은 컨테이너 운영/관리
```

라고 먼저 이해하면 된다.

---

# 2. 왜 Kubernetes가 필요한가?

Docker만 사용하는 상황을 생각해보자.

```bash
docker run -d nginx
```

nginx 컨테이너 하나 정도는 사람이 직접 관리할 수 있다.

하지만 실제 서비스에서

```text
Web Container     × 30
API Container     × 20
DB Container      × 5
Redis Container   × 5
```

처럼 수십~수백 개의 컨테이너이 운영된다면 문제가 생긴다.

예를 들어 Web 컨테이너 하나가 죽었다.

```text
관리자
"어...? nginx 하나 죽었네?"

→ 직접 확인
→ 직접 다시 실행
```

서버 자체가 죽으면 더 복잡해진다.

Kubernetes를 사용하면 이런 작업을 자동화할 수 있다.

```text
Web Pod 3개 필요
       ↓
Kubernetes가 계속 확인
       ↓
Pod 하나 장애 발생 💀
       ↓
자동으로 새로운 Pod 생성
       ↓
다시 3개 유지
```

이것을 **Self-Healing(자가 치유)** 이라고 한다.

---

# 3. Kubernetes의 핵심 철학: Desired State

Kubernetes에서 굉장히 중요한 개념이다.

관리자가 직접

```text
컨테이너 하나 실행해!
```

라고 명령하는 것보다,

```text
nginx를 3개 실행하고 있는 상태를 유지해줘.
```

라고 **원하는 상태(Desired State)** 를 선언한다.

예:

```yaml
replicas: 3
```

의미:

```text
나는 nginx 애플리케이션이
항상 3개 실행되기를 원한다.
```

현재 상태가

```text
Pod 3개
```

라면 Kubernetes:

```text
정상 😎
```

Pod 하나가 죽어서

```text
Pod 2개
```

가 되면 Kubernetes:

```text
Desired = 3
Current = 2

→ 하나 부족함
→ 새 Pod 생성
```

다시

```text
Pod 3개
```

가 된다.

### 핵심

```text
Desired State
      ↓
Kubernetes
      ↓
Current State를 계속 비교
      ↓
Desired State에 맞춤
```

이 개념은 Kubernetes 전체를 관통한다.

---

# 4. Kubernetes Cluster 구조

Kubernetes 환경 전체를 **Cluster**라고 한다.

크게 두 영역이 있다.

```text
Kubernetes Cluster
│
├── Control Plane
│
│   └── 클러스터 관리
│
└── Worker Node
    │
    └── 실제 애플리케이션 실행
```

쉽게 표현하면

```text
Control Plane = 감독/지휘관 🧠
Worker Node   = 실제 작업자 💪
```

이다.

---

# 5. Control Plane

클러스터 전체를 관리한다.

대표 구성 요소:

```text
kube-apiserver
etcd
kube-scheduler
kube-controller-manager
```

## kube-apiserver

Kubernetes의 **중앙 통신 창구**.

사용자가

```bash
kubectl get pods
```

같은 명령을 입력하면 요청이 API Server로 전달된다.

```text
kubectl
   ↓
API Server
   ↓
Kubernetes Cluster
```

매우 중요한 구성 요소다.

---

## etcd

Kubernetes 클러스터의 상태 정보를 저장하는 **Key-Value Database**.

예:

```text
어떤 Pod가 존재하는가?
Node 상태는 어떤가?
Service 설정은?
Deployment 설정은?
```

등의 중요한 클러스터 정보가 저장된다.

쉽게 말하면

```text
etcd = Kubernetes의 기억 🧠
```

---

## Scheduler

새로운 Pod를 **어떤 Worker Node에서 실행할지 결정**한다.

예:

```text
Worker1
CPU 여유 있음

Worker2
CPU 부족

Worker3
CPU 여유 있음
```

Scheduler:

```text
"새 Pod는 Worker1에서 돌리자."
```

주의:

> Scheduler가 직접 컨테이너를 실행하는 것은 아니다.

**어느 Node에 배치할지를 결정**하는 역할이다.

---

## Controller Manager

현재 상태와 원하는 상태가 일치하는지 계속 감시한다.

```text
Desired Pod = 3
Current Pod = 2

→ 하나 생성 필요
```

이러한 조정(Reconciliation)을 담당하는 여러 Controller를 실행한다.

---

# 6. Worker Node

실제 애플리케이션의 Pod가 실행되는 서버다.

대표 구성 요소:

```text
kubelet
kube-proxy
Container Runtime
```

## kubelet

각 Worker Node에서 동작하는 Kubernetes Agent.

Control Plane으로부터

```text
"이 Pod 실행해."
```

라는 정보를 받아 실제 Node에서 Pod가 실행되도록 관리한다.

---

## Container Runtime

실제 컨테이너를 실행한다.

대표적으로:

```text
containerd
CRI-O
```

등이 있다.

중요한 점:

> Kubernetes가 직접 컨테이너를 실행하는 것은 아니다.

Container Runtime을 통해 실행한다.

---

## kube-proxy

Service 네트워크 통신이 가능하도록 Node의 네트워크 규칙을 관리하는 구성 요소다.

초반에는 일단

```text
kube-proxy
→ Kubernetes Service 통신을 위한 네트워크 처리
```

정도로 이해하면 충분하다.

---

# 7. ⭐ Pod

내일 가장 많이 듣게 될 가능성이 높은 단어.

**Pod는 Kubernetes에서 배포할 수 있는 가장 작은 실행 단위**다.

Docker에서는:

```text
Container
```

Kubernetes에서는:

```text
Pod
 └── Container
```

보통 Pod 하나 안에 Container 하나가 들어간다.

예:

```text
Pod
└── nginx Container
```

하지만 필요하면 여러 Container를 넣을 수도 있다.

```text
Pod
├── Main Container
└── Sidecar Container
```

같은 Pod 내부의 Container들은 네트워크와 일부 리소스를 공유한다.

---

# 8. Container와 Pod를 구분하자

초반에 가장 헷갈리기 좋은 부분이다.

```text
Docker
Container 직접 관리

Kubernetes
Pod를 중심으로 관리
    ↓
Pod 내부에서 Container 실행
```

따라서 Kubernetes에서는 보통

```text
Container를 배포한다
```

보다는

```text
Pod를 배포한다
```

라는 관점으로 생각한다.

---

# 9. ReplicaSet

Pod의 **개수를 유지**한다.

예:

```yaml
replicas: 3
```

현재

```text
Pod
Pod
Pod
```

중 하나가 죽으면

```text
Pod
Pod
💀
```

ReplicaSet이 새로운 Pod를 만들어

```text
Pod
Pod
Pod
```

상태를 다시 유지한다.

---

# 10. ⭐ Deployment

실무 및 수업에서 매우 중요한 Object.

Deployment는 Pod/ReplicaSet을 관리하면서 애플리케이션의 **배포와 업데이트**를 담당한다.

구조를 단순화하면:

```text
Deployment
     ↓
ReplicaSet
     ↓
Pod
     ↓
Container
```

예:

```text
Deployment
  │
  └── ReplicaSet
        │
        ├── Pod → nginx
        ├── Pod → nginx
        └── Pod → nginx
```

따라서 실제 애플리케이션은 단독 Pod보다 **Deployment로 관리하는 경우가 일반적**이다.

---

# 11. ⭐ Service

Pod에는 중요한 문제가 있다.

> Pod는 생성되고 삭제될 수 있다.

그리고 새로 만들어진 Pod는 IP가 달라질 수 있다.

예:

```text
Pod1 → 10.244.1.10

Pod1 장애 💀

새 Pod → 10.244.2.7
```

클라이언트가 Pod IP를 직접 사용하면 문제가 발생한다.

그래서 **Service**를 사용한다.

```text
Client
   ↓
Service
   ↓
┌───────────────┐
│ Pod1          │
│ Pod2          │
│ Pod3          │
└───────────────┘
```

Service는 Pod들에게 접근할 수 있는 **안정적인 네트워크 엔드포인트**를 제공한다.

초반에는

```text
Pod = 실제 애플리케이션
Service = Pod로 접근하기 위한 안정적인 창구
```

라고 기억하면 된다.

---

# 12. Service 종류

대표적으로 다음이 있다.

```text
ClusterIP
NodePort
LoadBalancer
```

### ClusterIP

클러스터 내부에서 접근.

```text
Client inside Cluster
        ↓
   ClusterIP
        ↓
      Pods
```

기본 Service 타입이다.

### NodePort

Node의 특정 포트를 통해 외부에서 접근.

```text
외부 Client
     ↓
NodeIP:NodePort
     ↓
Service
     ↓
Pods
```

Docker에서 배웠던

```bash
-p 8080:80
```

과 완전히 동일한 개념은 아니지만, 처음 이해할 때 연결해서 보면 편하다.

### LoadBalancer

클라우드 환경의 Load Balancer와 연동하여 외부 서비스를 제공할 때 주로 사용한다.


처음부터 전부 외울 필요 없다.

내일은 우선:

```text

Deployment
ReplicaSet
Service
```

이 4개가 가장 중요하다.

# 14. YAML이 매우 중요하다 💀

Docker Compose를 했다면 상당히 익숙할 것이다.

Kubernetes에서는 리소스를 YAML 파일로 선언하는 경우가 많다.

기본 구조:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: my-nginx

spec:
  containers:
    - name: nginx
      image: nginx
```

핵심 구조:

```text
apiVersion
kind
metadata
spec
```

### apiVersion

어떤 Kubernetes API를 사용할지 지정.

### kind

무엇을 만들 것인가?

```yaml
kind: Pod
```

또는

```yaml
kind: Deployment
```

### metadata

Object 정보.

예:

```yaml
metadata:
  name: my-nginx
```

### spec

**원하는 상태(Desired State)** 를 정의한다.

예:

```yaml
spec:
  containers:
    - name: nginx
      image: nginx
```

# 18. Docker와 Kubernetes 연결하기 ⭐

Docker를 배웠다면 다음처럼 연결하면 된다.

| Docker | Kubernetes |
|---|---|
| Container | Pod 내부 Container |
| `docker run` | Pod/Deployment 생성 |
| `docker ps` | `kubectl get pods` |
| `docker inspect` | `kubectl describe` |
| `docker logs` | `kubectl logs` |
| `docker exec` | `kubectl exec` |
| `-p 8080:80` | Service |
| Docker Volume | PV/PVC |
| Docker Compose YAML | Kubernetes YAML |
| Container 관리 | Cluster 전체 관리 |

단, 각각이 **완전히 1:1로 동일한 기능이라는 뜻은 아니다.**

기존 Docker 지식에서 Kubernetes로 넘어가기 위한 개념적 연결이라고 보면 된다.

# 19. Kubernetes 네트워크에서 중요한 생각

네트워크를 이미 공부했다면 Kubernetes 네트워크는 상당히 재미있게 볼 수 있다.

기본적으로 다음 IP들이 등장한다.

```text
Node IP
Pod IP
Service IP
```

예:

```text
Node1
192.168.10.10

└── Pod
    10.244.1.10
```

그리고 Service:

```text
10.96.0.10
```

따라서 Kubernetes를 배우다 보면

```text
Routing
NAT
DNS
Load Balancing
Subnet
Firewall
```

같은 기존 네트워크 지식이 다시 등장한다.

특히 Kubernetes 내부 DNS를 통해 Service 이름으로 통신하는 구조도 배우게 된다.

# 20. Kubernetes Storage

Pod는 언제든 삭제되고 다시 생성될 수 있다.

따라서 중요한 데이터를 단순히 Pod 내부에만 저장하면 곤란하다.

그래서 Kubernetes에서는 영구적인 저장 공간을 다루기 위해 대표적으로

```text
PV  = PersistentVolume
PVC = PersistentVolumeClaim
```

을 사용한다.

처음에는 다음 정도로 기억하자.

```text
Pod
 ↓
PVC
 ↓
PV
 ↓
실제 Storage
```

Docker의 Volume을 공부했다면 나중에 연결해서 이해하기 좋다.

# 21. ConfigMap / Secret

환경설정과 애플리케이션을 분리하기 위한 Object다.

### ConfigMap

일반적인 설정 정보:

```text
DB_HOST
APP_MODE
PORT
```

### Secret

민감한 설정을 다루기 위한 리소스:

```text
DB_PASSWORD
API_KEY
TOKEN
```

단, Kubernetes Secret을 사용한다고 해서 그 자체만으로 모든 보안 문제가 해결되는 것은 아니다.

프로젝트/팀/환경별로 리소스를 분리할 때 사용할 수 있다.

# 23. Kubernetes의 핵심 장점

### Self-Healing

Pod 장애 시 자동 복구.

### Scaling

Pod 수를 증가/감소시킬 수 있다.

```text
3 Pods
   ↓
10 Pods
```

### Load Balancing

여러 Pod에 트래픽을 분산할 수 있다.

### Rolling Update

서비스 전체를 한꺼번에 중단하지 않고 새 버전으로 순차 업데이트할 수 있다.

### Rollback

문제가 발생하면 이전 버전으로 되돌릴 수 있다.

# 24. Docker → Kubernetes 전체 그림

지금까지 배운 내용을 한 번에 연결하면:

```text
Dockerfile
   ↓
docker build
   ↓
Container Image
   ↓
Registry
   ↓
Kubernetes
   ↓
Deployment
   ↓
ReplicaSet
   ↓
Pod
   ↓
Container
```

그리고 외부에서 접근:

```text
User
 ↓
Service
 ↓
Deployment가 관리하는 Pods
 ↓
Container
```

이 그림이 머릿속에 들어오면 Kubernetes 첫 수업의 절반은 성공이다.

# 25. 초반에 반드시 구분할 것 💀

### Container ≠ Pod

Pod는 하나 이상의 Container를 감싸는 Kubernetes 실행 단위.

### Pod ≠ Deployment

Deployment는 Pod들의 배포/업데이트 등을 관리한다.

### Deployment ≠ Service

Deployment는 **애플리케이션 실행 상태 관리**.

Service는 **네트워크 접근 경로 제공**.

### Node ≠ Pod

Node는 Pod가 실행되는 **서버/VM**.

# 26. 가장 중요한 구조

이 그림은 꼭 기억하자.

```text
            Kubernetes Cluster
                    │
       ┌────────────┴────────────┐

       │                         │
```

# 28. Docker 경험자용 10초 요약

Docker에서:

```bash
docker run nginx
```

했다면 Kubernetes에서는 사고방식을 이렇게 바꾼다.

```text
"nginx 하나 실행해"
        ↓
"nginx Pod가 항상 3개 존재하도록 유지해"
```

그리고 Kubernetes가

```text
어디에서 실행하지?
→ Scheduler

실제로 실행해
→ kubelet + Container Runtime

3개 제대로 살아 있나?
→ Controller

죽었네?
→ 다시 생성

사용자가 어디로 접속하지?
→ Service
```

를 관리한다.

# 🎯 내일 수업 전 최종 체크

아래 질문에 답할 수 있으면 충분하다.

```text
Q. Kubernetes는 왜 사용하는가?
→ 여러 컨테이너의 배포와 운영을 자동화하기 위해.

Q. Pod란?
→ Kubernetes의 최소 실행 단위.

Q. Node란?
→ Pod가 실행되는 서버.

Q. Deployment란?
→ Pod들의 배포와 업데이트를 관리하는 Object.

Q. ReplicaSet은?
→ 원하는 수의 Pod를 유지.

Q. Service는?
→ Pod에 안정적으로 접근할 수 있는 네트워크 엔드포인트.

Q. kubectl은?
→ Kubernetes Cluster를 조작하는 CLI.

Q. YAML은 왜 쓰는가?
→ 원하는 리소스 상태를 선언하기 위해.

Q. Pod 하나가 죽으면?
→ Controller가 원하는 상태와 비교하고 다시 생성되도록 조정한다.

Q. Kubernetes에서 가장 중요한 사고방식은?
→ "명령 하나씩 실행"보다 "원하는 상태를 선언하고 유지".
```

# 🔥 한 문장으로 끝내기

> **Docker가 컨테이너를 만드는 기술이라면, Kubernetes는 그 컨테이너들이 대규모 환경에서 원하는 상태로 계속 살아 있도록 배치·복구·확장·연결해주는 오케스트레이션 플랫폼이다.**

```text
Docker 🐳
   ↓
Image
   ↓
Container
   ↓
Pod
   ↓
Deployment
   ↓
Service
   ↓
Kubernetes Cluster ☸️
```

**내일은 이 흐름만 머릿속에 넣고 수업에 들어가도 충분하다. 😎**
