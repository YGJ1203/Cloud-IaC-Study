# Kubernetes 주간 총정리 --- 09/14 \~ 09/19

> 이번 주 핵심 흐름: **Pod → Controller → Service/Load Balancing →
> Label/Annotation → ConfigMap/Secret**

이번 주는 Kubernetes의 개별 기능을 외우는 단계보다, **리소스들이 서로
어떻게 연결되는지** 이해하는 것이 핵심이다.

------------------------------------------------------------------------

## 1. 전체 구조 한눈에 보기

``` text
사용자
  │
  ▼
Service (고정된 접근점)
  │  selector
  ▼
Pod 여러 개
  ▲
  │ 생성/복구/스케일링
Deployment / ReplicaSet
  │
  ├── ConfigMap : 일반 설정값
  └── Secret    : 민감한 설정값
```

### 꼭 기억할 문장

-   **Pod**: 컨테이너가 실제로 실행되는 최소 배포 단위
-   **ReplicaSet**: 지정한 수의 Pod를 유지
-   **Deployment**: ReplicaSet을 관리하며 배포/업데이트까지 담당
-   **Service**: 변하는 Pod 앞에 고정된 네트워크 접근점을 제공
-   **Label**: Kubernetes 리소스를 분류하는 `key: value`
-   **Selector**: 원하는 Label을 가진 리소스를 선택
-   **ConfigMap**: 일반 설정 데이터를 분리
-   **Secret**: 비밀번호 등 민감 데이터를 분리

# 2. Pod 핵심

Pod 안에는 하나 이상의 컨테이너가 들어간다.

기본 YAML 구조:

``` yaml
apiVersion: v1
kind: Pod
metadata:
  name: myweb6
  namespace: product
spec:
  containers:
    - name: nginx-container
      image: nginx
      ports:
        - containerPort: 80
```

## 환경 변수

``` yaml
env:
  - name: DB
    value: mydb
  - name: MYWEB
    value: /usr/share/nginx/html
```

확인:

``` bash
kubectl get pods
kubectl get pods -n product
kubectl describe pod myweb6 -n product
```

# 3. Resource requests / limits

``` yaml
resources:
  requests:
    cpu: 200m
    memory: 500Mi
  limits:
    cpu: "1"
    memory: 1Gi
```

### 의미

  항목       의미
  ---------- ---------------------------------------
  requests   스케줄링할 때 필요한 최소 자원 기준
  limits     컨테이너가 사용할 수 있는 자원의 상한

`requests`와 `limits`의 **작성 순서는 상관없다.**

``` yaml
resources:
  limits:
    cpu: "1"
  requests:
    cpu: 200m
```

위처럼 작성해도 YAML 구조상 문제없다.

> YAML은 같은 계층 안의 키 순서보다 **들여쓰기와 계층 구조**가 훨씬
> 중요하다.

# 4. Liveness / Readiness Probe

``` yaml
livenessProbe:
  httpGet:
    path: /
    port: 80

readinessProbe:
  httpGet:
    path: /
    port: 80
```

### 차이

``` text
Liveness
"이 컨테이너 살아 있나?"
        ↓
실패 지속 → 컨테이너 재시작

Readiness
"지금 요청 받을 준비됐나?"
        ↓
실패 → Service 트래픽 대상에서 제외
```

면접에서도 매우 자주 헷갈리는 부분이다.

# 5. Static Pod

Static Pod는 일반적으로 API Server를 통해 직접 생성하는 방식과 다르다.

**특정 Node의 kubelet이 manifest 디렉터리의 YAML을 감시하여 직접
관리한다.**

예:

``` text
/etc/kubernetes/manifests/
```

실습에서는 node1에 YAML을 배치하여 생성.

핵심:

``` text
일반 Pod
kubectl → API Server → Scheduler → Node

Static Pod
manifest 파일 → 해당 Node의 kubelet → Pod
```

# 6. Controller

## ReplicationController

실습 조건:

``` text
파일: lab_rc.yml
RC: lab-rc
replicas: 3 → 6
label: app=apache
Pod: apache-pod
Container: apache-web
Image: httpd:2.2
```

개념:

``` text
ReplicationController
       │
       ├── Pod
       ├── Pod
       └── Pod
```

Pod가 삭제되면 원하는 개수를 맞추기 위해 다시 생성한다.

Scale:

``` bash
kubectl scale rc lab-rc --replicas=6
```

------------------------------------------------------------------------

## ReplicaSet

ReplicationController보다 발전된 형태이며 일반적으로 Deployment가
ReplicaSet을 관리한다.

예:

``` yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: lab-rs
spec:
  replicas: 6
  selector:
    matchLabels:
      app: apache
  template:
    metadata:
      labels:
        app: apache
    spec:
      containers:
        - name: apache-web
          image: httpd:2.2
```

### 가장 중요한 부분

``` yaml
selector:
  matchLabels:
    app: apache

template:
  metadata:
    labels:
      app: apache
```

두 Label이 서로 맞아야 한다.

# 7. Deployment ⭐

실습:

``` text
Deployment: httpd-deploy
replicas: 6
label: app=apache
Pod: apache-pod
Container: apache-web
Image: httpd:2.2
```

구조:

``` text
Deployment
    │
    ▼
ReplicaSet
    │
    ├── Pod
    ├── Pod
    ├── Pod
    └── ...
```

즉,

> **Deployment가 ReplicaSet을 관리하고 ReplicaSet이 Pod 개수를
> 유지한다.**

실무에서 애플리케이션 Pod를 직접 여러 개 만드는 대신 Deployment를
사용하는 이유다.

확인:

``` bash
kubectl get deployments
kubectl get rs
kubectl get pods
```

# 8. Label과 Selector ⭐

Label:

``` yaml
metadata:
  labels:
    app: apache
    tier: frontend
```

조회:

``` bash
kubectl get pods --show-labels
```

특정 Label 선택:

``` bash
kubectl get pods -l app=apache
```

### 핵심 관계

``` text
Pod
labels:
  app: apache

        ▲
        │ selector
        │
Service / ReplicaSet
```

Kubernetes에서 **Label + Selector는 리소스를 연결하는 접착제**라고
생각하면 쉽다.

------------------------------------------------------------------------

# 9. Annotation

Label과 비슷하게 metadata에 정보를 기록하지만 목적이 다르다.

``` yaml
metadata:
  annotations:
    description: "Apache Web Server"
```

### Label vs Annotation

  Label                Annotation
  -------------------- ---------------------------------
  리소스 분류          추가 정보 기록
  Selector 사용 가능   Selector 용도가 아님
  app, tier, env 등    설명, 빌드 정보, 관리 데이터 등

# 10. Service

Pod IP는 생성/삭제 과정에서 바뀔 수 있다.

따라서 Service가 **고정된 접근점** 역할을 한다.

``` text
Client
   │
   ▼
Service
   │
   ├── Pod #1
   ├── Pod #2
   └── Pod #3
```

## ClusterIP

실습:

``` text
Service: httpd-svc1
ClusterIP: 10.233.10.10
Port: 80
TargetPort: 80
```

예:

``` yaml
apiVersion: v1
kind: Service
metadata:
  name: httpd-svc1
spec:
  type: ClusterIP
  clusterIP: 10.233.10.10
  selector:
    app: apache
  ports:
    - port: 80
      targetPort: 80
```

### port와 targetPort

``` text
Client
  │
  │ Service port: 80
  ▼
Service
  │
  │ targetPort: 80
  ▼
Pod :80
```

ClusterIP는 기본적으로 **클러스터 내부에서 Service에 접근하기 위한 가상
IP**다.

------------------------------------------------------------------------

# 11. NodePort

Node의 특정 포트를 외부에 노출한다.

``` text
외부 Client
     │
     ▼
NodeIP:30000
     │
     ▼
Service
     │
     ▼
Pod
```

이번 실습에서 HAProxy가 다음과 같은 NodePort를 향하도록 구성했다.

``` text
app1 → 192.168.2.61:30000
app2 → 다른 Node의 :30000
```

# 12. HAProxy Load Balancing

Load Balancer:

``` text
192.168.2.80
```

구조:

``` text
Client
   │
   ▼
HAProxy :80
   │
   ├── node1 192.168.2.61:30000
   └── node? xxx.xxx.xxx.xxx:30000
             │
             ▼
        Kubernetes Service
             │
             ▼
            Pods
```

Round Robin:

``` text
요청 #1 → app1
요청 #2 → app2
요청 #3 → app1
...
```

HAProxy 예시:

``` text
backend app
    balance roundrobin
    server app1 192.168.2.61:30000
    server app2 <NODE-IP>:30000
```

# 13. Headless Service

일반 Service는 ClusterIP를 가진다.

Headless Service는:

``` yaml
clusterIP: None
```

즉 Service 자체의 일반적인 가상 IP를 두지 않고, Pod의 주소를 직접 찾을
수 있도록 사용하는 형태다.

``` text
일반 Service
DNS → ClusterIP → Pod

Headless Service
DNS → Pod IP들
```

StatefulSet 등에서 각 Pod를 직접 식별해야 할 때 중요하다.

# 14. ConfigMap ⭐

애플리케이션 설정값을 Pod YAML 안에 박아 넣지 않고 별도의 리소스로
관리한다.

``` text
ConfigMap
   │
   └── 일반 설정
       DB_HOST
       APP_MODE
       설정 파일 등
```

Pod에서는 환경 변수나 Volume 등의 방식으로 사용할 수 있다.

핵심:

> **ConfigMap = 민감하지 않은 설정값 분리**

# 15. Secret ⭐

이번 실습:

``` text
파일: secret.yml
Secret: test-secret

project.id   = webserver-1234
project.user = webadmin
project.pass = abcd1234
```

`stringData`를 사용하면 사람이 읽을 수 있는 문자열을 그대로 작성할 수
있다.

``` yaml
apiVersion: v1
kind: Secret
metadata:
  name: test-secret
type: Opaque
stringData:
  project.id: webserver-1234
  project.user: webadmin
  project.pass: abcd1234
```

생성:

``` bash
kubectl apply -f secret.yml
```

확인:

``` bash
kubectl describe secret test-secret
```

실습 결과:

``` text
Type: Opaque

Data
====
project.id:   14 bytes
project.pass: 8 bytes
project.user: 8 bytes
```

## `data`를 사용하는 경우

`data` 필드는 값이 Base64로 인코딩되어 있어야 한다.

``` bash
echo -n 'abcd1234' | base64
```

따라서 다음처럼 평문을 `data`에 바로 넣으면 안 된다.

``` yaml
data:
  project.pass: abcd1234   # 잘못된 방식
```

초기 학습에서는 `stringData`를 사용하면 훨씬 이해하기 쉽다.

### Opaque

``` yaml
type: Opaque
```

일반적인 사용자 정의 Secret에 사용하는 대표적인 타입이다.

> 주의: Base64는 **암호화가 아니다.** 인코딩일 뿐이다.

# 16. ConfigMap vs Secret

  구분         ConfigMap         Secret
  ------------ ----------------- -----------------
  목적         일반 설정         민감 데이터
  예           URL, 환경 설정    Password, Token
  Pod에 전달   env / volume 등   env / volume 등
  보안 목적    X                 민감정보 관리용

기억법:

``` text
설정 → ConfigMap
비밀 → Secret
```

# 18. YAML 작성할 때 진짜 중요한 것

키의 작성 순서보다 **계층과 들여쓰기**가 중요하다.

일반적인 가독성 순서:

``` yaml
apiVersion:
kind:
metadata:
spec:
```

Container 내부도 보통:

``` yaml
containers:
  - name:
    image:
    ports:
    env:
    resources:
```

하지만 같은 계층이라면 논리적으로 허용되는 필드의 순서는 대부분 중요하지
않다.

즉:

``` text
"순서 암기"보다
"어떤 항목이 어느 부모 밑에 들어가는가?"
```

를 이해해야 한다.

# 19. 이번 주 Troubleshooting 포인트 ☠️

## ① Node가 NotReady

``` bash
kubectl get nodes
```

예:

``` text
node1   NotReady
node2   NotReady
node3   NotReady
```

우선 Node에서 kubelet 상태를 확인한다.

``` bash
systemctl status kubelet
```

추가 확인:

``` bash
journalctl -u kubelet
```

그리고 Control Plane에서:

``` bash
kubectl describe node node1
```

`NotReady`는 단순히 "Pod 문제"라고 단정하면 안 되고, **kubelet /
container runtime / CNI / 노드 통신 상태** 등을 순차적으로 확인해야
한다.

------------------------------------------------------------------------

## ② Service가 Pod를 못 찾는 경우

가장 먼저:

``` bash
kubectl get pods --show-labels
```

그리고 Service:

``` bash
kubectl describe svc <SERVICE>
```

확인할 것:

``` text
Service selector
      ↕
Pod label
```

둘이 일치하는가?

Kubernetes 초반 장애의 상당수가 Label/Selector 연결을 이해하면 훨씬 쉽게
보인다.

------------------------------------------------------------------------

## ③ YAML 오류

``` bash
kubectl apply -f example.yml
```

오류가 나면 우선 확인:

``` text
1. 들여쓰기
2. apiVersion
3. kind
4. 필드 위치
5. selector ↔ label
6. 오타
```

# 21. 면접/시험 초압축 Q&A

### Q. Pod란?

Kubernetes에서 컨테이너를 실행하는 **최소 배포 단위**.

### Q. ReplicaSet의 역할은?

지정한 개수의 Pod가 계속 실행되도록 유지한다.

### Q. Deployment는 왜 사용하는가?

ReplicaSet과 Pod를 관리하면서 배포, 스케일링, 업데이트 등을 쉽게 하기
위해 사용한다.

### Q. Service가 필요한 이유는?

Pod는 재생성되면서 IP가 변경될 수 있으므로 안정적인 네트워크 접근점을
제공하기 위해 사용한다.

### Q. ClusterIP란?

클러스터 내부에서 Service에 접근하기 위한 기본 Service 타입 및 가상 IP.

### Q. NodePort란?

Node의 포트를 외부에 노출하여 Service에 접근할 수 있게 하는 Service
타입.

### Q. Label이란?

Kubernetes 리소스를 분류하기 위한 `key: value` 메타데이터.

### Q. Selector란?

특정 Label을 가진 리소스를 선택하는 조건.

### Q. ConfigMap과 Secret의 차이는?

ConfigMap은 일반 설정값, Secret은 비밀번호/토큰 등 민감 데이터를
관리한다.

### Q. Liveness와 Readiness의 차이는?

-   Liveness: 컨테이너가 정상적으로 살아 있는지 검사
-   Readiness: 현재 트래픽을 받을 준비가 되었는지 검사

### Q. requests와 limits의 차이는?

-   requests: 스케줄링 시 필요한 자원 기준
-   limits: 컨테이너 자원 사용 상한

# 22. 이번 주 연결 구조 --- 이것만 머리에 남겨도 성공 🔥

``` text
                    Deployment
                         │
                         ▼
                    ReplicaSet
                         │
               ┌─────────┼─────────┐
               ▼         ▼         ▼
             Pod #1    Pod #2    Pod #3
               │         │         │
               └─────────┼─────────┘
                         ▲
                         │ selector
                      Service
                         ▲
                         │
                      Client
```

그리고 Pod에 필요한 설정은:

``` text
            Pod
          ↙     ↘
   ConfigMap    Secret
   일반 설정     민감 정보
```

외부 로드밸런서까지 포함하면:

``` text
Client
  │
  ▼
HAProxy
  │
  ▼
NodePort Service
  │
  ▼
Pods
```

# 23. 이번 주 최종 암기 문장 😏

``` text
Pod는 실행한다.
ReplicaSet은 개수를 맞춘다.
Deployment는 배포를 관리한다.
Service는 Pod를 연결한다.
Label은 리소스를 묶는다.
Selector는 그 묶음을 찾는다.
ConfigMap은 설정을 담는다.
Secret은 비밀을 담는다.
Probe는 Pod의 상태를 확인한다.
requests/limits는 자원을 관리한다.
```

## ⭐ 복습 우선순위

**1순위** `Deployment → ReplicaSet → Pod`

**2순위** `Service → Selector → Label → Pod`

**3순위** `ConfigMap / Secret → Pod`

**4순위** `Liveness / Readiness`, `requests / limits`

이 네 흐름이 연결되면 이번 주 Kubernetes 내용은 단순 암기가 아니라
**구조로 이해하기 시작한 것**이다. 😎🔥
