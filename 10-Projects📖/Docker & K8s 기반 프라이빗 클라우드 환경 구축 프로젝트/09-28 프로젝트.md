# 2026-09-28 Kubernetes Private Cloud Project --- LVM 기반 NFS 스토리지 구축 및 트러블슈팅

## 1. 오늘의 목표

Kubernetes 프라이빗 클라우드 프로젝트에서 사용할 **NFS 공유 스토리지**를
별도 디스크 기반의 LVM으로 구성하고, 기존 Kubernetes PV/PVC 및
Deployment와 연동하여 학과별 웹 서비스를 정상화하였다.

최종 구성 흐름:

``` text
5GB Disk × 2
    ↓
LVM PV (/dev/sdb1, /dev/sdc1)
    ↓
VG (kaist_vg)
    ↓
LV (kaist_lv, 약 10GB)
    ↓
EXT4
    ↓
/www/vol
├── ai
├── sys
├── com
└── ft
    ↓
NFS
    ↓
PV → PVC
    ↓
Deployment / Pod
    ↓
NodePort 30001 ~ 30004
```

------------------------------------------------------------------------

## 2. NFS 서버 구축

NFS 서버에 필요한 패키지를 설치하고 서비스를 활성화하였다.

``` bash
dnf install -y nfs-utils
systemctl enable --now nfs-server
systemctl status nfs-server
```

### 핵심 확인 사항

-   `nfs-utils` 설치
-   `nfs-server` 부팅 시 자동 시작 설정
-   NFS 서비스 활성화 상태 확인

------------------------------------------------------------------------

## 3. NFS 전용 디스크 추가

VMware의 NFS 서버 VM에 **5GB 디스크 2개**를 추가하였다.

``` text
/dev/sdb → 5GB
/dev/sdc → 5GB
```

기존 OS 디스크와 서비스 데이터를 분리하고, 두 디스크를 LVM으로 통합하여
NFS 데이터 전용 저장공간으로 사용한다.

------------------------------------------------------------------------

## 4. LVM 스토리지 구성

각 추가 디스크에 LVM 파티션을 생성하였다.

``` text
/dev/sdb1 → 5GB, Linux LVM
/dev/sdc1 → 5GB, Linux LVM
```

### Physical Volume 생성

``` bash
pvcreate /dev/sdb1 /dev/sdc1
```

### Volume Group 생성

``` bash
vgcreate kaist_vg /dev/sdb1 /dev/sdc1
```

### Logical Volume 생성

``` bash
lvcreate -n kaist_lv -l 100%FREE kaist_vg
```

두 개의 5GB 디스크를 `kaist_vg`로 통합하고, 사용 가능한 전체 공간을
`kaist_lv`에 할당하였다.

### EXT4 파일시스템 생성

``` bash
mkfs -t ext4 /dev/kaist_vg/kaist_lv
```

> `> /dev/null`은 명령 출력 억제 용도일 뿐 필수 설정은 아니다.

### 결과 확인

``` bash
pvs
vgs
lvs
lsblk
```

최종 구조:

``` text
/dev/sdb1 ─┐
           ├── kaist_vg
/dev/sdc1 ─┘      ↓
               kaist_lv (~10GB)
```

------------------------------------------------------------------------

## 5. LVM 볼륨 마운트 및 영구 마운트

생성한 논리 볼륨을 NFS 공유 데이터 경로인 `/www/vol`에 마운트하였다.

``` bash
mkdir -p /www/vol
mount /dev/kaist_vg/kaist_lv /www/vol
```

파일시스템 UUID:

``` text
0ce4eb3a-90e5-4174-a86f-31e5d1fadcfe
```

`/etc/fstab`에 UUID 기반 자동 마운트 설정을 추가하였다.

``` text
UUID=0ce4eb3a-90e5-4174-a86f-31e5d1fadcfe /www/vol ext4 defaults 0 2
```

검증:

``` bash
mount -a
findmnt /www/vol
df -hT /www/vol
lsblk
```

재부팅 후에도 `/www/vol`에 자동 마운트되는 것을 확인하였다.

### 주의점

기존 `/www/vol`에 데이터가 존재하는 상태에서 새 파일시스템을 마운트하면
기존 파일은 삭제되는 것이 아니라 **마운트 아래에 가려진다.**

따라서 기존 데이터를 백업한 후 신규 LVM 파일시스템에 복원하였다.

------------------------------------------------------------------------

## 6. NFS 공유 디렉터리 구성

학과별 웹 데이터를 분리하기 위해 다음 디렉터리를 사용하였다.

``` text
/www/vol/
├── ai
├── sys
├── com
└── ft
```

필요 시:

``` bash
mkdir -p /www/vol/{ai,sys,com,ft}
```

각 디렉터리에는 해당 학과의 웹 콘텐츠(`index.html`)를 배치한다.

### NFS Export

`/etc/exports`에서 각 학과 디렉터리를 Kubernetes 노드가 접근할 수 있도록
공유한다.

설정 적용 및 확인:

``` bash
exportfs -rav
exportfs -v
systemctl status nfs-server
```

------------------------------------------------------------------------

## 7. Kubernetes NFS 연동

NFS 서버:

``` text
192.168.2.80
```

학과별 NFS 경로:

``` text
AI  → /www/vol/ai
SYS → /www/vol/sys
COM → /www/vol/com
FT  → /www/vol/ft
```

PV의 핵심 NFS 설정 예시:

``` yaml
nfs:
  server: 192.168.2.80
  path: /www/vol/ai
```

이번 프로젝트에서는 Deployment가 NFS를 직접 지정하는 대신 **PV/PVC
구조**를 사용하였다.

``` text
NFS Server
    ↓
PersistentVolume
    ↓
PersistentVolumeClaim
    ↓
Deployment
    ↓
Pod
```

NFS 서버의 실제 주소와 공유 경로는 PV에 정의되고, Deployment는 PVC를
참조한다.

> PV/PVC 상세 구성은 별도 담당 파트에서 설명하며, NFS 파트에서는 NFS
> 서버와 공유 경로 제공에 초점을 맞춘다.

------------------------------------------------------------------------

## 8. PV/PVC 상태 확인

최종 확인 결과 각 학과 PVC가 정상적으로 PV와 `Bound` 상태였다.

``` text
kaist-ai  / kaist-ai-pvc  → kaist-ai-pv
kaist-sys / kaist-sys-pvc → kaist-sys-pv
kaist-com / kaist-com-pvc → kaist-com-pv
kaist-ft  / kaist-ft-pvc  → kaist-ft-pv
```

각 PV는 `RWX (ReadWriteMany)`를 사용하여 NFS 공유 스토리지를 여러 Pod가
사용할 수 있도록 구성하였다.

------------------------------------------------------------------------

## 9. 학과별 NodePort

``` text
AI  → 30001
SYS → 30002
COM → 30003
FT  → 30004
```

AI 기준 Service는 `app=kaist-ai` selector를 통해 6개의 Pod Endpoint를
정상적으로 연결하였다.

# 10. 핵심 트러블슈팅 --- Stale file handle

## 증상

LVM 구성 및 `/www/vol` 마운트 이후 NodePort에 접근했을 때:

``` text
500 Internal Server Error
```

가 발생하였다.

Pod 내부 NFS 경로 확인:

``` bash
kubectl exec -n kaist-ai <POD> -- ls -la /usr/share/nginx/html
```

결과:

``` text
ls: cannot access '/usr/share/nginx/html': Stale file handle
```

nginx 로그에서도 동일한 원인이 확인되었다.

``` text
open() "/usr/share/nginx/html/..." failed (116: Stale file handle)
```

## 원인

기존 Pod가 NFS 서버의 **변경 전 파일시스템에 대한 file handle**을
유지하고 있었다.

오늘 `/www/vol`에 신규 LVM 기반 EXT4 파일시스템을 마운트하면서 NFS 서버
측 backing filesystem이 변경되었지만, 기존 Pod/NFS 클라이언트는 이전
file handle을 계속 참조하였다.

``` text
기존 /www/vol
    ↑
기존 NFS file handle
    │
    Pod

↓ 신규 LVM 파일시스템 마운트

새 EXT4 /www/vol
    ↑
    X  ← 기존 file handle 사용 불가
```

이로 인해 `ESTALE (Stale file handle)`이 발생했고 nginx가 웹 파일을 읽지
못하면서 HTTP 500을 반환하였다.

## 해결

NFS Export 상태를 확인한 뒤 Deployment를 Rolling Restart하였다.

``` bash
exportfs -v
```

AI:

``` bash
kubectl rollout restart deployment kaist-ai-deploy -n kaist-ai
kubectl rollout status deployment kaist-ai-deploy -n kaist-ai
```

SYS / COM / FT 역시 각 namespace의 Deployment를 재시작하였다.

재생성된 Pod는 새로운 NFS 파일시스템을 다시 마운트하여 정상적인 file
handle을 획득하였다.

## 해결 확인

새 AI Pod 내부:

``` bash
kubectl exec -n kaist-ai <NEW-POD> -- ls -la /usr/share/nginx/html
```

결과:

``` text
index.html
```

정상 확인.

이후:

``` bash
curl http://192.168.2.61:30001
```

에서 KAIST AI 학부 HTML이 정상 반환되었다.

## 11. Namespace 실수

COM Deployment를 재시작하면서 다음과 같이 잘못된 namespace를 지정하였다.

``` bash
kubectl rollout restart deployment kaist-com-deploy -n kaist-ai
```

결과:

``` text
Error from server (NotFound):
deployments.apps "kaist-com-deploy" not found
```

실제 Deployment 위치:

``` text
kaist-ai  → kaist-ai-deploy
kaist-sys → kaist-sys-deploy
kaist-com → kaist-com-deploy
kaist-ft  → kaist-ft-deploy
```

올바른 명령:

``` bash
kubectl rollout restart deployment kaist-com-deploy -n kaist-com
```

### 교훈

Kubernetes 리소스를 조작할 때는 **리소스 이름뿐 아니라 namespace도
반드시 확인**해야 한다.

잘못된 namespace에서 명령을 실행한 경우 해당 Deployment를 찾지
못했으므로 기존 리소스에는 변경이 발생하지 않았다.

# 14. PPT 구성 흐름

NFS 담당 파트는 다음 순서로 구성한다.

1.  **NFS 서버 구축**
    -   `nfs-utils`
    -   `systemctl enable --now nfs-server`
2.  **NFS 전용 디스크 추가**
    -   VMware 5GB × 2
3.  **LVM 구성**
    -   PV → VG → LV
    -   EXT4
    -   `lsblk`, `pvs`, `vgs`, `lvs`
4.  **LVM 볼륨 마운트**
    -   `/www/vol`
    -   `/etc/fstab`
    -   `df -hT`, `findmnt`
5.  **NFS 공유 디렉터리 구성**
    -   `/www/vol/{ai,sys,com,ft}`
    -   `/etc/exports`
    -   `exportfs -v`
6.  **Kubernetes YAML 연동**
    -   `server: 192.168.2.80`
    -   `path: /www/vol/...`
    -   PV/PVC 상세 설명은 담당 조원 파트로 연결
7.  **최종 검증**
    -   NodePort 30001\~30004 정상 접속
8.  **트러블슈팅**
    -   HTTP 500
    -   `Stale file handle`
    -   Rolling Restart를 통한 정상화

# 15. 핵심 정리

> **NFS 자체에 LVM이 필수적인 것은 아니지만, OS 영역과 서비스 데이터를
> 분리하고 스토리지를 유연하게 관리하기 위해 별도의 5GB 디스크 2개를
> LVM으로 통합하였다.**

> **LVM 기반 약 10GB 논리 볼륨을 EXT4로 구성하여 `/www/vol`에 영구
> 마운트하고, 학과별 디렉터리를 NFS로 공유하였다.**

> **Kubernetes에서는 해당 NFS 공유 경로를 PV/PVC를 통해 Pod의 nginx
> DocumentRoot에 연결하였다.**

> **LVM 마운트 후 기존 NFS file handle이 무효화되어 `Stale file handle`
> 및 HTTP 500이 발생했으며, Deployment Rolling Restart를 통해 NFS를
> 재마운트하여 정상화하였다.**
