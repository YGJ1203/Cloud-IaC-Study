# 2026-09-29 Kubernetes Private Cloud Project 정리

## 1. 오늘의 핵심 목표

기존 NFS 공유 경로와 Kubernetes PV/PVC 구성을 최종 PPT 설계에 맞게
정리하였다.

### 변경 전 / 변경 후

``` text
변경 전                 변경 후
/www/vol/ai     →       /www/vol/web
/www/vol/sys            /www/vol/sys
/www/vol/com            /www/vol/com
/www/vol/ft             /www/vol/ft
```

핵심은 **`/www/vol/ai`만 `/www/vol/web`으로 변경**하고 SYS/COM/FT는
그대로 유지하는 것이다.

기존 Pod가 NFS를 사용 중인 상태에서 공유 경로를 변경하면 오래된 파일
핸들 때문에 문제가 생길 수 있으므로 다음 순서로 진행하였다.

``` text
→ replicas=6 복구

```

### Pod 종료

``` bash
kubectl scale deployment kaist-ai-deploy -n kaist-ai --replicas=0
kubectl get pods -n kaist-ai -w
```

6개 Pod가 `Terminating` 상태를 거쳐 완전히 종료된 뒤 다음 작업으로
진행하였다.

## 3. NFS 공유 경로 변경

NFS 서버 `192.168.2.80`에서:

``` bash
mv /www/vol/ai /www/vol/web
```

확인:

``` bash
ls -la /www/vol
ls -la /www/vol/web
```

최종 구조:

``` text
/www/vol/
├── web
├── sys
├── com
└── ft
```

WEB 디렉터리 내부의 기존 웹 콘텐츠도 정상적으로 유지되는지 확인하였다.

------------------------------------------------------------------------

## 4. /etc/exports 수정

기존:

``` text
/www/vol/ai
```

변경:

``` text
/www/vol/web
```

최종 공유 구조:

``` text
/www/vol/web  192.168.2.0/24(rw)
/www/vol/sys  192.168.2.0/24(rw)
/www/vol/com  192.168.2.0/24(rw)
/www/vol/ft   192.168.2.0/24(rw)
```

적용 및 확인:

``` bash
exportfs -rav
exportfs -v
```

`/etc/exports`는 NFS 서버가 어떤 경로를 어떤 클라이언트 네트워크에
공유할 것인지 정의한다.

------------------------------------------------------------------------

## 5. PV/PVC 재구성

기존 AI PV/PVC는 이미 `Bound` 상태였기 때문에 기존 객체의 NFS 경로를
억지로 변경하지 않고 정리 후 WEB용으로 다시 구성하였다.

``` bash
kubectl delete pvc kaist-ai-pvc -n kaist-ai
kubectl delete pv kaist-ai-pv
```

기존 PV의 Reclaim Policy는 `Retain`이므로 Kubernetes 객체 삭제 자체가
NFS 서버의 실제 웹 파일을 자동 삭제하는 것은 아니다.

### WEB PV 핵심

``` yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: kaist-web-pv
spec:
  capacity:
    storage: 2Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteMany
  persistentVolumeReclaimPolicy: Retain
  storageClassName: manual
  nfs:
    server: 192.168.2.80
    path: /www/vol/web
```

최종 관계:

``` text
kaist-web-pv
      ↕ Bound
kaist-ai/kaist-web-pvc
```

확인:

``` bash
kubectl get pv
kubectl get pvc -n kaist-ai
```

> 참고: 정적 NFS PV의 `capacity: 2Gi`는 NFS 디렉터리의 실제 파일시스템
> 사용량을 자동으로 2GiB로 제한하는 quota 설정은 아니다.

## 6. Deployment 수정

Deployment 자체는 기존 AI 서비스 구성을 유지하였다.

``` text
Deployment : kaist-ai-deploy
Namespace  : kaist-ai
Label      : app=kaist-ai
NodePort   : 30001
```

변경 핵심은 PVC 참조 한 곳이다.

``` yaml
volumeMounts:
  - name: kaist-ai-vol
    mountPath: /usr/share/nginx/html

volumes:
  - name: kaist-ai-vol
    persistentVolumeClaim:
      claimName: kaist-web-pvc
```

`kaist-ai-vol`은 Pod 내부 볼륨 식별자이므로 이름을 변경할 필요가 없다.
`volumeMounts[].name`과 `volumes[].name`이 일치하면 된다.

실제 PVC를 결정하는 부분은:

``` yaml
claimName: kaist-web-pvc
```

이다.

## 7. Pod 복구 및 최종 검증

PV/PVC가 `Bound` 상태인 것을 확인한 뒤 Deployment를 다시 6 replicas로
복구하였다.

``` bash
kubectl scale deployment kaist-ai-deploy -n kaist-ai --replicas=6
kubectl rollout status deployment kaist-ai-deploy -n kaist-ai
kubectl get pods -n kaist-ai -o wide
```

Pod 내부 NFS Mount 확인:

``` bash
kubectl exec -n kaist-ai <POD_NAME> -- ls -la /usr/share/nginx/html
```

최종 연결 구조:

``` text
NFS Server
192.168.2.80:/www/vol/web
        ↓
kaist-web-pv
        ↓
kaist-web-pvc
        ↓
kaist-ai-deploy
        ↓
Pod
        ↓
/usr/share/nginx/html
```

### NodePort 검증 결과

``` text
30001 → WEB(AI)  정상 ✅
30002 → SYS      정상 ✅

```

`curl` 테스트 결과 네 서비스 모두 정상적으로 웹 콘텐츠를 반환하였다.

# 8. PPT 역할 분리

팀원의 PPT 내용을 확인한 결과, 발표 역할을 다음처럼 분리하는 것이 가장
자연스럽다.

## 담당 파트 --- Linux / LVM / NFS

``` text
NFS 서버 구축
→ VMware 5GB × 2 디스크 추가
→ LVM 구성 (PV → VG → LV)
→ EXT4
→ /www/vol 마운트
→ 서비스별 공유 디렉터리
→ /etc/exports
→ exportfs 적용
```

## 다음 팀원 파트 --- Kubernetes

``` text
Namespace
→ PV
→ PVC
→ Deployment / Pod
```

따라서 담당 PPT에서는 **PV/PVC YAML을 별도 슬라이드로 중복 설명하지 않는
방향**으로 정리하였다.

팀원의 `PV & PVC` 슬라이드에 이미 다음 설정이 포함되어 있기 때문이다.

``` yaml
nfs:
  server: 192.168.2.80
  path: /www/vol/web
```

즉 발표 흐름은:

``` text
NFS 서버가 /www/vol/web 제공
             ↓
다음 팀원 슬라이드에서 PV/PVC가 해당 경로 사용
```

으로 연결된다.

# 9. NFS 파트 마지막 PPT 슬라이드

추천 소제목:

> **NFS 공유 디렉터리 Export 설정**

핵심 명령:

``` bash
vi /etc/exports
exportfs -rav
exportfs -v
```

추천 설명 문구:

> `/etc/exports`에 서비스별 공유 경로와 접근 허용 네트워크를 설정하고,
> `exportfs`를 통해 NFS 공유 정책을 적용하였다.

### 다음 팀원 파트로 연결하는 발표 멘트

> 이렇게 NFS 서버에 서비스별 공유 디렉터리를 구성하고 Export 설정을
> 완료했습니다. 이렇게 제공된 NFS 공유 경로는 다음 단계에서 Kubernetes의
> PV/PVC와 연동하여 각 Pod에서 사용할 수 있도록 구성했습니다.

이후 팀원의 `PV & PVC` 슬라이드에서 `/www/vol/web`을 사용하는 PV YAML이
등장하므로 자연스럽게 이어진다.

# 10. Troubleshooting 핵심

## Pod Terminating

NFS 볼륨을 사용하는 Pod는 종료 과정에서 볼륨 unmount 처리 때문에
`Terminating` 상태가 잠시 지속될 수 있다.

``` bash
kubectl get pods -n kaist-ai -w
```

강제 삭제부터 하기보다 정상 종료 여부를 먼저 확인한다.

## Stale file handle 방지

이전 작업에서 NFS backing filesystem 변경 후 기존 Pod가 오래된 파일
핸들을 유지하여 `Stale file handle`이 발생한 경험이 있었다.

이번에는:

``` text
Pod 종료
→ NFS 경로 변경
→ Export 적용
→ PV/PVC 재구성
→ 새 Pod 생성
```

순서를 지켜 기존 NFS 파일 핸들을 사용하는 상황을 피하였다.
