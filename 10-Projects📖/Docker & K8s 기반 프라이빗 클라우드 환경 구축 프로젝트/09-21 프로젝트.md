기존 Linux Web Server 프로젝트에서 제작했던 **KAIST AI 대학 및 3개 학과

``` text
Container Image / 외부 Storage 준비
              ↓
        Kubernetes 담당
              ↓
Namespace → Deployment → Pod → Service
              ↓
PV/PVC → 외부 접근 → Ingress
              ↓
Self-Healing / Scaling / 최종 검증
```

## 2. Namespace 분리

서비스를 논리적으로 분리하기 위해 4개의 Namespace를 생성했다.

  Namespace     역할
  ------------- -----------------------
  `kaist-ai`    AI 대학 메인 홈페이지
  `kaist-com`   AI 컴퓨팅학과
  `kaist-sys`   AI 시스템학과
  `kaist-ft`    AI 미래학과

확인:

``` bash
kubectl get ns
kubectl get namespaces --show-labels
```

### 트러블슈팅

처음 Namespace YAML에서 다음 오타가 발생했다.

``` yaml
apiVersion: vi   # X
apiVersion: v1   # O
```

오류 예시:

``` text
no matches for kind "Namespace" in version "vi"
```

**기억:** `Namespace`, `Pod`, `Service`, `ConfigMap`, `Secret`은 core
API이므로 `apiVersion: v1`을 사용한다. `Deployment`, `ReplicaSet`,
`StatefulSet`, `DaemonSet` 등은 일반적으로 `apps/v1`을 사용한다.

## 3. Docker Image 복습

Kubernetes 전담이지만 Container Image가 어떻게 만들어져 Kubernetes로
전달되는지 이해하기 위해 Docker Image 제작 과정을 복습했다.

### 기본 구조

``` text
kaist-ai/
├── Dockerfile
└── html/
    └── index.html
```

### Dockerfile

``` dockerfile
FROM nginx:latest
COPY html/ /usr/share/nginx/html/
EXPOSE 80
```

### Image Build

``` bash
docker build -t kaist-ai:v1 .
```

마지막 `.`은 **현재 디렉터리를 Build Context로 사용한다**는 의미다.

#### 트러블슈팅 --- Build Context 누락

``` bash
docker build -t kaist-ai:v1
```

실행 시:

``` text
docker buildx build requires 1 argument
```

해결:

``` bash
docker build -t kaist-ai:v1 .
```

### Image 이름 오타

``` bash
docker build -t kasit-ft:v1 .   # 오타
```

삭제 후 재생성:

``` bash
docker rmi kasit-ft:v1
docker build -t kaist-ft:v1 .
```

또는 tag를 수정할 수도 있다.

``` bash
docker tag kasit-ft:v1 kaist-ft:v1
docker rmi kasit-ft:v1
```

## 4. 완성한 4개 Docker Image

``` text
kaist-ai:v1   → AI 대학 메인
kaist-com:v1  → AI 컴퓨팅학과
kaist-sys:v1  → AI 시스템학과
kaist-ft:v1   → AI 미래학과
```

컨테이너 테스트 예시:

``` bash
docker run -d --name kaist-ai-test -p 8080:80 kaist-ai:v1
curl localhost:8080
```

4개를 동시에 테스트한다면 예시는 다음과 같다.

``` text
Host :8080 → kaist-ai  :80
Host :8081 → kaist-com :80
Host :8082 → kaist-sys :80
Host :8083 → kaist-ft  :80
```

### 핵심 개념

``` text
HTML
 ↓
Dockerfile
 ↓
docker build
 ↓
Docker Image
 ↓
docker run
 ↓
Container
 ↓
nginx :80
```

Kubernetes 담당자는 Image 제작 자체보다 **준비된 Image를 Deployment에서
사용하는 과정**이 핵심이다.

## 5. Docker와 Kubernetes의 역할 경계

### Docker 영역

``` text
HTML
 ↓
Dockerfile
 ↓
Image Build
 ↓
Registry Push
```

### Kubernetes 영역

``` text
Registry Image
 ↓
Deployment
 ↓
Pod
 ↓
Service
 ↓
Ingress / Storage / Scaling
```

실제 협업에서는 Docker 담당자가 Registry에 Image를 Push하고 Kubernetes
담당자는 Image 주소를 전달받아 Deployment YAML에서 사용한다.

> **Docker:** 컨테이너 실행 환경을 Image로 만든다.\
> **Kubernetes:** 원하는 컨테이너 상태를 선언하면 그 상태를 지속적으로
> 유지한다.

## 6. Kubernetes 프로젝트 정석 진행 순서

``` text
1. Kubernetes Cluster 구성
        ↓
2. Namespace 설계/생성
        ↓
3. Container Image + Registry 준비
        ↓
4. Deployment / Pod 구성
        ↓
5. ClusterIP Service 구성
        ↓
6. NFS + PV + PVC 구성
        ↓
7. PVC를 Pod에 Mount
        ↓
8. 외부 접근(NodePort / LoadBalancer)
        ↓
9. Ingress Controller + Ingress
        ↓
10. 4개 Namespace에 서비스 확장
        ↓
11. Self-Healing / Scale / Probe 검증
        ↓
12. 최종 테스트 및 Troubleshooting
```

> NFS/PV/PVC는 정적 HTML 서비스 자체에 반드시 필요한 것은 아니다.
> 프로젝트에서 **Persistent Storage**를 구현하고 검증하기 위한 별도
> 기능으로 설계하는 것이 자연스럽다.

## 7. 다음 단계 --- `kaist-ai` Deployment

처음부터 4개를 동시에 구성하지 않고 `kaist-ai` 하나를 먼저 완주한다.

``` text
Namespace: kaist-ai
       ↓
Deployment
       ↓
Pod × 2
       ↓
ClusterIP Service
       ↓
Endpoint 확인
       ↓
Self-Healing
       ↓
Scaling
```

Deployment 기본 구조:

``` yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kaist-ai-deploy
  namespace: kaist-ai
spec:
  replicas: 2
  selector:
    matchLabels:
      app: kaist-ai
  template:
    metadata:
      labels:
        app: kaist-ai
    spec:
      containers:
        - name: kaist-ai-web
          image: <REGISTRY>/kaist-ai:v1
          ports:
            - containerPort: 80
```

### 반드시 기억할 부분

``` yaml
selector:
  matchLabels:
    app: kaist-ai
```

과

``` yaml
template:
  metadata:
    labels:
      app: kaist-ai
```

는 서로 일치해야 한다.

## 8. Service 기본 구조

``` yaml
apiVersion: v1
kind: Service
metadata:
  name: kaist-ai-svc
  namespace: kaist-ai
spec:
  type: ClusterIP
  selector:
    app: kaist-ai
  ports:
    - port: 80
      targetPort: 80
```

Service는 Deployment 이름이 아니라 **Pod의 Label을 selector로
선택한다.**

확인 명령어:

``` bash
kubectl get svc -n kaist-ai
kubectl get endpoints -n kaist-ai
kubectl get endpointslices -n kaist-ai
```

## 9. Kubernetes 검증 시나리오

### Self-Healing

``` bash
kubectl delete pod <POD_NAME> -n kaist-ai
kubectl get pods -n kaist-ai -w
```

Deployment의 원하는 replica 수보다 Pod가 부족해지면 새로운 Pod가
생성되는지 확인한다.

### Scaling

``` bash
kubectl scale deployment kaist-ai-deploy --replicas=4 -n kaist-ai
kubectl get pods -n kaist-ai
```

### Service 연결

``` bash
kubectl get svc -n kaist-ai
kubectl get endpoints -n kaist-ai
```

Service selector와 Pod label이 정상적으로 연결되어 있는지 확인한다.

## 10. Image Registry 주의사항

master에서 만든 로컬 Image는 worker node에 자동으로 전달되지 않는다.

``` text
master
└── kaist-ai:v1 존재

node1 / node2 / node3
└── kaist-ai:v1 없음
```

Pod가 Image가 없는 Worker Node에 배치되면 다음과 같은 문제가 발생할 수
있다.

``` text
ErrImagePull
ImagePullBackOff
```

정석 구조:

``` text
Docker Build
    ↓
Registry Push
    ↓
Worker Node Pull
    ↓
Pod Running
```

따라서 실제 Deployment를 시작하기 전에 팀에서 사용할 **Registry와 Image
주소를 확정**해야 한다.

## 11. 오늘의 핵심 암기

``` text
Namespace = 논리적 격리
Deployment = Pod의 원하는 상태/복제본 관리
Pod = Container 실행 단위
Service = 변하는 Pod 앞의 안정적인 접근 지점
Label/Selector = Service와 Pod를 연결하는 핵심
PV/PVC = Pod와 독립적인 영속 Storage
Ingress = HTTP/HTTPS Routing
Registry = Kubernetes Node가 Image를 가져오는 저장소
```

### 한 줄 요약

> **Image를 준비하고 → Deployment가 Pod를 유지하며 → Service가 Pod를
> 연결하고 → Storage/Ingress를 추가하여 실제 서비스 구조로 확장한다.**
