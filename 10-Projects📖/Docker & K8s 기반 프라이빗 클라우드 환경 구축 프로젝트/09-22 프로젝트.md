# 2026-09-22 KAIST Kubernetes 프로젝트 정리

## 1. 오늘의 목표

KAIST 정적 웹 서비스를 Kubernetes에 배포하고, 외부 사용자가 다음 경로로
접근할 수 있도록 기본 인프라 흐름을 구성했다.

``` text
Client
  ↓
HAProxy Load Balancer
  ↓
Ingress Controller
  ↓
Ingress
  ↓
ClusterIP Service
  ↓
Deployment / ReplicaSet
  ↓
Pods
```

------------------------------------------------------------------------

## 2. 스토리지 설계 판단 --- NFS / PV / PVC 생략

현재 KAIST 웹 서비스는 정적 HTML/CSS를 Nginx 컨테이너 이미지 내부에
포함한다.

따라서 Pod가 재생성되어도 동일한 이미지에서 웹 파일이 다시 제공되므로,
별도의 영구 데이터 저장소가 필요하지 않다.

``` text
Pod 삭제
  ↓
Deployment / ReplicaSet가 새 Pod 생성
  ↓
동일한 Custom Image 실행
  ↓
정적 웹 페이지 다시 제공
```

### PV/PVC가 필요한 대표 상황

-   사용자 업로드 파일
-   데이터베이스 데이터
-   Pod 재생성 이후에도 보존해야 하는 파일
-   여러 Pod가 공유해야 하는 영구 데이터

> 현재 프로젝트에서는 Persistent Data가 없으므로 NFS / PV / PVC를 메인
> 아키텍처에서 제외했다.

## 3. Deployment 구성

Namespace:

``` text
kaist
```

AI Deployment 기본 구조:

``` yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: kaist-ai-deploy
  namespace: kaist
spec:
  replicas: 2
  selector:
    matchLabels:
      app: kaist-ai
  template:
    metadata:
      labels:
        app: kaist-ai
    spec:
      containers:
        - name: kaist-web-server
          image: nginx
          ports:
            - containerPort: 80
```

### 핵심

-   `replicas: 2` : Pod 2개 유지
-   `selector.matchLabels`와 `template.metadata.labels`는 서로 일치해야
    함
-   Deployment가 ReplicaSet을 관리하고 ReplicaSet이 원하는 Pod 개수를
    유지함

## 4. Self-Healing 확인

기존 Pod 하나를 직접 삭제했다.

``` bash
kubectl delete pod -n kaist <POD_NAME>
```

삭제 전 Pod IP 예:

``` text
10.233.102.140
```

삭제 후 ReplicaSet이 새 Pod를 자동 생성했고 새 IP가 할당됐다.

``` text
10.233.102.141
```

즉:

``` text
Desired Replicas = 2

Pod 하나 삭제
    ↓
현재 Replicas = 1
    ↓
ReplicaSet 감지
    ↓
새 Pod 자동 생성
    ↓
Replicas = 2 복구
```

### 핵심

Pod 자체의 IP는 변경될 수 있으므로 클라이언트가 Pod IP에 직접 의존하면
안 된다.

## 5. ClusterIP Service 구성

``` yaml
apiVersion: v1
kind: Service
metadata:
  name: kaist-service
  namespace: kaist
spec:
  type: ClusterIP
  selector:
    app: kaist-ai
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80
```

생성:

``` bash
kubectl apply -f kaist-service.yml
```

확인:

``` bash
kubectl get service -n kaist
kubectl get ep -n kaist kaist-service
```

확인된 Service:

``` text
kaist-service
ClusterIP: 10.233.11.94
Port: 80/TCP
```

Endpoint:

``` text
10.233.102.140:80
10.233.71.27:80
```

Self-Healing 이후에는 새 Pod IP로 Endpoint가 자동 갱신됐다.

### Service 핵심

``` text
Service
  ↓ selector: app=kaist-ai
Pod Label
```

Service는 Deployment 이름이 아니라 **Pod Label**을 기준으로 연결한다.

## 6. NodePort 외부 접근 테스트

외부 접근 원리를 확인하기 위해 NodePort Service를 추가했다.

``` yaml
apiVersion: v1
kind: Service
metadata:
  name: kaist-nodeport
  namespace: kaist
spec:
  type: NodePort
  selector:
    app: kaist-ai
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80
      nodePort: 30080
```

접근:

``` text
http://192.168.2.60:30080
```

브라우저에서 `Welcome to nginx!` 출력 확인.

### 포트 흐름

``` text
Node :30080
   ↓
Service :80
   ↓
Pod / Container :80
```

NodePort는 정상 동작 확인용으로 사용했으며 최종 구조에서는 Ingress
앞단의 NodePort를 사용한다.

## 8. HAProxy Load Balancer 구성

Load Balancer:

``` text
192.168.2.80
```

기존 HAProxy는 Kubernetes Node의 `31000` 포트를 바라보고 있었다.

Ingress Controller의 HTTP NodePort가 `31512`이므로 Backend를 다음과 같이
변경했다.

``` text
frontend main
    bind *:80
    default_backend app

backend app
    balance roundrobin
    server app1 192.168.2.61:31512 check
    server app2 192.168.2.62:31512 check
    server app3 192.168.2.63:31512 check
```

### 역할

``` text
HAProxy
  └─ 어느 Kubernetes Node로 보낼지 분산

Ingress
  └─ 어느 Kubernetes Service로 보낼지 HTTP Routing
```

설정 검사:

``` bash
haproxy -c -f /etc/haproxy/haproxy.cfg
```

결과:

``` text
Configuration file is valid
```

재시작:

``` bash
systemctl restart haproxy
systemctl status haproxy
```

정상 상태:

``` text
Active: active (running)
Status: "Ready."
```

### 기존 static Backend 문제

기존 설정에는 다음 Backend가 존재했다.

``` text
backend static
    server static 127.0.0.1:4331 check
```

해당 포트에 서비스가 없어:

``` text
Server static/static is DOWN
backend 'static' has no server available
```

경고가 발생했다.

현재 프로젝트에서는 필요하지 않아 기존 static ACL 및 Backend를 제거했다.

### pidfile 경고

로그에서:

``` text
'pidfile' already specified. Continuing.
```

을 확인했다.

HAProxy 설정 파일의 `pidfile`과 systemd 실행 옵션의 PID 파일 지정이
중복되어 발생한 경고이며 서비스 자체는 정상 동작했다.

## 9. Ingress 생성

``` yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: kaist-ingress
  namespace: kaist
spec:
  ingressClassName: nginx
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: kaist-service
                port:
                  number: 80
```

적용:

``` bash
kubectl apply -f kaist-ingress.yml
```

확인:

``` bash

10.233.71.27:80
```

즉:

``` text
Ingress
  ↓
ClusterIP Service
  ↓
Pod Endpoint 2개
```

연결 성공.

## 11. Custom KAIST 이미지 준비

Master에 생성한 이미지:

``` text
kaist-ai:v1
kaist-com:v1
kaist-ft:v1
kaist-sys:v1
```

확인:

``` bash
docker images | grep kaist
```

Kubernetes Pod가 Worker에 스케줄링되므로 이미지들을 node1\~node3에도
전달했다.

Master:

``` bash
docker save \
  kaist-ai:v1 \
  kaist-com:v1 \
  kaist-ft:v1 \
  kaist-sys:v1 \
  -o /root/kaist-images.tar
```

전송:

``` bash
scp /root/kaist-images.tar root@192.168.2.61:/root/
scp /root/kaist-images.tar root@192.168.2.62:/root/
scp /root/kaist-images.tar root@192.168.2.63:/root/
```

각 Worker:

``` bash
docker load -i /root/kaist-images.tar
docker images | grep kaist
```

## 12. nginx → KAIST AI Custom Image RollingUpdate

기존:

``` yaml
image: nginx
```

변경:

``` yaml
image: kaist-ai:v1
imagePullPolicy: IfNotPresent
```

적용:

``` bash
kubectl apply -f kaist-ai-deploy.yml
```

확인:

``` bash
kubectl get pods -n kaist -w
kubectl rollout status deployment/kaist-ai-deploy -n kaist
```

Deployment의 Pod Template이 변경되면서 기존 nginx Pod가 새로운
`kaist-ai:v1` Pod로 RollingUpdate 됐다.

최종적으로:

``` text
http://192.168.2.80
```

접속 시 기본 `Welcome to nginx!`가 아닌 **직접 제작한 KAIST AI 홈페이지
출력 성공**.

## 13. imagePullPolicy

``` yaml
image: kaist-ai:v1
imagePullPolicy: IfNotPresent
```

### IfNotPresent

``` text
Node에 이미지 존재?
   ├─ YES → 로컬 이미지 사용
   └─ NO  → Registry에서 Pull 시도
```

현재처럼 Worker에 직접 `docker load`한 환경에 적합하다.

### 주요 정책

  Policy           의미
  ---------------- -----------------------------------------------
  `Always`         이미지 Registry를 확인하여 Pull
  `IfNotPresent`   로컬에 없을 때만 Pull
  `Never`          Registry에서 Pull하지 않고 로컬 이미지만 사용

`v1`처럼 `latest`가 아닌 태그를 사용하면 기본적으로 `IfNotPresent`가
적용되는 경우가 일반적이지만, 프로젝트 YAML에서는 명시해두면 의도를
이해하기 쉽다.

### 이미지 버전 관리

동일한 `v1` 태그를 계속 재사용하기보다:

``` text
kaist-ai:v1
kaist-ai:v2
kaist-ai:v3
```

처럼 버전을 변경하는 것이 좋다.

Deployment의 이미지 태그를 변경하면 새로운 Pod Template이 생성되고
RollingUpdate가 수행된다.

## 16. 오늘의 핵심 개념

``` text
Deployment
   ↓
ReplicaSet
   ↓
Pod
```

``` text
Service
   ↓ selector
Pod Label
```

``` text
HAProxy
   ↓
Ingress Controller
   ↓
Ingress Rule
   ↓
Service
   ↓
Pod
```

### 기억할 것

1.  Pod IP는 영구적이지 않다.
2.  Service는 Pod Label을 기준으로 Pod를 찾는다.
3.  ClusterIP는 클러스터 내부의 안정적인 접점이다.
4.  NodePort는 Node의 포트를 통해 외부 접근을 제공한다.
5.  Ingress는 HTTP 요청을 Service로 라우팅한다.
6.  HAProxy는 여러 Kubernetes Node의 Ingress NodePort로 트래픽을
    분산한다.
7.  정적 웹 파일을 이미지에 포함한 현재 프로젝트에는 PV/PVC가 필수가
    아니다.
8.  Worker가 로컬 Custom Image를 사용하려면 해당 Worker에도 이미지가
    존재해야 한다.
9.  `IfNotPresent`는 로컬 이미지가 있으면 이를 우선 사용한다.
10. Deployment 이미지 변경은 RollingUpdate로 이어진다.
