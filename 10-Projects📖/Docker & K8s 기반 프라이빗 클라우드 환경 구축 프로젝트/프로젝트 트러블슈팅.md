# 🛠 Docker & Kubernetes 프로젝트 트러블슈팅 핵심 정리

> **Project:** Docker & Kubernetes 기반 프라이빗 클라우드 환경 구축  
> **핵심 범위:** Pod → Deployment → Service → NodePort → Ingress → HAProxy  
> **목표:** 장애 발생 시 무작정 설정을 수정하지 않고 계층별로 원인을 추적한다.

---

# 1. 가장 중요한 트러블슈팅 원칙

Kubernetes에서 웹 접속이 안 된다고 바로 YAML부터 수정하지 않는다.

먼저 **어느 구간까지 정상인지** 확인한다.

```text
Client
  ↓
HAProxy / VIP
  ↓
NodePort / Ingress
  ↓
Service
  ↓
Endpoint
  ↓
Pod
  ↓
Container
```

## 핵심 사고방식

```text
"안 된다"
   ↓
어디까지 되는가?
   ↓
문제가 발생하는 계층은 어디인가?
   ↓
해당 계층의 설정과 로그 확인
   ↓
수정
   ↓
다시 검증
```

# 2. 가장 먼저 확인할 기본 명령어

## Pod

```bash
kubectl get pods -n kaist -o wide
```

확인할 것:

- STATUS가 `Running`인가?
- READY가 `1/1`인가?
- Pod IP가 존재하는가?
- 어느 Node에서 실행되고 있는가?

상세 확인:

```bash
kubectl describe pod <POD_NAME> -n kaist
```

로그 확인:

```bash
kubectl logs <POD_NAME> -n kaist
```

# 3. Pod가 Running이 아닐 때

대표적인 상태:

```text
Pending
ContainerCreating
ImagePullBackOff
ErrImagePull
CrashLoopBackOff
```

## ImagePullBackOff

### 증상

```text
STATUS
ImagePullBackOff
```

### 확인

```bash
kubectl describe pod <POD_NAME> -n kaist
```

특히 마지막의 `Events` 확인.

### 주요 원인

- 이미지 이름 오타
- 이미지 태그 오류
- Worker Node에 이미지가 없음
- Private Registry 인증 문제
- `imagePullPolicy` 설정 문제

### 프로젝트에서 특히 확인할 부분

직접 만든 이미지라면:

```bash
docker images | grep kaist
```

각 Node에서 이미지 존재 여부를 확인한다.

# 5. Selector와 Label 불일치

Kubernetes에서 굉장히 중요한 장애 원인이다.

Deployment:

```yaml
selector:
  matchLabels:
    app: kaist-ai
```

Pod Template:

```yaml
metadata:
  labels:
    app: kaist-ai
```

Service:

```yaml
selector:
  app: kaist-ai
```

세 부분이 서로 일치해야 한다.

## 확인

```bash
kubectl get pods -n kaist --show-labels
```

Service 확인:

```bash
kubectl describe svc kaist-service -n kaist
```

### 핵심

```text
Service Selector
       ↓
Pod Label
       ↓
일치해야 Endpoint 생성
```

# 6. Service는 있는데 접속이 안 될 때

확인:

```bash
kubectl get svc -n kaist
```

그 다음 바로 확인할 것:

```bash
kubectl get endpoints -n kaist
```

프로젝트 정상 예시:

```text
kaist-service
10.233.x.x:80
10.233.x.x:80
```

## Endpoint가 `<none>`이라면?

```text
Service
   ↓
selector
   X
Pod label
```

즉, Service가 연결할 Pod를 찾지 못했을 가능성이 높다.

확인:

```bash
kubectl get pods -n kaist --show-labels
kubectl describe svc kaist-service -n kaist
```

# 7. Pod 삭제 후 IP가 바뀌었다

예:

```bash
kubectl delete pod <POD_NAME> -n kaist
```

이후:

```bash
kubectl get pods -n kaist -o wide
```

새로운 Pod가 생성되면서 Pod IP가 변경될 수 있다.

이것은 **정상 동작**이다.

Deployment가 원하는 Replica 수를 유지하기 때문이다.

```text
Pod 삭제
   ↓
Deployment 감지
   ↓
ReplicaSet이 새로운 Pod 생성
   ↓
새로운 Pod IP 할당
   ↓
Service Endpoint 갱신
```

따라서 Pod IP를 직접 서비스 주소로 사용하면 안 된다.

# 8. NodePort 접속 문제

Service 확인:

```bash
kubectl get svc -n kaist
```

예:

```text
TYPE       NodePort
PORT(S)    80:30080/TCP
```

접속 테스트:

```bash
curl http://192.168.2.60:30080
```

또는 Worker Node:

```bash
curl http://192.168.2.61:30080
```

## 확인 포인트

```text
Node IP
   ↓
NodePort
   ↓
Service
   ↓
Endpoint
   ↓
Pod
```

NodePort 자체가 열려 있어도 Service Endpoint가 없다면 정상적인 웹 서비스로 전달되지 않는다.

# 9. Ingress 접속 문제

Ingress 확인:

```bash
kubectl get ingress -n kaist
```

상세 확인:

```bash
kubectl describe ingress -n kaist
```

IngressClass 확인:

```bash
kubectl get ingressclass
```

Ingress Controller 확인:

```bash
kubectl get pods -n ingress-nginx
```

Service 확인:

```bash
kubectl get svc -n ingress-nginx
```

프로젝트에서 Ingress-NGINX Controller의 NodePort를 직접 테스트한 예:

```bash
curl http://192.168.2.61:31512
```

`200 OK`가 나온다면 최소한 다음 경로는 정상이라고 판단할 수 있다.

```text
NodePort
   ↓
Ingress Controller
   ↓
Ingress Rule
   ↓
Service
```

# 10. HAProxy에서 Connection refused

프로젝트에서 실제 확인했던 대표적인 문제.

## 증상

HAProxy 로그에서 Backend 연결 실패:

```text
Connection refused
```

## 확인

```bash
systemctl status haproxy
```

로그:

```bash
journalctl -u haproxy
```

설정 확인:

```bash
vi /etc/haproxy/haproxy.cfg
```

## 핵심

HAProxy Backend가 실제로 서비스가 열려 있는 주소와 포트를 바라보는지 확인한다.

예를 들어:

```text
192.168.2.61:80
```

에서 서비스가 열려 있지 않은데 HAProxy가 이곳으로 연결하려 하면:

```text
Connection refused
```

가 발생할 수 있다.

반면 실제 Ingress NodePort가:

```text
192.168.2.61:31512
```

라면 HAProxy Backend 역시 실제 서비스 경로에 맞게 설정해야 한다.

# 11. HAProxy 수정 후 검증

설정 파일을 수정했다고 바로 끝이 아니다.

문법 검사:

```bash
haproxy -c -f /etc/haproxy/haproxy.cfg
```

재시작:

```bash
systemctl restart haproxy
```

상태 확인:

```bash
systemctl status haproxy
```

로그 확인:

```bash
journalctl -u haproxy
```

최종 접근:

```bash
curl http://192.168.2.80
```

프로젝트에서는 HAProxy VIP를 통한 `200 OK`까지 확인하였다.

# 13. 포트 매핑 누락

컨테이너는 정상인데 Host에서 접속이 안 되는 경우.

예:

```bash
docker run -d --name test-nginx nginx
```

확인:

```bash
docker ps
```

```text
PORTS
80/tcp
```

이것은 컨테이너 내부에서 80번 포트를 사용한다는 의미이지 Host의 80번 포트와 연결됐다는 의미가 아니다.

외부 접근이 필요하면:

```bash
docker run -d \
  --name test-nginx \
  -p 8080:80 \
  nginx
```

확인:

```bash
curl http://localhost:8080
```

# 14. NFS / PV / PVC는 무조건 필요한가?

아니다.

이번 프로젝트에서는 NFS/PV/PVC 사용을 검토했지만 최종적으로 현재 범위에서는 생략할 수 있다고 판단했다.

이유:

```text
정적 웹 페이지
+
Docker Image 내부에 콘텐츠 포함
+
영속적인 사용자 데이터 저장 요구 없음
```

따라서 단순히 기술을 많이 사용하는 것보다:

> **"현재 서비스에서 Persistent Storage가 실제로 필요한가?"**

를 먼저 판단하는 것이 중요하다.

향후 DB, 업로드 파일, 공유 콘텐츠 등이 추가된다면 PV/PVC 또는 외부 스토리지 도입을 다시 검토할 수 있다.

# 16. 빠른 장애 판단 Cheat Sheet

| 증상 | 먼저 볼 곳 |
|---|---|
| Pod가 실행되지 않음 | `kubectl describe pod` |
| 이미지 실행 실패 | Image / Tag / Pull Policy |
| Replica 부족 | Deployment / ReplicaSet |
| Service 접속 실패 | Selector / Label |
| Endpoint 없음 | Service Selector |
| Pod IP 변경 | 정상 가능성 높음 |
| NodePort 접속 실패 | Service / Endpoint / Node |
| Ingress 접속 실패 | Ingress Rule / Controller |
| HAProxy DOWN | Backend IP / Port |
| Connection refused | 대상 서비스 Listen 여부 |
| Docker 웹 접속 실패 | `-p HostPort:ContainerPort` |
| 이미지 Pull 실패 | 이미지명 / 태그 / Registry |

# 18. 이번 프로젝트에서 얻은 핵심 교훈

## ① "Running"만 보고 정상이라고 판단하지 않는다.

Pod가 Running이어도:

```text
Service Selector 오류
Endpoint 없음
NodePort 오류
Ingress 오류
HAProxy Backend 오류
```

등으로 서비스는 실패할 수 있다.

---

## ② Endpoint 확인은 매우 강력하다.

```bash
kubectl get endpoints -n kaist
```

Service와 Pod가 실제로 연결되어 있는지 빠르게 판단할 수 있다.

---

## ③ 외부에서 안 되면 내부부터 확인한다.

```text
Pod
 ↓
Service
 ↓
Endpoint
 ↓
NodePort
 ↓
Ingress
 ↓
HAProxy
 ↓
Client
```

아래 계층부터 하나씩 검증하면 장애 구간을 빠르게 좁힐 수 있다.

---

## ④ 변경 후에는 반드시 검증한다.

```text
설정 수정
   ↓
서비스 재시작 / apply
   ↓
상태 확인
   ↓
로그 확인
   ↓
curl
   ↓
Browser
```

설정 파일을 저장했다고 작업이 끝난 것이 아니다.

# 19. 면접에서 설명한다면 ⭐

> Kubernetes 환경에서 접속 장애가 발생하면 Pod부터 외부 Load Balancer까지 계층적으로 확인합니다. 먼저 Pod와 Deployment 상태를 확인하고, Service의 Selector가 Pod Label과 일치하는지 확인합니다. 이후 Endpoint를 확인해 Service가 실제 Pod와 연결되어 있는지 검증합니다. 내부 서비스가 정상이라면 NodePort와 Ingress를 확인하고, 마지막으로 HAProxy의 Backend 상태와 로그를 점검합니다. 이를 통해 전체 설정을 무작정 수정하지 않고 장애가 발생한 구간을 단계적으로 좁혀갈 수 있습니다.
