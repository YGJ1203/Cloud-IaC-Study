## 4. PV / PVC 핵심

AI PV 예시:

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: kaist-ai-pv
spec:
  nfs:
    server: 192.168.2.80
    path: /www/vol/ai
  capacity:
    storage: 2Gi
  volumeMode: Filesystem
  accessModes:
    - ReadWriteMany
  storageClassName: manual
  persistentVolumeReclaimPolicy: Retain
```

AI PVC:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: kaist-ai-pvc
  namespace: kaist-ai
spec:
  volumeName: kaist-ai-pv
  accessModes:
    - ReadWriteMany
  volumeMode: Filesystem
  resources:
    requests:
      storage: 2Gi
  storageClassName: manual
```

SYS는 동일 패턴으로 `kaist-sys-pv`, `kaist-sys-pvc`, `/www/vol/sys`, `namespace: kaist-sys`를 사용한다.

핵심:
- PV는 **Cluster Scope** → `metadata.namespace` 불필요
- PVC는 **Namespaced Resource**
- NFS 공유 볼륨이므로 `ReadWriteMany(RWX)`
- `volumeName`으로 서비스별 PVC ↔ PV 연결을 명확하게 고정
- `Retain`은 Claim 해제 후에도 기존 스토리지 데이터를 보존하는 정책

```text
kaist-ai-pvc  → kaist-ai-pv  → /www/vol/ai
kaist-sys-pvc → kaist-sys-pv → /www/vol/sys
```

확인:

```bash
kubectl get pv
kubectl get pvc -n kaist-ai
kubectl get pvc -n kaist-sys
```

정상 목표: `PV = Bound`, `PVC = Bound`

## 5. Deployment에서 PVC Mount

핵심 부분:

```yaml
volumeMounts:
  - name: kaist-ai-vol
    mountPath: /usr/share/nginx/html

volumes:
  - name: kaist-ai-vol
    persistentVolumeClaim:
      claimName: kaist-ai-pvc
```

전체 연결:

```text
NFS → PV → PVC → Pod Volume → /usr/share/nginx/html → Nginx
```

AI Deployment는 `replicas: 6`으로 구성했고 실제 결과는 node1/node2/node3에 각각 2개씩 배치되었다.

> 주의: `replicas: 6`만으로 항상 2/2/2 균등 배치가 보장되는 것은 아니다. 보장이 필요하면 Topology Spread Constraints 또는 Pod Anti-Affinity 등을 고려한다.

Pod 내부 실제 NFS 데이터 검증:

```bash
kubectl exec -n kaist-ai <POD_NAME> -- cat /usr/share/nginx/html/index.html
```

NFS의 `index.html` 내용이 그대로 출력되어 **NFS → PV → PVC → Pod Mount** 체인을 확인했다.

## 6. Service / NodePort

AI:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: kaist-service
  namespace: kaist-ai
spec:
  type: NodePort
  selector:
    app: kaist-ai
  ports:
    - protocol: TCP
      port: 80
      targetPort: 80
      nodePort: 30001
```

SYS는:
- Namespace: `kaist-sys`
- selector: `app: kaist-sys`
- NodePort: `30002`

Namespace가 다르므로 두 Service 모두 `metadata.name: kaist-service` 사용 가능.

```text
<Node IP>:30001 → Service:80 → Pod:80
```

NodePort 검증:

```bash
curl http://192.168.2.61:30001
curl http://192.168.2.62:30001
curl http://192.168.2.63:30001
```

AI는 Worker 3대 모두 정상 출력 확인. SYS도 `30002`로 동일하게 정상 검증 완료.

## 7. 오늘의 트러블슈팅 ⭐

### PV Released / PVC Pending

증상:

```text
PV  : Released
PVC : Pending
```

원인: `persistentVolumeReclaimPolicy: Retain`인 PV가 이전 PVC에 Bound된 뒤 Claim이 삭제되어 `Released` 상태가 됨.

핵심:

> **Released ≠ Available**

초기 실습 환경에서는 기존 PV/PVC를 정리하고 `PV 재생성 → Available 확인 → PVC 생성 → Bound` 순서로 복구했다.

### Deployment selector 오류

오류:

```text
unknown field "spec.selector.app"
```

잘못된 구조:

```yaml
selector:
  app: kaist-ai
```

정상:

```yaml
selector:
  matchLabels:
    app: kaist-ai
```

`selector.matchLabels`와 `template.metadata.labels`가 일치해야 한다.

### Namespace 오류 사전 수정

기존 `namespace: kaist`를 최종 구조인 `namespace: kaist-ai`로 수정했다. PVC는 Namespaced Resource이므로 Deployment와 PVC가 동일 Namespace에 있어야 한다.

## 8. 발표용 NFS / PV / PVC 정리 🎤

- **NFS**: 실제 웹 데이터를 저장하는 공유 네트워크 스토리지
- **PV**: NFS 같은 외부 스토리지를 Kubernetes의 Storage Resource로 표현
- **PVC**: Pod가 필요한 Storage를 요청하는 Namespaced Resource
- **RWX**: 여러 Node의 여러 Pod가 동일한 NFS 볼륨을 공유하기 위해 사용

### 발표용 한 문장

> NFS에 실제 웹 데이터를 저장하고 이를 PV로 Kubernetes 스토리지 자원화한 뒤, 각 Namespace의 PVC가 해당 PV를 Claim하도록 구성했습니다. Deployment의 여러 Pod는 PVC를 Nginx DocumentRoot에 마운트하여 동일한 웹 콘텐츠를 공유합니다.
