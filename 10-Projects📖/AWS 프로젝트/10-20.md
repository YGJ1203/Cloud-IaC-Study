## 5. 팀원 HQ Terraform 파일 구조

| 파일 | 핵심 리소스 | 검토 포인트 |
|---|---|---|
| `main(4).tf` | VPC `10.0.0.0/16`, Public 2, Private 2, IGW, NAT 2, 라우팅, 공통 SG, Key Pair | 개인 HQ와 CIDR 다름, SSH `0.0.0.0/0` 등 보안 정책 검토 |
| `alb(1).tf` | Public ALB, Internal ALB, Target Groups, Listeners | **Internal ALB의 subnet 지정이 Public 2개**; 샘플 본사 표의 Private 2개와 불일치 |
| `asg(1).tf` | Launch Template, ASG, ALB Target 연결 | desired 4 / min 4 / max 6; Public Subnet 배치, 스크립트 파일 필요 |
| `intra.tf` | Private EC2 2대, Target Group Attachment | `intra-script.sh` 필요, SG 및 내부 접근 경로 확인 |
| `rds(1).tf` | DB SG, DB Subnet Group, Aurora Cluster + 2 인스턴스 | Private 2개 사용; DB 3306 허용 범위 확인 |

### 중요한 코드 검토 결과

**(A) Internal ALB의 `internal = true`는 내부용 Scheme을 뜻한다.** Public Subnet에 배치했다고 인터넷 공개형 ALB로 바뀌지는 않는다. 그러나 샘플 본사 표에는 Private ALB가 Private 1/2 Subnet에 배치된 것으로 명시되어 있으므로 팀 코드 수정 여부를 협의한다.

```hcl
# 팀원 alb(1).tf의 현 상태
subnets = [
  aws_subnet.KAPublic1Subnet.id,
  aws_subnet.KAPublic2Subnet.id
]

# 하나금융그룹 샘플의 본사 표를 따를 경우 검토할 방향
subnets = [
  aws_subnet.KAPrivate1Subnet.id,
  aws_subnet.KAPrivate2Subnet.id
]
```

**(B) ASG는 Public 2개 서브넷에 배치됨.** 샘플의 구성도와 코드를 추가로 대조하여 팀 최종 배치를 확정한다. Public Subnet이라고 항상 공인 IP가 할당되는 것은 아니므로 Launch Template의 네트워크 설정까지 검토한다.

**(C) 공통 SG의 SSH 22를 `0.0.0.0/0`에 허용한 설정은 보안상 위험.** 교재 실습과 실제 운영 정책을 구분하고, 발표 시 최소 권한·SSM 접근·역할별 SG 분리를 개선안으로 제시할 수 있다.

**(D) `script.sh`, `intra-script.sh`, 로컬 공개키 파일 경로가 필요.** 팀원 파일 5개만으로 전체 배포 성공을 보장할 수 없다. 경로·권한·AMI·초기화 스크립트·보안 그룹을 확인해야 한다.

**(E) DB는 Aurora 클러스터 + 인스턴스 2개.** 인스턴스 이름으로 Writer/Reader를 단정하지 말고 생성 후 AWS 상태를 조회한다.

## 9. 면접·시험 대비 핵심 Q&A

**Q1. `terraform plan`과 `apply`의 차이는?**  
A. Plan은 현재 State와 코드, 원격 리소스 상태를 비교해 예상 변경을 보여주고, Apply는 변경을 실제 반영한다. Plan이 성공해도 Apply 성공을 보장하지는 않는다.

**Q2. Public Subnet의 조건은?**  
A. 해당 서브넷에 연결된 Route Table이 인터넷 게이트웨이로 향하는 적절한 경로를 갖는 것이 핵심이다. EC2가 인터넷과 통신하려면 공인 IP 및 SG/NACL 조건도 충족해야 한다.

**Q3. `map_public_ip_on_launch = true`만 설정하면 인터넷이 되나?**  
A. 아니다. 이는 EC2 시작 시 공인 IPv4 자동 할당 동작을 설정하는 속성이다. IGW/Route Table/보안 정책이 필요하다.

**Q4. NAT Gateway의 목적은?**  
A. Private Subnet의 리소스가 외부로 연결을 시작할 수 있게 해준다. 외부 인터넷에서 Private EC2로 직접 연결을 허용하는 것은 아니다.

**Q5. Internal ALB가 Public Subnet에 있으면 자동으로 외부 공개되나?**  
A. 아니다. `internal = true`이면 내부용 Scheme이다. 다만 샘플에서 요구하는 Private Subnet 배치와 일치하는지는 별도로 검토해야 한다.

**Q6. VPC Peering만 만들면 두 VPC가 통신하나?**  
A. 아니다. CIDR 비중복, 요청/수락, 양쪽 Route Table, SG/NACL, 서비스 포트 및 실제 통신 검증이 필요하다. Peering은 비전이적이다.

**Q7. Terraform 리소스 이름을 바꾸면?**  
A. Terraform 주소가 바뀌면 기존 State의 리소스와 다른 객체로 판단될 수 있다. 단순 리팩터링이라면 `moved` 블록 또는 `terraform state mv` 등 안전한 이전 방식을 검토해야 한다.

**Q8. 왜 팀원 파일을 기존 `hq/`에 바로 복사하면 안 되나?**  
A. 다른 리소스 주소·CIDR·구성으로 인해 기존 인프라 변경, 교체, 삭제 또는 신규 생성이 계획될 수 있기 때문이다. 특히 유료 DB와 NAT는 신중히 다뤄야 한다.

**Q9. Aurora 인스턴스 2개면 무조건 특정 이름이 Writer인가?**  
A. 아니다. 실제 Writer/Reader 역할은 클러스터 상태와 엔드포인트를 조회해 확인한다.

**Q10. 현재 프로젝트의 우선 목표는?**  
A. 교재 및 하나금융그룹 샘플 아키텍처를 충실히 재현하고, 팀원 코드와 개인 실습의 차이를 검증해 팀 최종 계정에서 안전하게 통합 구축하는 것이다.
