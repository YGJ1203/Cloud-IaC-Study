# KAIST HQ EKS + CloudWatch 프로젝트 정리

> 작성일: 2026-10-26  
> 범위: 본사(HQ) VPC 기반 Amazon EKS 및 Amazon CloudWatch 담당 파트, 구축·검증·시연 영상 회고

## 1. 오늘의 핵심 요약

- 본사(HQ)의 기존 VPC 아키텍처를 기반으로 EKS 클러스터를 구축·운영하는 프로젝트이므로 EKS를 네트워크 구성과 무관한 독립 리소스로 설명하면 안 된다.
- EKS와 CloudWatch 담당 범위를 중심으로 최종 발표/시연 영상 구성을 정리했다.
- CloudWatch 로그 그룹에 **오늘 날짜의 로그가 확인되지 않는 문제**가 있어, 영상에서 해당 로그 조회 장면은 과감히 제외했다.
- 영상은 **3분 55초**로 마무리해 4분 제한을 충족했다.
- 교수자/강사 PDF 교재의 설정을 우선 적용하고, 다른 권장 설정은 별도 개선안으로 구분한다.

## 2. 아키텍처에서 EKS의 위치

```text
KAIST HQ AWS 환경
└─ HQ VPC
   ├─ 서브넷 / 라우팅 / 보안 그룹 등 네트워크 기반
   ├─ Amazon EKS 클러스터
   │  ├─ 워커 노드(EC2 기반 노드 그룹)
   │  ├─ Kubernetes 시스템 구성 요소
   │  └─ 애플리케이션 Pod 및 Service
   └─ Amazon CloudWatch
      ├─ EKS/노드/워크로드 관련 지표(설정에 따라 수집)
      └─ 로그 그룹 및 로그 스트림(수집 구성에 따라 표시)
```

**설명 포인트:** EKS 컨트롤 플레인은 AWS가 관리하지만, 클러스터의 네트워크 연결과 워커 노드·Pod의 통신은 HQ VPC의 서브넷, 라우팅, 보안 정책과 밀접하게 연결된다. CloudWatch는 관측·모니터링 서비스이며, 모든 로그가 자동으로 수집된다고 단정하면 안 된다.

## 3. 확인된 Kubernetes 구성 요소

이전 실습에서 `kubectl get pods -A` 결과로 다음 구성 요소의 실행 상태를 확인한 기록이 있다.

| 네임스페이스 | 구성 요소 | 당시 관측 상태 | 의미 |
|---|---|---|---|
| `external-dns` | `external-dns` | Running | DNS 레코드 자동 관리 구성 요소 |
| `kube-system` | `aws-node` | Running | AWS VPC CNI 네트워크 관련 DaemonSet Pod |
| `kube-system` | `coredns` | Running | 클러스터 내부 DNS |
| `kube-system` | `eks-node-monitoring-agent` | 목록에 등장 | 노드 모니터링 관련 에이전트 |

> 주의: 위 내용은 **이전 실습 시점의 출력 기록**이다. 10월 26일 현재의 실행 상태를 보장하지 않는다.

## 4. 검증 명령어 모음

```powershell
# EKS 클러스터 접근 설정 확인
kubectl config current-context

# 노드 확인
kubectl get nodes -o wide

# 모든 네임스페이스의 Pod 상태 확인
kubectl get pods -A

# 서비스 확인
kubectl get svc -A

# 배포 리소스 확인
kubectl get deployments -A

# 특정 Pod 상세 진단 (실제 이름으로 교체)
kubectl describe pod <POD_NAME> -n <NAMESPACE>

# Pod 로그 조회 (실제 이름으로 교체)
kubectl logs <POD_NAME> -n <NAMESPACE> --tail=100
```

**영상 설명 시 유의:** `Running`만으로 애플리케이션의 모든 기능이 정상임을 보장하지 않는다. 필요한 경우 `READY`, 재시작 횟수, Service 연결 및 실제 응답까지 함께 확인한다.

## 5. CloudWatch에서 확인할 항목

| 구분 | 확인할 내용 | 해석 시 주의 |
|---|---|---|
| Metrics | EKS/EC2/Container Insights 관련 CPU, 메모리, 노드·Pod 지표 | 메모리·Pod 상세 지표는 수집 설정에 따라 미제공 가능 |
| Log groups | EKS 컨트롤 플레인 또는 워크로드 로그 그룹 존재 여부 | 로깅 기능 활성화 여부에 따라 달라짐 |
| Log streams | 스트림별 최신 이벤트 시각 | 로그 그룹 존재와 최신 로그 수집은 별개 |
| Logs Insights | 로그 쿼리 및 기간 필터링 | 조회 기간·리전·로그 그룹을 먼저 확인 |
| Alarms | 경보 생성 및 상태 | 경보를 실제 생성하지 않았다면 생성했다고 발표하지 않기 |

### 오늘 날짜의 로그가 보이지 않았던 상황

**확인된 사실:** 오늘 날짜의 로그를 영상에서 보여주기 어려웠으며, 최종 시연에서 로그 관리 부분을 생략했다.

**가능한 원인(미확정):** 로그 수집 비활성화, 해당 시간대 이벤트 미발생, 조회 기간/시간대 문제, 잘못된 리전·로그 그룹 선택, 로그 수집 지연 또는 에이전트 설정 문제.

**재점검 순서:**
1. AWS 리전 및 로그 그룹 선택을 확인한다.
2. CloudWatch Logs의 시간 범위와 타임존을 확인한다.
3. 로그 스트림의 마지막 이벤트 시간을 확인한다.
4. EKS 컨트롤 플레인 로깅 및 워크로드 로그 수집 설정을 각각 확인한다.
5. 필요하면 에이전트와 권한 설정을 점검한다.

> 로그가 없다는 사실만으로 EKS 전체 장애라고 판단해서는 안 된다. 반대로 로그가 과거에 있었다는 이유로 오늘 수집이 정상이라고 단정해서도 안 된다.

## 8. 면접 대비 핵심 Q&A

**Q1. EKS가 VPC와 관계가 있나요?**  
네. EKS의 노드와 Pod 네트워킹, 서브넷 배치 및 보안 설정은 VPC와 긴밀하게 연결됩니다.

**Q2. `kubectl get pods -A`는 무엇을 확인하나요?**  
모든 네임스페이스에 속한 Pod의 준비 상태, 실행 상태, 재시작 횟수 등을 확인합니다.

**Q3. CloudWatch와 Kubernetes 로그는 같은 것인가요?**  
아닙니다. Kubernetes 로그는 `kubectl logs` 등으로 확인할 수 있고, CloudWatch에 보려면 대상에 맞는 로그 전달·수집 설정이 필요합니다.

**Q4. CloudWatch에 오늘 로그가 없으면 장애인가요?**  
반드시 그렇지는 않습니다. 로그 생성 여부, 수집 설정, 권한, 시간 범위, 리전 등을 순서대로 점검해야 합니다.

**Q5. EKS 컨트롤 플레인과 워커 노드는 누가 관리하나요?**  
컨트롤 플레인은 AWS가 관리합니다. 워커 노드는 사용한 노드 방식(관리형 노드 그룹, 자체 관리형, Fargate 등)에 따라 관리 책임이 다릅니다.
