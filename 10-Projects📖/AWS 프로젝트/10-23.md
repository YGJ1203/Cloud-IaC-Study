# 2026-10-23 KAIST 하이브리드 클라우드 — EKS·ALB 구축 및 Terraform 삭제 트러블슈팅

> **오늘의 한 줄:** Terraform 기반 AWS 인프라 위에 EKS와 ALB Ingress를 구성하고 KAIST 홈페이지의 실제 접속 및 HTTP 200 응답까지 확인했다. 이후 `terraform destroy` 중 서브넷 종속성 오류가 발생하여 삭제 작업을 안전하게 중단하고 최신 프로젝트를 ZIP으로 백업했다.
>
> **기록 기준:** 대화에서 보고된 실제 명령 출력과 확인 결과를 우선 기록했다. 일부 식별자 및 재구축 절차는 당시 확인된 값에 기반하며, AWS 리소스의 **현재 상태**를 의미하지 않는다.

## 3. AWS Load Balancer Controller 구성

### 오늘 확인한 핵심 사항

- EKS의 OIDC 연동 및 Controller용 IAM 역할 준비
- Helm으로 AWS Load Balancer Controller 설치
- `kube-system` 네임스페이스에서 Controller Deployment 확인
- 최종적으로 Controller `READY 2/2`, `AVAILABLE 2` 확인

확인 명령 예시:

```bash
kubectl get deployment -n kube-system aws-load-balancer-controller
kubectl get pods -n kube-system
```

> 위 명령은 복습·재검증용 예시다. 실제 설치에 사용한 전체 Helm 명령과 IAM 설정값은 프로젝트 파일/명령 기록을 기준으로 확인해야 한다. 임의로 복원하지 않았다.

### Controller가 중요한 이유

- Kubernetes의 `Ingress` 선언을 AWS ALB와 연결한다.
- ALB, Listener, Target Group 등의 생성·조정을 수행한다.
- 따라서 Kubernetes 리소스를 삭제하지 않고 AWS 콘솔에서 ALB만 수동 삭제하면, Controller가 해당 ALB를 다시 생성하려 할 수 있다.
- 이 점이 **Terraform 삭제 과정의 종속성 문제**와도 연결된다.

## 4. KAIST 홈페이지 Kubernetes 배포

### 적용한 파일

`kaist-eks-homepage.yaml`

이 파일에는 다음 네 종류의 리소스를 정의했다.

| Kubernetes 리소스 | 이름 | 역할 |
|---|---|---|
| ConfigMap | `kaist-homepage-html` | KAIST 홈페이지 HTML 제공 |
| Deployment | `kaist-homepage` | Nginx Pod 2개 운영 |
| Service | `kaist-homepage` | Pod에 대한 내부 서비스 엔드포인트 제공 |
| Ingress | `kaist-homepage` | ALB를 통해 외부 HTTP 요청 수신 |

### 실제 적용 결과

```console
configmap/kaist-homepage-html created
deployment.apps/kaist-homepage created
service/kaist-homepage created
ingress.networking.k8s.io/kaist-homepage created
```

실행 명령:

```bash
kubectl apply -f kaist-eks-homepage.yaml
```

### HTML 처리 방식

- 기존 EC2 사용자 데이터 스크립트 `script(1).txt`에 있던 **홈페이지 HTML 부분**을 활용했다.
- 해당 HTML을 Kubernetes ConfigMap으로 제공하고 Nginx가 서비스하도록 구성했다.
- 기존 EC2 사용자 데이터 전체를 Kubernetes에 그대로 실행한 것은 아니다.
- 별도 ECR 이미지 빌드·푸시 없이도 ConfigMap + Nginx 방식으로 이번 홈페이지 접속 검증을 완료했다.

### ALB Ingress 설정의 핵심 개념

- Ingress class: `alb`
- ALB scheme: `internet-facing`
- Target type: `ip`
- ALB가 사용할 공개 서브넷 지정

> 위 항목은 당시 적용한 구성의 핵심 특성이다. **실제 YAML 전문은 백업 ZIP의 원본 파일을 정본으로 사용**한다. 본 문서에 기억으로 YAML 전문을 재작성하지 않았다.

## 6. Terraform `destroy` 트러블슈팅

### 사건 개요

실습 후 AWS 과금 방지를 위해 Terraform으로 리소스 삭제를 시도했으나, 일부 네트워크 리소스가 삭제되지 않고 `Still destroying...` 상태가 오래 지속되었다.

대화에서 언급된 지연 대상:

- Internet Gateway
- Public Subnet
- Aurora RDS Cluster Instance
- 이후 Private Subnet의 `DependencyViolation` 오류

### 실제 확인된 오류

```text
Error: deleting EC2 Subnet (subnet-04109d80f5d6f654e):
operation error EC2: DeleteSubnet,
StatusCode: 400,
api error DependencyViolation:
The subnet 'subnet-04109d80f5d6f654e'
has dependencies and cannot be deleted.
```

이 오류가 의미하는 바:

- Terraform이 서브넷 삭제 API를 호출했다.
- AWS가 해당 서브넷에 **남아 있는 종속 리소스**를 이유로 삭제를 거부했다.
- 따라서 단순한 Terraform HCL 문법 오류라고 볼 수 없다.
- **정확히 어떤 종속 리소스가 삭제를 막았는지는 이 메시지만으로 확정할 수 없다.**

### 원인 후보와 확인해야 할 대상

| 후보 | 왜 확인하는가 | 확인 위치 |
|---|---|---|
| EKS 관리형 노드 그룹 | 워커 EC2와 ENI가 서브넷을 사용 | EKS → 클러스터 → 컴퓨팅 |
| EKS 클러스터 | EKS 관리 ENI 등이 존재할 수 있음 | EKS → 클러스터 |
| ALB | 로드밸런서가 서브넷 및 ENI 사용 | EC2 → 로드 밸런서 |
| NAT Gateway | 서브넷과 ENI/EIP를 사용 | VPC → NAT 게이트웨이 |
| EC2 / ENI | 인스턴스 또는 관리형 ENI가 서브넷 점유 | EC2 → 네트워크 인터페이스 |
| RDS 관련 리소스 | DB 서브넷 그룹·DB 인스턴스 등 의존성 | RDS → 데이터베이스 |

**당시 콘솔에서 실제 확인된 사실:**

- `KAEKSCluster` 상태가 `ACTIVE`였음
- `KAEKSNodeGroup` 상태도 `ACTIVE`였음

이는 EKS 관련 리소스가 여전히 남아 있었다는 **강한 단서**지만, 문제의 Private Subnet을 막은 **직접 원인이 무엇인지는 ENI/종속성 확인 전까지 미확정**이다.

### 왜 Terraform으로 만들었는데 자동 삭제가 안 됐을까?

Terraform은 **자신이 상태 파일로 관리하는 리소스**의 의존성을 기준으로 삭제를 조정한다. 반면 Kubernetes Ingress를 보고 Controller가 생성한 ALB 등은 Terraform이 직접 생성·추적한 리소스가 아닐 수 있다.

따라서 다음 상황이 발생할 수 있다.

```text
Terraform: VPC/서브넷을 삭제하려고 시도
       |
       v
AWS: 이 서브넷은 아직 사용 중!
       |
       v
가능한 사용 주체: EKS, 노드 그룹, ALB, NAT Gateway, ENI 등
       |
       v
DependencyViolation → 삭제 실패
```

**실무 교훈:** Terraform으로 생성한 리소스와 Kubernetes Controller 등 **외부 시스템이 생성한 리소스의 소유·삭제 책임을 구분**해야 한다.

## 7. 시간이 촉박할 때 Terraform 안전 중단

학원 컴퓨터를 종료해야 해서 Terraform 실행을 중단했다.

### 실제 중단 출력

```text
Interrupt received.
Please wait for Terraform to exit or data loss may occur.
Gracefully shutting down...
```

이후 `Error: execution halted`와 서브넷 삭제 오류가 표시되었고, 최종적으로 CMD 프롬프트가 돌아왔다.

```cmd
C:\terraform\project>
```

### 실제 취한 조치

1. `Ctrl+C` 한 번으로 정상 종료 요청
2. Terraform 프로세스가 종료되어 CMD 프롬프트가 돌아온 것 확인
3. 최신 `C:\terraform\project` 폴더를 ZIP으로 압축
4. ZIP 파일을 카카오톡 대화방에 업로드하여 별도 보관

### 주의 사항

- `Ctrl+C`를 여러 번 연속 입력하거나 CMD를 강제 종료하면 상태 파일 기록이 손상될 위험이 있다.
- Terraform이 종료되더라도 AWS 측에서 이미 시작한 비동기 삭제 작업이 계속 진행될 수 있다.
- `destroy` 중단은 **전체 리소스 삭제 완료를 의미하지 않는다.**
- `terraform.tfstate` 및 ZIP에는 민감한 구성 정보가 포함될 수 있으므로 공개 저장소에 업로드하지 않는다.
- ZIP이 카카오톡에서 정상적으로 내려받아지는지도 확인하는 것이 좋다.

## 8. 집에서 AWS 콘솔로 정리할 때의 원칙

### 왜 콘솔 삭제가 어려웠나?

AWS 리소스는 여러 단계의 종속성을 가진다. 예를 들어 서브넷을 삭제하려면 그 안에서 동작하는 서비스와 ENI가 먼저 정리되어야 한다.

### 안전한 점검 순서

1. **리전 확인:** 서울 `ap-northeast-2` 선택
2. **EKS:** 클러스터와 노드 그룹이 남아 있는지 확인
3. **ALB:** Kubernetes Ingress가 생성한 로드밸런서 잔존 여부 확인
4. **RDS:** Aurora 인스턴스·클러스터 삭제 진행 여부 확인
5. **NAT Gateway:** `Available`, `Deleting`, `Deleted` 등 상태 확인
6. **EC2 → 네트워크 인터페이스:** 삭제 실패한 서브넷 ID로 필터링하고 ENI 설명·소유 서비스 확인
7. **VPC:** 종속 리소스 정리 후 서브넷·라우팅·VPC 정리

**중요한 삭제 순서 원칙:** 가능하면 Kubernetes Ingress/Service 등으로 생성된 외부 리소스를 먼저 정리하고, 워크로드 → 노드 그룹 → EKS 클러스터 순으로 정리한다. 다만 **이미 Terraform과 콘솔 삭제가 섞인 상태**이므로 실제 잔존 리소스를 확인한 뒤 진행해야 한다.

> ENI가 삭제되지 않는다고 무작정 강제 삭제하거나, 사용 중인 보안 그룹/서브넷을 먼저 지우려 하지 않는다. 먼저 ENI의 **소유 서비스**를 확인한다.

### 과금 주의

EKS 클러스터, EC2 워커 노드, NAT Gateway, ALB, RDS 등은 남아 있는 동안 과금될 수 있다. **콘솔에서 일부 항목이 삭제된 것만으로 모든 비용이 중단되었다고 단정하면 안 된다.**

## 9. 월요일 시연 영상 준비 계획

### 시연 방식

**기존 캡처를 보여주는 발표가 아니라, 실제 AWS 콘솔과 작동 중인 KAIST 홈페이지를 영상으로 촬영할 예정.** 따라서 월요일에는 시연에 필요한 환경이 다시 동작해야 한다.

### 우선순위별 작업

| 우선순위 | 작업 | 성공 기준 |
|---|---|---|
| P0 | 백업 ZIP 다운로드·압축 해제 | `.tf`, `.tfstate`, YAML 확보 |
| P0 | AWS 현재 잔존 리소스 확인 | 중복·과금 위험 파악 |
| P0 | Terraform 상태 확인 | `terraform plan` 검토 |
| P1 | EKS 및 노드 그룹 재구축 | Cluster `ACTIVE`, Nodes `Ready` |
| P1 | Controller 배포/확인 | `2/2` |
| P1 | 홈페이지 YAML 적용 | Pod 2개 `Running` |
| P1 | Ingress/ALB 확인 | ALB DNS 발급 |
| P1 | 홈페이지 접속 검증 | 브라우저 표시 + HTTP 200 |
| P1 | 영상 촬영 | 실제 AWS 화면과 홈페이지 작동 장면 |
| P2 | CloudWatch 관련 시연 범위 점검 | 팀 요구사항에 맞는 증빙 |
| P2 | 시연 후 리소스 정리 | 유료 리소스 잔존 여부 확인 |

### 재구축 전 특히 주의할 점

- 콘솔에서 리소스를 수동 삭제했으므로 **백업한 Terraform 상태 파일과 실제 AWS 상태가 불일치**할 수 있다.
- 기존 상태 파일을 지우고 처음부터 `apply`하는 방식은 **중복 리소스와 추가 비용**을 초래할 수 있다.
- `terraform init` 후 `terraform plan` 결과를 꼼꼼히 읽고, 의도치 않은 생성/교체/삭제가 없는지 확인한다.
- 기존 `terraform.tfstate`는 작업 전 한 번 더 복사하여 보존한다.
- EKS 및 ALB 프로비저닝 시간은 가변적이다. **월요일 점심 전 완료를 목표로 하되 시간을 보장할 수는 없다.**
- 새로 생성한 ALB DNS는 과거 주소와 달라질 수 있으므로 `kubectl get ingress`에서 최신 주소를 확인한다.

### 월요일 재검증 명령 치트시트

```bash
# Terraform 프로젝트에서
terraform version
terraform init
terraform plan

# EKS 접속 설정 (필요할 때)
aws eks update-kubeconfig --region ap-northeast-2 --name KAEKSCluster

# 클러스터/Controller 확인
kubectl get nodes -o wide
kubectl get deployment -n kube-system aws-load-balancer-controller

# 홈페이지 배포 및 검증
kubectl apply -f kaist-eks-homepage.yaml
kubectl get deployment kaist-homepage
kubectl get pods
kubectl get service kaist-homepage
kubectl get ingress kaist-homepage

# 새로 발급된 ALB DNS로 검증
curl -I http://<새_ALB_DNS>
```

> `terraform apply`와 `terraform destroy`는 의도한 변경을 `plan`으로 검토한 뒤 실행한다. 위 명령은 복습용이며, 실제 파일명·경로·리소스 상태에 맞춰 조정한다.

## 11. 실무·면접 핵심 Q&A

**Q1. EKS 클러스터가 ACTIVE인데 왜 서브넷을 삭제할 수 없나요?**  
A. EKS 자체 또는 관련 노드 그룹·로드밸런서·ENI 등이 서브넷을 사용 중일 수 있기 때문이다. 단, ACTIVE라는 사실만으로 직접 원인을 확정할 수는 없으며 ENI와 소유 서비스를 확인해야 한다.

**Q2. Terraform으로 만든 환경인데 왜 `destroy`가 실패하나요?**  
A. Terraform이 관리하지 않는 외부 생성 리소스(Kubernetes Controller가 생성한 ALB 등), AWS의 비동기 삭제, 남아 있는 종속 리소스 때문에 실패할 수 있다.

**Q3. Ingress와 Service는 무엇이 다른가요?**  
A. Service는 Kubernetes 내부에서 Pod 집합에 접근하는 안정적인 추상화이고, Ingress는 HTTP/HTTPS 요청을 서비스로 라우팅하는 규칙이다. AWS Load Balancer Controller는 Ingress를 바탕으로 ALB를 관리할 수 있다.

**Q4. 왜 ALB의 target type을 `ip`로 설정했나요?**  
A. Pod IP를 대상으로 직접 라우팅하는 방식으로 구성하기 위해서다. 실제 배포 환경의 VPC CNI, 대상 그룹 및 보안 설정이 정상이어야 동작한다.

**Q5. ConfigMap으로 HTML을 배포한 이유는 무엇인가요?**  
A. 정적 HTML을 컨테이너 이미지에 다시 빌드하지 않고 Nginx에 제공하기 위해서다. 이번 실습에서는 별도 ECR 이미지 연동 없이 홈페이지 접속 검증을 수행했다.

**Q6. HTTP 200만 나오면 서비스 검증이 끝난 건가요?**  
A. HTTP 요청이 성공했다는 강력한 증거지만, 화면 렌더링·콘텐츠·지속성·보안·가용성 전체를 보장하지는 않는다. 이번에는 브라우저에서 실제 KAIST 홈페이지가 표시되는 것도 확인했다.

**Q7. `Ctrl+C`로 Terraform을 중단하면 AWS 리소스가 자동 복구되나요?**  
A. 아니다. 이미 완료된 생성·삭제는 유지될 수 있고, AWS에서 진행 중인 비동기 작업은 계속될 수 있다. 최신 state를 보존하고 현재 리소스 상태를 확인해야 한다.

**Q8. Terraform state가 왜 중요한가요?**  
A. Terraform 구성과 실제 관리 대상 리소스의 대응 관계를 저장하기 때문이다. state를 잃거나 오래된 파일로 되돌리면 잘못된 변경·중복 생성·삭제 누락 위험이 생긴다.

**Q9. 월요일 시연 전에 반드시 확인할 것은?**  
A. 클러스터 ACTIVE, 노드 Ready, Controller 2/2, 홈페이지 Pod Running, Ingress ALB 주소, 브라우저 접속 및 HTTP 200이다.

**Q10. 이번 경험에서 가장 큰 실무 교훈은?**  
A. “생성 자동화”뿐 아니라 **삭제 순서, 외부 Controller의 리소스 소유권, 상태 파일 백업, 비용 관리, 재현 가능한 시연 절차**까지 설계해야 한다는 점이다.

## 마무리 — 오늘의 엔지니어링 포인트

오늘의 성과는 **EKS를 만들었다**는 사실만이 아니다.

1. 실제 웹 애플리케이션을 Kubernetes에 배포했다.
2. AWS Load Balancer Controller와 ALB Ingress로 외부 접근 경로를 만들었다.
3. Pod·Ingress·HTTP·브라우저 화면까지 단계별로 검증했다.
4. `terraform destroy`가 실패했을 때 `DependencyViolation`의 의미와 리소스 소유권 문제를 경험했다.
5. 작업 종료가 급박한 상황에서 Terraform을 정상 중단하고 상태 파일을 포함한 프로젝트를 백업했다.

> **기억할 문장:** “클라우드 인프라를 잘 구축하는 것만큼, 누가 어떤 리소스를 만들었고 어떤 순서로 안전하게 제거할 수 있는지 아는 것이 중요하다.”

**프로젝트 상태:** EKS 홈페이지 배포 검증 성공 / Terraform 삭제 미완료 / 월요일 실제 시연 준비 예정.
