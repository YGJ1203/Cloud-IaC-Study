### 2.1 기존 환경 정리

VPC Peering을 먼저 삭제한 뒤 Branch를 철거했고, HQ는 Aurora RDS 클러스터가 중지된 상태여서 첫 삭제 과정에서 오류가 발생했다.

### 2.2 Aurora 삭제 오류

당시 오류 요지:

```text
InvalidDBClusterStateFault: Db cluster mydbcluster-hq is in stopped state
```

Aurora 클러스터를 시작하고 사용 가능 상태가 될 때까지 대기한 뒤 삭제를 재시도했다.

```bat
aws rds start-db-cluster --db-cluster-identifier mydbcluster-hq --region ap-northeast-2
aws rds wait db-cluster-available --db-cluster-identifier mydbcluster-hq --region ap-northeast-2
terraform destroy
```

최종 출력:

```text
Destroy complete! Resources: 10 destroyed.
```

**해석:** 10개는 마지막 HQ 삭제 재시도에서 제거된 리소스 수이며, 앞선 삭제 과정에서 이미 제거된 리소스는 포함하지 않는다.

## 3. KAIST-REAL 신규 프로젝트 전환

기존 폴더를 덮어쓰지 않고 별도의 새 폴더에서 구축했다.

```text
C:\terraform\KAIST-REAL
├── alb(3).tf
├── asg(3).tf
├── intra(1).tf
├── main(5).tf
├── rds(2).tf
├── script.sh
└── intra-script.sh
```

처음 전달받은 초기화 스크립트는 `.txt` 확장자였다. Terraform 설정에서 `.sh`를 참조하므로 **파일 내용은 변경하지 않고 이름만 변경**했다.

```bat
ren "script.txt" "script.sh"
ren "intra-script.txt" "intra-script.sh"
```

`.tf` 파일명에 `(5)` 등의 번호가 붙어 있어도 Terraform은 해당 디렉터리의 `.tf` 파일을 읽는다.

### 파일별 역할

| 파일 | 담당 구성 |
|---|---|
| `main(5).tf` | VPC, 서브넷, IGW, NAT Gateway, 라우팅, 보안 그룹 등 |
| `alb(3).tf` | Public/Private ALB, Listener, Target Group |
| `asg(3).tf` | Launch Template, Auto Scaling Group, ALB 연결 |
| `intra(1).tf` | 내부 EC2 2대와 Target Group 등록 |
| `rds(2).tf` | Aurora 클러스터, DB 서브넷 그룹, DB 인스턴스 2대 |
| `script.sh` | 외부 웹 서버의 초기화 및 KAIST 데모 홈페이지 |
| `intra-script.sh` | 내부 웹 서버의 초기화 및 관리자 포털 데모 페이지 |

> 프로젝트의 우선 목표는 전달받은 팀원 코드를 원본대로 재현하는 것이었다. 단, 이것이 하나금융그룹 샘플 보고서의 모든 구성과 완전히 일치한다는 검증은 아직 이루어지지 않았다.

## 4. Terraform 오류 및 해결

### 4.1 `terraform validate` 파일 경로 오류

발생한 오류:

```text
Invalid function argument
no file exists at "./script.sh"
no file exists at "./intra-script.sh"
```

원인:

- `asg(3).tf`의 `filebase64("${path.module}/script.sh")`
- `intra(1).tf`의 `file("${path.module}/intra-script.sh")`
- 실제 파일명은 `script.txt`, `intra-script.txt`였음

해결: 위에서 설명한 `ren` 명령으로 파일명만 변경.

## 6. 실제 서비스 동작 검증

### 6.1 Public ALB — 성공

```bat
terraform state show aws_lb.KAPublicALB
```

출력의 `dns_name`을 이용해 웹 브라우저에서 KAIST 데모 홈페이지 접속에 성공했다.

**검증 범위:** Public ALB를 통한 외부 HTTP 웹페이지 표시.

### 6.2 Private ALB — 성공

Private ALB DNS:

```text
internal-KAPrivateALB-219238162.ap-northeast-2.elb.amazonaws.com
```

내부 EC2 `KAIntra1` 사설 IP:

```text
10.0.100.101
```

`KAIntra1` 터미널에서 실행:

```bash
curl -I http://internal-KAPrivateALB-219238162.ap-northeast-2.elb.amazonaws.com
```

실제 출력 일부:

```text
HTTP/1.1 200 OK
Date: Wed, 21 Oct 2026 08:32:44 GMT
Content-Type: text/html; charset=UTF-8
Content-Length: 7445
Server: Apache/2.4.69 ()
```

**검증 범위:** VPC 내부 DNS 해석, Private ALB HTTP 응답, 백엔드 웹 서버 응답 성공. 단, `curl -I` 한 번으로 모든 대상 인스턴스의 상태를 확인한 것은 아니다.

### 6.3 Target Group 검증 — 다음 작업

Windows CMD에서 처음 `<PRIVATE_TARGET_GROUP_ARN>`을 그대로 입력했을 때 오류가 발생했다. `<`, `>`는 CMD에서 특수 기호이므로 실제 ARN을 큰따옴표로 감싸 입력해야 한다.

확인한 Private Target Group ARN:

```text
arn:aws:elasticloadbalancing:ap-northeast-2:275060989875:targetgroup/KAPrivateTargetGroup/ac2bd3ac3a8f452a
```

**다음 실행 명령:**

```bat
aws elbv2 describe-target-health --target-group-arn "arn:aws:elasticloadbalancing:ap-northeast-2:275060989875:targetgroup/KAPrivateTargetGroup/ac2bd3ac3a8f452a" --region ap-northeast-2
```

기대 확인 사항: `KAIntra1`, `KAIntra2`에 해당하는 두 대상의 `TargetHealth.State`가 모두 `healthy`인지 확인.

## 7. 내일 이어서 확인할 항목

1. **Private Target Group:** 두 내부 EC2 대상 모두 `healthy`인지 확인.
2. **Public Target Group:** ASG가 등록한 웹 서버 대상의 상태 확인.
3. **Auto Scaling:** 현재/희망/최소/최대 용량과 실제 인스턴스 상태 확인.
4. **Aurora:** 클러스터와 인스턴스의 `available` 상태 확인. 필요 시 애플리케이션 DB 접속 테스트.
5. **샘플 대조:** 하나금융그룹 보고서의 네트워크 및 서비스 구성과 현재 팀원 코드 차이 비교.
6. **발표 자료:** 아키텍처, `terraform apply` 결과, Public/Private ALB 검증 화면 캡처 정리.

## 8. 운영상 주의사항

- 현재 교육용 프로젝트 원본에는 **SSH 22번 포트의 전체 인터넷 허용** 및 **고정 root 비밀번호·root SSH 로그인 활성화** 설정이 포함되어 있다. 이번 작업에서는 사용자 요청에 따라 원본 코드를 임의로 변경하지 않았다. 외부 공개 환경이나 장기 운영 환경에 재사용해서는 안 된다.
- NAT Gateway, ALB, Aurora, EC2 등은 **생성 후 사용하지 않아도 비용이 발생할 수 있다.** 실습 종료 후 별도 철거 일정을 정한다.
- `terraform.tfstate`, `*.tfstate.backup`, `*.tfplan`, 개인 키 및 비밀정보는 공개 GitHub 커밋 대상에서 제외한다.
- 인프라가 살아 있는 동안 Terraform 작업 폴더와 State를 임의로 삭제하지 않는다.
