## 2. 프로젝트 맥락과 Terraform 관리 경계

### 2.1 HQ 인프라 구성

오늘의 EKS 실습은 기존 Terraform HQ 인프라 위에서 진행했다.

- VPC: `KAVPC`, CIDR `10.0.0.0/16`
- Public Subnet: `10.0.1.0/24`(2a), `10.0.2.0/24`(2c)
- Private Subnet: `10.0.100.0/24`(2a), `10.0.200.0/24`(2c)
- NAT Gateway: 각 AZ에 1개씩 구성한 기존 실습 환경
- 기존 HQ 서비스: Public/Private ALB, Auto Scaling Group, 내부 EC2, Aurora RDS 등
- 작업 위치: Windows CMD `C:\terraform\project`

> **핵심:** Terraform으로 만든 VPC 안에 콘솔에서 EKS를 생성해도, 그 EKS가 자동으로 Terraform state에 등록되지는 않는다.

### 2.2 기존 Terraform EKS와 새 콘솔 EKS의 차이

| 구분 | 기존 Terraform EKS | 오늘의 콘솔 EKS |
|---|---|---|
| 클러스터 이름 | `KAEKSCluster` | `KAEKSConsoleLab` |
| 구축 방법 | Terraform | AWS Management Console |
| Kubernetes 버전 | 1.35 | 1.37 (`kubectl` 노드 출력은 1.37.1) |
| Terraform 관리 여부 | 관리 대상이었음 | **관리 대상 아님** |
| 재구축 방법 | 관련 `.tf` 코드 복원·적용 | 콘솔에서 재생성 또는 코드화 필요 |
| 삭제 방법 | Terraform으로 관리 | EKS 콘솔/CLI에서 별도 삭제 |

### 2.3 기존 Terraform EKS 정리 과정

1. Terraform 프로젝트를 별도 폴더에 백업.
2. 기존 EKS Deployment를 먼저 정리.
3. Terraform 관리 EKS 관련 리소스 8개를 통제된 방식으로 삭제.
4. `terraform state list | findstr /I "eks"`에서 EKS 관련 항목이 남지 않았음을 확인.
5. `aws eks list-clusters --region ap-northeast-2`에서 기존 클러스터가 없음을 확인.
6. `terraform plan`에서 **No changes** 확인.

백업 예시:

```bat
cd /d C:\terraform
robocopy project project-backup-before-console-eks /E /R:1 /W:1 /XD .terraform
```

**주의:** `terraform.tfstate`, `.tfstate.backup`, `.terraform` 내부의 정보, 비밀값 등이 포함된 파일을 공개 GitHub에 올리지 않는다. `.gitignore`와 비밀정보 점검이 필요하다.

## 3. EKS 콘솔 구축 과정

### 3.1 IAM 역할 생성

**클러스터 역할**

- 이름: `KAEKSConsoleClusterRole`
- 신뢰 주체: EKS 서비스
- 주요 권한: `AmazonEKSClusterPolicy`

**노드 역할**

- 이름: `KAEKSConsoleNodeRole`
- 신뢰 주체: EC2 서비스
- 실습 교재를 따라 노드 운영 관련 권한을 연결.

> 실습용으로 부여한 일부 권한(`AmazonEC2ContainerRegistryFullAccess`, `ElasticLoadBalancingFullAccess` 등)은 운영 환경에서 과도할 수 있다. 팀 프로젝트 최종 제출 전 **최소 권한 원칙**에 따라 재검토한다. 노드 역할, EKS 클러스터 역할, Pod Identity 역할은 서로 목적이 다르다.

### 3.2 EKS 클러스터

| 항목 | 설정 |
|---|---|
| 클러스터 | `KAEKSConsoleLab` |
| 리전 | `ap-northeast-2` |
| Kubernetes | `1.37` |
| VPC | `KAVPC` |
| 서브넷 | Public 2개 + Private 2개를 클러스터 구성에 지정 |
| EKS Auto Mode | OFF |
| 클러스터 IAM 역할 | `KAEKSConsoleClusterRole` |
| API 엔드포인트 | Public + Private |
| Public API 허용 CIDR | 실습 시 `0.0.0.0/0` |
| 인증 모드 | EKS API |

**보안 메모:** Public API 엔드포인트의 `0.0.0.0/0` 허용은 실습 편의 설정이다. 실제 운영에서는 신뢰할 수 있는 IP 범위로 제한하거나 프라이빗 접근 중심으로 설계한다. API 접근은 네트워크 제한과 IAM 인증을 함께 고려한다.

### 3.3 Managed Node Group

| 항목 | 설정 |
|---|---|
| 이름 | `KAEKSNodeGroup` |
| 노드 IAM 역할 | `KAEKSConsoleNodeRole` |
| AMI 계열 | Amazon Linux 2023, x86_64 |
| 인스턴스 | `t3.medium` |
| 구매 옵션 | On-Demand |
| 루트 디스크 | 20 GiB |
| Desired / Min / Max | **2 / 2 / 2** |
| 배치 서브넷 | Private 2a + Private 2c |
| SSH 원격 액세스 | 사용하지 않음 |
| 노드 자동 복구 | OFF |

노드 그룹은 **Private Subnet에만 배치**했으며, EKS 클러스터 설정에 Public Subnet이 포함된 것과 혼동하면 안 된다.

### 3.4 애드온

실습 중 선택·설치한 주요 애드온:

1. Amazon VPC CNI (`aws-node`)
2. CoreDNS
3. kube-proxy
4. EKS Pod Identity Agent
5. EKS Node Monitoring Agent
6. ExternalDNS
7. Metrics Server

**주의:** 애드온 Pod가 `Running`이라는 사실은 모든 외부 AWS API 권한 및 기능 검증이 끝났다는 뜻이 아니다. 특히 ExternalDNS가 Route 53을 변경하려면 적절한 IAM 권한 및 연동 설정이 필요하다.

## 4. Windows CMD에서 EKS 접속

### 4.1 kubeconfig 갱신

```bat
aws eks update-kubeconfig --region ap-northeast-2 --name KAEKSConsoleLab
```

실제 결과:

```text
Added new context arn:aws:eks:ap-northeast-2:275060989875:cluster/KAEKSConsoleLab to C:\Users\User\.kube\config
```

**의미:** AWS CLI가 EKS 클러스터 접근 정보를 kubeconfig에 추가했다. 이 단계만으로 노드·애플리케이션이 정상이라는 뜻은 아니므로 `kubectl` 검증이 필요하다.

### 4.2 노드 확인

```bat
kubectl get nodes -o wide
```

실제 확인된 정보:

| 노드 | STATUS | INTERNAL-IP | EXTERNAL-IP | VERSION |
|---|---|---|---|---|
| `ip-10-0-100-176...internal` | Ready | `10.0.100.176` | `<none>` | `v1.37.1-eks-117f323` |
| `ip-10-0-200-202...internal` | Ready | `10.0.200.202` | `<none>` | `v1.37.1-eks-117f323` |

추가 확인:

- OS: `Amazon Linux 2023.12.20261016`
- 커널: `6.18.54-121.166.amzn2023.x86_64`
- 런타임: `containerd://2.3.5+unknown`
- 노드 역할 표시: `<none>` — Kubernetes 노드가 Ready가 아닌 상태라는 뜻이 아니다.

**해석:** EKS API와 노드 등록·기본 연결이 정상이며, 두 노드 모두 공인 IP 없이 사설 주소를 사용한다. 단, 이것만으로 모든 Pod 간 통신이나 외부 서비스 접속이 검증된 것은 아니다.

## 5. 시스템 Pod 검증

명령어:

```bat
kubectl get pods -A
```

실제 결과 요약:

| 네임스페이스 | 구성 요소 | 수량 | READY | STATUS | RESTARTS |
|---|---|---:|---|---|---:|
| `external-dns` | external-dns | 1 | 1/1 | Running | 0 |
| `kube-system` | aws-node | 2 | 2/2 | Running | 0 |
| `kube-system` | coredns | 2 | 1/1 | Running | 0 |
| `kube-system` | eks-node-monitoring-agent | 2 | 1/1 | Running | 0 |
| `kube-system` | eks-pod-identity-agent | 2 | 1/1 | Running | 0 |
| `kube-system` | kube-proxy | 2 | 1/1 | Running | 0 |
| `kube-system` | metrics-server | 2 | 1/1 | Running | 0 |
| **합계** | | **13** | **모두 Ready** | **모두 Running** | **0** |

### 구성 요소 이해

- **VPC CNI / aws-node:** Pod 네트워크 인터페이스 및 VPC IP 할당과 관련.
- **CoreDNS:** 클러스터 내부 Service 이름 해석.
- **kube-proxy:** Kubernetes Service 트래픽 전달 규칙 관리.
- **Pod Identity Agent:** Pod에 IAM 역할 자격 증명을 전달하는 데 사용.
- **Node Monitoring Agent:** 노드 수준의 상태·문제 감지 지원.
- **Metrics Server:** `kubectl top` 및 HPA 등의 리소스 지표 기반 기능에 사용.
- **ExternalDNS:** 설정과 IAM 권한이 충족될 때 Service/Ingress 정보에 따라 DNS 레코드 동기화.

### 검증의 범위

`13/13 Running`은 **기본 시스템 구성 요소의 실행 상태가 정상**임을 보여 준다. 다음은 별도 검증이 필요하다.

- 애플리케이션 Deployment 및 Service 동작
- 실제 Pod 네트워크 및 DNS 조회
- ExternalDNS의 Route 53 쓰기 권한
- LoadBalancer 생성 및 외부 HTTP 응답
- CloudWatch 로그·메트릭 수집

## 6. EKS, Metrics Server, CloudWatch 차이

| 서비스 | 주요 목적 | 오늘 확인 |
|---|---|---|
| `kubectl get nodes/pods` | Kubernetes 리소스 상태 확인 | **완료** |
| Metrics Server | CPU·메모리 리소스 지표 제공 | **Pod Running 확인** |
| EKS Node Monitoring Agent | 노드 건강 상태 감지 | **Pod Running 확인** |
| CloudWatch | AWS 로그·메트릭·경보·대시보드 | **별도 구축 필요** |
| Container Insights | EKS 컨테이너 관측성 | **설치·수집 미검증** |

**핵심 면접 포인트:** Metrics Server가 설치됐다고 CloudWatch Container Insights가 자동으로 완성되는 것은 아니다.

### CloudWatch 담당 후속 계획

1. 관측 범위 결정: 클러스터 / 노드 / Pod / 애플리케이션.
2. CloudWatch Observability EKS 애드온 또는 적합한 수집 에이전트 방식 선정.
3. Pod Identity 또는 IRSA를 통한 최소 권한 IAM 구성.
4. CloudWatch Logs 및 Container Insights 메트릭 수집 여부 확인.
5. CPU·메모리·노드 상태 등의 대시보드와 경보 작성.
6. 장애 시나리오와 경보 동작 검증, PPT용 캡처 확보.
7. 로그 보존 기간 및 과금 요소 점검.

> 위 내용은 **후속 설계 제안**이며, 오늘 실제 구축 완료한 항목이 아니다.

## 7. 수업 종료 후 삭제 및 비용 관리

### 7.1 확인된 현재 상태

- 사용자가 `terraform destroy`를 실행했고, 최종 승인 단계에서 **`Plan: 0 to add, 0 to change, 38 to destroy`**를 확인함.
- 대화에서는 `yes` 승인 여부 및 실제 삭제 완료 로그가 공유되지 않음.
- 콘솔에서 생성한 `KAEKSConsoleLab`은 Terraform state에 없으므로 **38개에 포함되지 않음**.

### 7.2 안전한 삭제 순서

**사전 확인**

- 팀원이 공유 인프라를 사용 중인지 확인.
- Aurora RDS 데이터가 필요하면 삭제 전 스냅샷 등 백업 확보.
- `terraform.tfstate` 백업 및 리소스 목록 확인.
- `terraform destroy` 승인 전 대상 리소스 목록 검토.

**콘솔 EKS 먼저 삭제**

1. `KAEKSNodeGroup` 삭제.
2. 노드 그룹 삭제 완료 확인.
3. `KAEKSConsoleLab` 삭제.
4. EKS가 생성한 네트워크 인터페이스, 보안 그룹, 로드 밸런서 등 잔여 리소스 확인.
5. 필요하면 EKS CLI로 클러스터 목록 재확인.

**그다음 Terraform HQ 정리**

```bat
cd /d C:\terraform\project
terraform plan -destroy
terraform destroy
```

`terraform destroy` 승인 시 Terraform 관리 리소스 삭제가 진행된다. **콘솔 EKS가 기존 VPC를 사용 중인 상태에서 HQ VPC부터 삭제하면 종속성 문제로 실패할 수 있다.**

### 7.3 주요 과금 요소

- EKS 클러스터 제어 영역
- EC2 Worker Node
- NAT Gateway (시간 및 데이터 처리)
- ALB/NLB
- Aurora RDS
- EBS 및 기타 저장소
- CloudWatch Logs/메트릭/보존

**중요:** `kubectl delete`로 Pod만 지워도 EKS 클러스터, 노드 그룹, NAT Gateway 등의 비용이 자동으로 사라지는 것은 아니다.

### 7.4 내일 재구축 시 주의

- Terraform HQ 인프라는 코드와 state 상태를 확인한 후 `terraform apply`로 다시 생성할 수 있다.
- **콘솔 EKS는 `terraform apply`로 재생성되지 않는다.** 다시 콘솔에서 만들거나 Terraform 코드로 옮겨야 한다.
- 기존 RDS 데이터, EIP, ALB DNS 이름, EC2 IP, EKS 노드 IP 등은 이전과 같다고 가정하지 않는다.
- IAM 역할은 삭제하지 않았다면 재사용 가능하다. 단, 정책·신뢰 관계가 적절한지 확인한다.

## 9. 트러블슈팅 및 실무 포인트

### Q1. `aws eks update-kubeconfig` 성공이면 EKS 전체가 정상인가?

아니다. kubeconfig에 접근 정보가 등록된 것뿐이다. `kubectl get nodes`, `kubectl get pods -A`, 애플리케이션 및 서비스 접근까지 단계별 확인해야 한다.

### Q2. `EXTERNAL-IP <none>`이면 문제가 있는가?

아니다. 오늘 노드는 Private Subnet에 배치되어 공인 IP가 없는 것이 설계 의도에 부합한다. 외부로 나가는 통신은 라우팅과 NAT Gateway 등의 구성에 좌우된다.

### Q3. 클러스터에는 Public/Private Subnet을 모두 선택했는데 노드는 왜 Private에만 있는가?

클러스터 네트워크 설정에서 지정하는 서브넷과 관리형 노드 그룹에서 EC2를 실제로 배치할 서브넷은 구분된다. 오늘 노드 그룹에는 Private Subnet 2개를 지정했다.

### Q4. `aws-node`가 `2/2`인 이유는?

해당 Pod에 준비되어야 할 컨테이너가 2개 있고 둘 다 Ready라는 뜻이다. `2/2`는 Pod가 2개라는 의미가 아니다. 실제 `aws-node` Pod는 노드당 1개씩 총 2개 확인됐다.

### Q5. ExternalDNS Pod가 Running인데 Route 53 권한은 왜 별도 확인해야 하나?

Pod의 실행 상태와 AWS API에 대한 IAM 권한은 다른 문제다. DNS 변경이 필요한 시점에 권한, ServiceAccount 연결, 로그, 실제 Route 53 레코드를 검증해야 한다.

### Q6. `terraform destroy`가 콘솔 EKS를 삭제하지 않는 이유는?

Terraform은 기본적으로 자신이 관리하는 state상의 리소스를 대상으로 동작하기 때문이다. 콘솔에서 만든 리소스는 자동 편입되지 않는다.

### Q7. Terraform으로 38개를 삭제하면 내일 완전히 같은 환경이 복원되는가?

코드로 재구축 가능한 구조는 복원할 수 있지만, 데이터·리소스 ID·일부 IP·DNS 이름·수동 콘솔 설정까지 동일하다는 보장은 없다. 데이터 백업과 선언적 코드 관리가 중요하다.

### Q8. Metrics Server와 CloudWatch는 어떻게 다른가?

Metrics Server는 Kubernetes 리소스 지표를 제공하며, CloudWatch는 AWS 전반의 로그·메트릭·경보·대시보드를 위한 서비스다. 목적과 데이터 수집 구성이 다르다.
