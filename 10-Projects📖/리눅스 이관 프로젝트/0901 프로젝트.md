# KAIST AI 대학 온프레미스 인프라 Linux 재구축 프로젝트

> 기존 Windows Server 기반으로 구현했던 **KAIST AI 대학 온프레미스 네트워크 프로젝트**의 서버 서비스 구성을 Linux 환경에서 다시 구현하며, 각 서비스의 동작 원리와 연계 구조를 복습하는 프로젝트이다.

## 1. 프로젝트 배경

기존 프로젝트에서는 KAIST AI 대학을 가정하여 네트워크를 VLAN 단위로 분리하고, 사용자/행정/연구 구역과 서버 구역을 구성하였다.

기존 VLAN 및 서버 역할은 다음과 같다.

|---|---|---|---|
| 11 | AI 컴퓨팅학과 | `10.1.11.0/24` | `10.1.11.254` |
| 12 | AI 시스템학과 | `10.1.12.0/24` | `10.1.12.254` |
| 13 | AI 미래학과 | `10.1.13.0/24` | `10.1.13.254` |

| 22 | 연구 | `10.1.22.0/24` | `10.1.22.254` |

| 102 | DHCP + FTP | `10.1.102.0/24` | `10.1.102.254` |
| 103 | Email | `10.1.103.0/24` | `10.1.103.254` |
| 104 | Intranet | `10.1.104.0/24` | `10.1.104.254` |

기존 프로젝트의 주요 서버 주소 예시는 다음과 같다.

- DNS 서버: `10.1.101.200`

```bash

cat /etc/resolv.conf
ping <gateway>
```

# 5. Day 1 - DNS 서버 구축 시작

## 5.1 BIND 설정 파일 확인

DNS 서버 구축을 시작하면서 `/etc/named.conf`의 주요 설정을 확인하였다.

사용한 명령어:

```bash
egrep 'listen-on|allow-query|directory' /etc/named.conf
```

확인 결과:

```conf
listen-on port 53 { 127.0.0.1; };
listen-on-v6 port 53 { ::1; };

directory "/var/named";

allow-query { localhost; };

managed-keys-directory "/var/named/dynamic";
geoip-directory "/usr/share/GeoIP";
```

---

# 6. named.conf 주요 설정 분석

## 6.1 `listen-on`

```conf
listen-on port 53 { 127.0.0.1; };
```

BIND가 IPv4에서 DNS 요청을 받을 주소를 지정한다.

현재 설정은 `127.0.0.1`, 즉 **Loopback 주소에서 들어오는 요청만 수신**하도록 되어 있다.

따라서 다른 Client가 해당 DNS 서버의 실제 NIC 주소로 질의를 보내야 하는 프로젝트 환경에서는 이 상태를 그대로 사용할 수 없다.

개념적으로는 프로젝트에서 사용할 서버 인터페이스 주소 또는 허용할 주소 범위를 고려하여 수정해야 한다.

> 무조건 `any`를 사용하는 것보다 프로젝트에서 실제로 필요한 인터페이스와 접근 범위를 명확히 지정하는 것이 좋다.

---

## 6.2 `listen-on-v6`

```conf
listen-on-v6 port 53 { ::1; };
```

IPv6의 Loopback 주소인 `::1`에서만 DNS 요청을 받도록 설정되어 있다.

이번 프로젝트에서 IPv4만 사용할 경우 IPv6 사용 여부와 정책에 맞게 설정한다.

---

## 6.3 `directory`

```conf
directory "/var/named";
```

BIND의 Zone 파일 등을 참조하는 기본 작업 디렉터리이다.

따라서 Zone 설정에서 상대 경로를 사용하는 경우 `/var/named`를 기준으로 파일을 찾게 된다.

예:

```conf
file "kaist.com.zone";
```

이라면 일반적으로 다음 파일을 의미한다.

```text
/var/named/kaist.com.zone
```

---

## 6.4 `allow-query`

```conf
allow-query { localhost; };
```

DNS 질의를 허용할 Client의 범위를 지정한다.

현재는 `localhost`만 허용하므로 **원격 Client가 DNS Query를 수행할 수 없다.**

프로젝트 내부망에서 DNS를 사용하려면 실제 내부 Network 범위를 고려하여 접근 정책을 구성해야 한다.

예시 개념:

```conf
allow-query {
    localhost;
    <internal-network>;
};
```

> 실제 값은 현재 Linux 프로젝트의 IP 설계가 확정된 뒤 적용한다.

# 7. 현재 초기 설정에서 발생하는 문제

현재 설정을 구조적으로 보면 다음과 같다.

```text
Client
  │
  │ DNS Query : UDP/TCP 53
  ▼
Linux DNS Server
  │
  X
listen-on = 127.0.0.1
allow-query = localhost
```

즉 두 단계에서 외부 Client의 DNS 사용이 제한될 수 있다.

### 문제 1 - Listen 주소

```conf
listen-on port 53 { 127.0.0.1; };
```

BIND가 Loopback 인터페이스에서만 요청을 기다린다.

### 문제 2 - Query 허용 범위

```conf
allow-query { localhost; };
```

원격 Client의 Query 자체가 허용되지 않는다.

따라서 Linux DNS 서버를 내부망에서 사용하려면 **Listen 대상과 Query 허용 정책을 함께 검토**해야 한다.

# 8. DNS 구성 시 예정 작업

## 8.1 Forward Zone

기존 프로젝트의 내부 Domain인 `kaist.com`을 기준으로 정방향 조회 영역을 구성한다.

목적:

```text
Hostname / Domain
       ↓
      DNS
       ↓
   IP Address
```

예:

```text
www.kaist.com
      ↓
10.x.x.x
```

---

## 8.2 Reverse Zone

역방향 조회가 필요한 경우 PTR Record를 구성한다.

```text
IP Address
    ↓
   DNS
    ↓
Hostname
```

---

## 8.3 주요 DNS Record

| Record | 역할 |
|---|---|
| `SOA` | Zone의 기본 관리 정보 |
| `NS` | 해당 Zone을 담당하는 DNS Server |
| `A` | Hostname → IPv4 |
| `PTR` | IPv4 → Hostname |
| `MX` | 해당 Domain의 Mail Server 지정 |

특히 Email 서비스를 구성할 때는 **MX Record와 Mail Server의 이름 해석 관계**를 함께 검증한다.

# 9. DNS 검증 계획

설정 후 바로 서비스 연동으로 넘어가지 않고 다음 순서로 검증한다.

## 설정 문법

```bash
named-checkconf
```

Zone 파일 작성 후:

```bash
named-checkzone <zone-name> <zone-file>
```

## Service

```bash
systemctl restart named
systemctl status named
```

## Port

```bash
ss -lntup | grep ':53'
```

DNS는 일반적인 Query에서 UDP 53을 사용하지만 TCP 53도 사용하므로 두 프로토콜 모두 확인한다.

## Firewall

```bash
firewall-cmd --list-all
```

필요한 경우 DNS 서비스를 허용한다.

```bash
firewall-cmd --permanent --add-service=dns
firewall-cmd --reload
```

## Query Test

```bash
dig <domain>
nslookup <domain>
```

가능하면 다음 순서로 테스트한다.

```text
DNS Server Local Query
        ↓
다른 Linux Server Query
        ↓
Client Query
```

이렇게 하면 문제가 발생했을 때 범위를 쉽게 좁힐 수 있다.

# 10. DNS Troubleshooting Flow

Client에서 DNS 질의가 실패한다면 무작정 설정 파일부터 수정하지 않고 아래 순서로 확인한다.

```text
① Client IP
      ↓
② Client Routing / Gateway
      ↓
③ DNS Server까지 Ping
      ↓
④ Client DNS 설정
      ↓
⑤ dig / nslookup
      ↓
⑥ named 상태
      ↓
⑦ 53/tcp + 53/udp Listen
      ↓
⑧ named.conf
      ↓
⑨ Zone File
      ↓
⑩ Firewall
      ↓
⑪ Log
```

주요 명령어:

```bash
ip addr
ip route
ping <dns-server-ip>

cat /etc/resolv.conf

dig <domain>
nslookup <domain>

systemctl status named
ss -lntup | grep ':53'

named-checkconf
named-checkzone <zone-name> <zone-file>

firewall-cmd --list-all

journalctl -u named
```

# 12. 오늘의 핵심 정리

오늘은 프로젝트 전체 서비스를 바로 구축하기보다 **DNS를 첫 번째 기반 서비스로 선정하고 BIND의 초기 설정 상태를 분석**하였다.

특히 다음 설정을 통해 기본 상태에서는 원격 Client의 DNS 사용이 제한될 수 있음을 확인하였다.

```conf
listen-on port 53 { 127.0.0.1; };
allow-query { localhost; };
```

이 과정에서 중요한 점은 설정값을 단순히 변경하는 것이 아니라,

```text
"왜 Client에서 접속할 수 없는가?"
        ↓
"서버가 어느 주소에서 Listen하는가?"
        ↓
"누구의 Query를 허용하는가?"
```

라는 관점으로 설정 파일을 해석하는 것이다.
