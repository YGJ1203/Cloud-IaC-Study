> **담당 영역:** Web + DNS\

# 2. BIND DNS 서버 구성

## 2.1 주요 패키지

``` bash
rpm -q bind
rpm -qi bind
rpm -ql bind
rpm -qc bind
```

DNS 서비스는 `named`를 사용한다.

``` bash
systemctl enable --now named
systemctl status named
```

프로세스와 포트도 확인할 수 있다.

``` bash
ps -ef | grep '[n]amed'
ss -lntup | grep ':53'
```

DNS는 TCP/UDP `53` 포트를 사용한다.

------------------------------------------------------------------------

## 2.2 `/etc/named.conf`

외부에서도 DNS 질의를 받을 수 있도록 실습 환경에서 다음과 같이
설정하였다.

``` conf
options {
    listen-on port 53 { any; };
    directory "/var/named";

    allow-query { any; };

    forwarders {
        168.126.63.1;
    };

    recursion yes;
    dnssec-validation yes;

    managed-keys-directory "/var/named/dynamic";
    geoip-directory "/usr/share/GeoIP";
    pid-file "/run/named/named.pid";
    session-keyfile "/run/named/session.key";
};
```

### 핵심

-   `listen-on port 53 { any; };`
    -   모든 IPv4 인터페이스에서 DNS 요청 수신
-   `allow-query { any; };`
    -   실습 환경에서 모든 클라이언트의 DNS 질의 허용
-   `forwarders { 168.126.63.1; };`
    -   내부 DNS가 모르는 외부 도메인은 KT DNS로 전달
-   `recursion yes;`
    -   재귀 질의 허용

> `forwarders`에 자기 자신의 IP인 `10.1.101.200`을 넣으면 외부 질의를
> 자기 자신에게 다시 전달하게 되므로 사용하지 않는다.

# 3. DNS Zone 구성

## 3.1 Zone 선언

`/etc/named.rfc1912.zones`

``` conf
zone "kaist.com" IN {
    type master;
    file "kaist.com.zone";
    allow-update { none; };
};

zone "1.10.in-addr.arpa" IN {
    type master;
    file "10.1.rev";
    allow-update { none; };
};
```

Zone 파일 생성:

``` bash
cd /var/named

cp -p named.empty kaist.com.zone
cp -p named.empty 10.1.rev
```

------------------------------------------------------------------------

## 3.2 정방향 Zone

`/var/named/kaist.com.zone`

``` dns
$TTL 3H
@   IN SOA  @ rname.invalid. (
                    0   ; serial
                    1D  ; refresh
                    1H  ; retry
                    1W  ; expire
                    3H ) ; minimum

kaist.com       IN NS   ns.kaist.com.
ns.kaist.com    IN A    10.1.101.200

kaist.com       IN MX 10 mail.kaist.com.

mail            IN A    10.1.103.200
www             IN A    10.1.101.200
ftp             IN A    10.1.102.200
intranet        IN A    10.1.104.200
```

검증:

``` bash
named-checkzone kaist.com kaist.com.zone
```

정상:

``` text
zone kaist.com/IN: loaded serial 0
OK
```

# 4. 역방향 DNS 구성

`10.1.0.0/16`을 기준으로 `1.10.in-addr.arpa` Zone을 사용하므로 PTR
레코드의 owner 작성에 주의한다.

`/var/named/10.1.rev`

``` dns
200.101 IN PTR ns.kaist.com.
200.101 IN PTR www.kaist.com.

200.102 IN PTR ftp.kaist.com.
200.103 IN PTR mail.kaist.com.
200.104 IN PTR intranet.kaist.com.
```

예를 들어:

``` text
10.1.101.200
```

은 역방향 DNS에서:

``` text
200.101.1.10.in-addr.arpa
```

형태가 되므로 Zone `1.10.in-addr.arpa` 내부의 owner는:

``` text
200.101
```

이 된다.

검증:

``` bash
named-checkzone 1.10.in-addr.arpa 10.1.rev
systemctl restart named
```

테스트:

``` bash
nslookup www.kaist.com 10.1.101.200
nslookup 10.1.101.200 10.1.101.200
nslookup 10.1.102.200 10.1.101.200
nslookup 10.1.103.200 10.1.101.200
nslookup 10.1.104.200 10.1.101.200
```

# 5. 내부 DNS와 외부 Forwarder의 관계

각 Linux 서버의 DNS 주소는:

``` text

```

으로 설정하였다.

구조는 다음과 같다.

``` text
Linux Client / Server
        |
        | DNS Query
        v
10.1.101.200
BIND DNS Server
        |
        +-- kaist.com ?
        |      |
        |      +--> Local Zone에서 직접 응답
        |
        +-- google.com ?
               |
               +--> 168.126.63.1 Forwarder
```

따라서 내부 서버에서는:

``` bash

```

실행 시 다음 DNS 서버를 사용해야 한다.

``` text
Server:  10.1.101.200
Address: 10.1.101.200#53
```

# 6. DNS 트러블슈팅 - 실제 공개 kaist.com으로 접속된 문제

## 증상

Web 서버 자체에서:

``` bash
curl http://localhost
curl http://10.1.101.200
```

은 정상적으로 내부 Apache 페이지가 출력되었다.

하지만:

``` bash
curl http://www.kaist.com
```

을 실행하면 예상하지 않은 외부 페이지가 출력되었다.

## 원인 확인

``` bash
nslookup www.kaist.com
```

확인 결과 DNS 서버가:

``` text
168.126.63.1
```

이었으며 `www.kaist.com`이 인터넷상의 실제 공개 IP로 해석되고 있었다.

## 해결

CentOS NetworkManager GUI에서 DNS를:

``` text
10.1.101.200
```

으로 변경하고:

``` bash
systemctl restart NetworkManager
```

이후 다시 확인하였다.

``` bash
nslookup www.kaist.com
```

정상 결과:

``` text
Server:  10.1.101.200
Name:    www.kaist.com
Address: 10.1.101.200
```

이후:

``` bash
curl http://www.kaist.com
```

으로 내부 Apache 페이지에 정상 접속하였다.

### 핵심 교훈

> IP 직접 접속은 정상인데 도메인 접속만 이상하다면 Web 서버보다 먼저 DNS
> Resolver 설정을 확인한다.


# 11. Directory Indexing 보안 설정

Apache의 `Options Indexes`가 활성화되어 있고 기본 문서가 없으면 디렉터리
내부 파일 목록이 노출될 수 있다.

따라서 VirtualHost의 `<Directory>` 설정에서:

``` apache
Options -Indexes
```

를 사용한다.

예:

``` apache
<Directory "/var/www/www1">
    Options -Indexes
    Require all granted
</Directory>
```

### 효과

``` text
index.html 존재
    → index.html 출력

index.html 없음
    → 디렉터리 파일 목록 노출 방지
```

`Options -Indexes`는 불필요한 파일/디렉터리 정보 노출을 줄이기 위한
설정이다.

# 12. 포트 기반 VirtualHost 구성

기존 네트워크 설계에서 학과별 VLAN은 다음과 같다.

  학과              VLAN Subnet             Web Port
  --------------- ------ ---------------- ----------
  AI 컴퓨팅학과       11 `10.1.11.0/24`       `8081`
  AI 시스템학과       12 `10.1.12.0/24`       `8082`
  AI 미래학과         13 `10.1.13.0/24`       `8083`

Web 서버 자체는 VLAN 101의:

``` text
10.1.101.200
```

을 사용한다.

즉 Web 서버 하나에서 포트를 구분하여 학과별 Web 콘텐츠를 제공한다.

``` text
10.1.101.200:8081 → AI 컴퓨팅학과
10.1.101.200:8082 → AI 시스템학과
10.1.101.200:8083 → AI 미래학과
```

> VLAN 번호 자체가 Apache VirtualHost를 자동으로 선택하는 것은 아니다.
> 이번 구성에서는 각 학과에 대응하는 포트 번호로 Web 서비스를 구분한다.

# 14. 학과별 DocumentRoot

디렉터리 구조는 관리자가 목적에 맞게 결정할 수 있다.

이번 프로젝트에서는 포트별 구조를 명확하게 표현하기 위해:

``` text
/var/www/
├── html/       # 기본 HTTP :80
├── www1/       # :8081 - AI 컴퓨팅학과
├── www2/       # :8082 - AI 시스템학과
└── www3/       # :8083 - AI 미래학과
```

형태로 구성하였다.

생성:

``` bash
mkdir -p /var/www/www1
mkdir -p /var/www/www2
mkdir -p /var/www/www3
```

------------------------------------------------------------------------

# 15. VirtualHost 설정 예시

`/etc/httpd/conf.d/vhost.conf`

``` apache
Listen 8081
Listen 8082
Listen 8083

<VirtualHost 10.1.101.200:8081>
    DocumentRoot /var/www/www1

    <Directory "/var/www/www1">
        Options -Indexes
        Require all granted
    </Directory>
</VirtualHost>

<VirtualHost 10.1.101.200:8082>
    DocumentRoot /var/www/www2

    <Directory "/var/www/www2">
        Options -Indexes
        Require all granted
    </Directory>
</VirtualHost>

<VirtualHost 10.1.101.200:8083>
    DocumentRoot /var/www/www3

    <Directory "/var/www/www3">
        Options -Indexes
        Require all granted
    </Directory>
</VirtualHost>
```

### `VirtualHost` IP의 의미

``` apache
<VirtualHost 10.1.101.200:8081>
```

에서:

-   `10.1.101.200` → Web 서버가 실제 보유한 IP
-   `8081` → 해당 VirtualHost가 사용하는 TCP 포트

따라서 학과 VLAN의 주소를 `<VirtualHost>`에 넣는 것이 아니다.

# 17. 트러블슈팅 - DocumentRoot가 존재하지 않음

처음 VirtualHost 설정 후:

``` bash

```

결과:

``` text
AH00112: Warning: DocumentRoot [/var/www/www1] does not exist
AH00112: Warning: DocumentRoot [/var/www/www2] does not exist
AH00112: Warning: DocumentRoot [/var/www/www3] does not exist
Syntax OK
```

## 원인

`vhost.conf`에는 DocumentRoot를 지정했지만 실제 디렉터리를 아직 생성하지
않았다.

## 해결

``` bash
mkdir -p /var/www/www1

mkdir -p /var/www/www3
```

이후 다시:

``` bash
apachectl configtest
```

을 실행하여 확인한다.

### 포인트

`Syntax OK`는 Apache 설정 파일의 문법이 정상이라는 의미이며, 별도로
출력된 `AH00112` 경고는 지정한 DocumentRoot 경로가 존재하지 않는다는
의미이다.

# 19. `mod_ssl` 관련 트러블슈팅

HTTPS 구성을 검토하는 과정에서 `mod_ssl`을 설치한 후 Apache 재시작이
실패하였다.

오류:

``` text
AH00526: Syntax error on line 85 of /etc/httpd/conf.d/ssl.conf:
SSLCertificateFile: file '/etc/pki/tls/certs/localhost.crt' does not exist...
```

확인 과정에서 SSL 인증서/키 파일이 정상적인 인증서로 준비되지 않은
상태임을 확인하였다.

하지만 프로젝트 요구사항을 다시 확인한 결과:

-   HTTPS 서비스 구축 자체는 필수 요구사항으로 명시되지 않음
-   Firewall에서 TCP 443 허용과 HTTPS 서비스 구축은 서로 다른 개념

따라서 불필요한 `mod_ssl`을 제거하고 기존 HTTP 서비스를 복구하였다.

``` bash
yum -y remove mod_ssl

apachectl configtest
systemctl restart httpd
systemctl status httpd
```

### 핵심 교훈

> 방화벽에서 특정 포트를 허용하는 것과 해당 포트에서 실제 Application
> Service가 Listen하는 것은 별개의 문제이다.

예를 들어 TCP `443`을 firewalld에서 허용하더라도 HTTPS 서비스를 반드시
구축했다는 의미는 아니다.

# 20. CGI / MariaDB 범위 판단

수업에서는 CGI 및 MariaDB 연동을 학습했지만 현재 프로젝트의 Web 서버
구축 요구사항에는 DB 생성, 사용자 테이블 생성 또는 Web-DB 연동이
명시되어 있지 않다.

따라서 현재 프로젝트에서는 불필요하게 범위를 확장하지 않고 다음 항목을
중심으로 구성한다.

``` text
Apache HTTP Server
        +
BIND DNS
        +
한글/영문 페이지
        +
학과별 Port-based VirtualHost
        +
firewalld
        +
Client 접속 테스트
```

CGI, MariaDB 연동 및 HTTPS는 명확한 추가 요구사항이 있을 경우 확장한다.
