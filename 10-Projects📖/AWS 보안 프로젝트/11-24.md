## 1. 실습 개요

### 1.1 실습 목적

FortiGate NGFW의 DoS Policy를 활용하여 네트워크 계층 및 전송 계층에서 발생하는 Flood 공격을 탐지하고 대응하는 과정을 검증한다.

주요 실습 내용은 다음과 같다.

1. FortiGate 네트워크 인터페이스 및 방화벽 정책 확인
2. Kali Linux에서 CentOS로 정상 통신 검증
3. FortiGate DoS Policy 설정
4. ICMP Flood, TCP SYN Flood, UDP Flood 탐지 기능 활성화
5. Kali Linux를 이용한 공격 트래픽 발생
6. FortiGate Anomaly 로그 분석
7. Wireshark를 이용한 대상 서버 패킷 관찰
8. FortiGate CLI 스니퍼를 이용한 패킷 경로 확인
9. CentOS CPU 및 메모리 사용률 확인
10. PPT 증빙 자료 구성

### 1.2 실습에서 확인하려는 핵심 사항

- 정상적인 네트워크 통신이 가능한가?
- 공격 트래픽이 FortiGate를 통과하는가?
- FortiGate가 Flood 공격을 탐지하는가?
- 임계값 초과 시 어떤 대응 동작이 발생하는가?
- 공격 대상 서버에서 실제로 어떤 패킷이 관찰되는가?
- 정상 통신과 이상 트래픽의 처리 결과가 어떻게 다른가?

## 5. Kali Linux 공격 실습

### 5.1 실습 대상

```text
192.168.20.200
```

FortiGate의 정책 임계값을 변경하더라도 공격 대상 CentOS의 IP 주소는 변경되지 않는다.

### 5.2 TCP SYN Flood

실습에서 사용한 공격 형태:

```bash
hping3 --interface eth0 --syn -p 80 \
192.168.20.200 --flood --rand-source
```

옵션 설명:

| 옵션 | 설명 |
|---|---|
| --interface eth0 | 패킷 전송 인터페이스 |
| --syn | TCP SYN 플래그 설정 |
| -p 80 | 목적지 TCP 80번 포트 |
| --flood | 최대 속도로 패킷 전송 |
| --rand-source | 출발지 IP 무작위 위조 |

### 5.3 UDP Flood

```bash
hping3 --interface eth0 --udp -p 53 \
192.168.20.200 --flood --rand-source
```

- UDP 패킷 전송
- 목적지 포트 53
- 무작위 출발지 IP 사용

참고로 이전 UTM 실습에서 `eth1`을 사용한 명령어도 있었으나, 해당 인터페이스는 방화벽 우회 경로가 될 수 있으므로 이번 FortiGate 경유 실습에서는 `eth0`을 사용하였다.

### 5.4 ICMP Flood

```bash
hping3 --interface eth0 --icmp \
192.168.20.200 --flood --rand-source
```

- ICMP Echo Request 전송
- 최대 속도 전송
- 출발지 IP 무작위 위조

### 5.5 실습 안전 사항

위 명령어는 당시 실습 기록용이다.

`--flood`와 `--rand-source`는 높은 부하와 출발지 IP 위조를 발생시킬 수 있으므로 격리된 허가 실습망 외에서는 실행하지 않는다.

정량적 검증에는 전송 패킷 수와 간격을 제한한 테스트를 우선 사용한다.

또한 출발지 IP를 위조한 Flood 테스트에서 Kali에 표시되는 `100% packet loss`는 FortiGate의 실제 차단률을 의미하지 않는다.

## 6. ICMP Flood 제한 테스트

### 6.1 첫 번째 테스트

```bash
sudo hping3 --icmp -c 100 -i u10000 \
192.168.20.200
```

설정:

- 패킷 수: 100
- 전송 간격: 10,000μs
- 이론적 전송률: 약 100pps

결과:

```text
100 packets transmitted
100 packets received
0% packet loss

round-trip min/avg/max = 0.5/5.5/12.0 ms
```

FortiGate Anomaly 로그:

```text
결과 없음
```

### 6.2 두 번째 테스트

- 패킷 수: 300
- 이론적 전송률: 약 200pps

결과:

```text
300 packets transmitted
300 packets received
0% packet loss

round-trip min/avg/max = 0.4/8.6/1002.7 ms
```

Anomaly 로그:

```text
결과 없음
```

**분석**

임계값보다 낮은 전송률의 테스트에서는 ICMP 통신이 정상적으로 수행되었다.

다만 최대 RTT가 약 1초까지 증가한 구간이 있었으며, 이것만으로 방화벽 또는 서버의 성능 저하를 확정할 수는 없다.

### 6.3 세 번째 테스트

```bash
sudo hping3 --icmp -c 300 -i u3000 \
192.168.20.200
```

설정:

- 패킷 수: 300
- 전송 간격: 3,000μs
- 이론적 전송률: 약 333pps

결과:

```text
300 packets transmitted
250 packets received
17% packet loss

round-trip min/avg/max = 0.4/9.0/1006.0 ms
```

FortiGate에서 `icmp_flood` 탐지 로그가 발생하였다.

**분석**

- 임계값을 초과하는 테스트에서 탐지가 발생하였다.
- 약 16.7%의 ICMP 응답 손실이 관찰되었다.
- 단, 손실된 응답이 모두 방화벽 차단으로 발생했다고 단정할 수는 없다.

## 7. ICMP Flood 임계값 강화 및 재검증

### 7.1 ICMP 임계값 변경

```text
기존 Threshold: 250
변경 Threshold: 150
```

FortiGate CLI에서 설정이 유지되고 있음을 확인하였다.

```text
status enable
threshold 150
```

### 7.2 짧은 테스트에서 탐지 로그 미발생

```bash
sudo hping3 --icmp -c 300 -i u3000 \
192.168.20.200
```

이 테스트에서는 FortiGate 스니퍼에서 일부 ICMP 패킷이 정상적으로 전달되는 모습이 관찰되었으며, 새로운 Anomaly 로그는 발생하지 않았다.

가능한 원인:

- 테스트 지속 시간이 짧았음
- FortiGate의 탐지 집계 주기
- 실제 관측 패킷률과 이론적 전송률의 차이

이 결과만으로 DoS Policy가 비활성화됐다고 판단할 수는 없다.

### 7.3 1,000패킷 테스트

```bash
sudo hping3 --icmp -c 1000 -i u3000 \
192.168.20.200
```

설정:

- 패킷 수: 1,000
- 전송 간격: 3,000μs
- 이론적 전송률: 약 333pps
- 예상 전송 시간: 약 3초

실제 결과:

```text
1000 packets transmitted
150 packets received
85% packet loss

round-trip min/avg/max = 0.6/11.6/1004.4 ms
```

### 7.4 결과 분석

| 항목 | 결과 |
|---|---:|
| 전송 패킷 | 1000 |
| 응답 수신 | 150 |
| 응답 미수신 | 850 |
| 응답 손실률 | 85% |
| ICMP 임계값 | 150 |

이번 테스트에서는 FortiGate에서 ICMP Flood 탐지 로그도 확인하였다.

**중요한 해석**

85%는 Kali가 수신하지 못한 ICMP 응답의 비율이다.

이를 FortiGate가 정확히 850개의 공격 패킷을 차단했다는 의미로 해석해서는 안 된다.

## 8. FortiGate Anomaly 로그 분석

### 8.1 로그 확인 경로

```text
Log & Report
    └── Anomaly
```

### 8.2 확인된 공격 유형

| 공격 유형 | 탐지 이름 | 심각도 | 동작 |
|---|---|---|---|
| ICMP Flood | icmp_flood | Critical | clear_session |
| TCP SYN Flood | tcp_syn_flood | Critical | clear_session |
| UDP Flood | udp_flood | Critical | clear_session |

세 공격 유형 모두 FortiGate에서 탐지되었다.

### 8.3 ICMP Flood 임계값 초과 메시지

실습에서 확인한 로그 예시:

```text
anomaly: icmp_flood, 151 > threshold 150,
repeats 144590 times
```

의미:

- `icmp_flood`: ICMP Flood 탐지
- `151 > threshold 150`: 임계값 초과
- `repeats 144590 times`: 이상 이벤트 반복 집계
- `clear_session`: 세션 정리 동작

### 8.4 반복 카운트 주의사항

FortiGate 로그의 `count` 또는 `repeats` 값을 실제 차단 패킷 수와 동일하게 해석해서는 안 된다.

예를 들어:

```text
repeats 144590 times
```

이는 해당 이상 이벤트의 반복 기록을 의미하며, 정확히 144,590개 패킷이 차단됐다는 증거는 아니다.

### 8.5 출발지 IP 위조

`--rand-source` 옵션을 사용하면 실제 Kali 주소와 다른 출발지 IP가 FortiGate 로그에 기록될 수 있다.

실제 Kali IP:

```text
192.168.2.50
```

따라서 로그에 나타난 무작위 출발지 주소를 실제 외부 공격자의 IP라고 판단하면 안 된다.

## 9. FortiGate CLI 패킷 스니퍼

### 9.1 실습 목적

FortiGate의 입구와 출구에서 ICMP 패킷을 관찰하여 정상 통신 경로와 이상 트래픽 전달 여부를 확인한다.

### 9.2 port1 패킷 캡처

```bash
diagnose sniffer packet port1 \
'icmp and dst host 192.168.20.200' 4 20
```

Kali에서 정상 Ping 실행:

```bash
ping -c 4 192.168.20.200
```

관찰 결과:

```text
port1 -- 192.168.2.50 -> 192.168.20.200:
icmp: echo request
```

Echo Request 4개가 FortiGate port1에서 확인되었다.

### 9.3 port2 패킷 캡처

```bash
diagnose sniffer packet port2 \
'icmp and dst host 192.168.20.200' 4 20
```

다시 정상 Ping 4회를 실행하였다.

관찰 결과:

```text
port2 -- 192.168.2.50 -> 192.168.20.200:
icmp: echo request
```

Echo Request 4개가 port2에서 확인되었다.

### 9.4 정상 통신 경로 검증

```text
Kali Linux
   |
   | ICMP Echo Request
   v
FortiGate port1
   |
   | 정상 패킷 전달
   v
FortiGate port2
   |
   v
CentOS
```

정상 Ping 테스트에서 port1과 port2 모두 패킷이 관찰되었다.

단, 두 인터페이스의 확인은 각각 별도의 Ping 실행으로 수행하였다.

### 9.5 통합 스니퍼

```bash
diagnose sniffer packet any \
'icmp and dst host 192.168.20.200' 4 100
```

출력 예시:

```text
port1 in 192.168.2.50 -> 192.168.20.200:
icmp: echo request

port2 out 192.168.2.50 -> 192.168.20.200:
icmp: echo request
```

이를 통해 일부 ICMP 패킷이 FortiGate에 유입된 뒤 CentOS 방향으로 전달되는 모습을 확인하였다.

### 9.6 중요한 학습 내용

FortiGate DoS Policy가 활성화되어 있다고 해서 모든 ICMP 패킷이 차단되는 것은 아니다.

정상 ICMP 통신은 허용될 수 있으며, 이상 트래픽 탐지는 임계값 및 장비의 집계 조건에 따라 동작한다.

또한 스니퍼에서 관찰된 일부 패킷만으로 전체 공격 트래픽의 통과율을 계산할 수는 없다.

- ICMP Echo Reply 4개
- 정상 Ping 통신 확인

이를 통해 CentOS의 Wireshark가 ICMP 패킷을 정상적으로 관찰할 수 있음을 확인하였다.

### 10.2 ICMP Flood 테스트

공격 테스트 중 Wireshark에서 ICMP 패킷이 표시되지 않은 화면을 확인하였다.

해당 시점에 Wireshark 캡처가 진행 중이었음도 확인하였다.

FortiGate에서는 별도로 `icmp_flood` 탐지 및 `clear_session` 로그가 발생하였다.

**해석**

FortiGate가 이상 트래픽의 전달을 제한했을 가능성을 뒷받침한다.

그러나 해당 화면만으로 모든 공격 패킷이 100% 차단됐다고 확정할 수는 없다.

### 10.3 TCP SYN Flood 테스트

CentOS Wireshark에서 TCP 관련 패킷을 확인하였다.

일부 화면에는 다음 주소 간 HTTPS/SSL 통신이 표시되었다.

```text
192.168.20.100 <-> 192.168.20.1
```

이는 FortiGate 관리 통신으로 보이며, Kali에서 CentOS로 전송한 TCP SYN Flood 패킷과 구분해야 한다.

### 10.4 UDP Flood 테스트

UDP Flood 테스트 중 CentOS Wireshark에서 UDP 패킷이 표시되지 않은 화면을 확보하였다.

FortiGate에서는 `udp_flood` 탐지 로그가 확인되었다.

다만 캡처에 UDP 패킷이 보이지 않았다는 사실만으로 전체 UDP 공격 패킷의 완전 차단을 확정할 수는 없다.

## 12. 실습 중 발생한 문제와 해결 과정

### 12.1 ICMP Flood 로그가 발생하지 않는 문제

**현상**

100패킷 및 300패킷 제한 테스트에서 FortiGate Anomaly 로그가 발생하지 않았다.

**확인 사항**

- DoS Policy 활성화 상태
- ICMP Flood 탐지 활성화 상태
- Threshold 설정
- Kali와 CentOS의 정상 통신
- FortiGate 경유 네트워크 경로

**조치**

전송 속도와 지속 시간을 구분하여 제한된 테스트를 진행하였다.

**결과**

1,000패킷 테스트에서 ICMP Flood 탐지 로그가 발생하였다.

**학습 내용**

이론적 전송률이 임계값을 초과한다고 해서 항상 탐지 로그가 발생하는 것은 아니다.

실제 관측 트래픽과 탐지 집계 방식, 테스트 지속 시간을 함께 고려해야 한다.

### 12.2 Wireshark에서 공격 패킷이 표시되지 않는 문제

**현상**

ICMP Flood 공격 중 CentOS Wireshark에 ICMP 패킷이 표시되지 않았다.

**확인 사항**

1. Wireshark 캡처 진행 상태 확인
2. 정상 Ping 실행
3. Echo Request 및 Echo Reply 확인
4. 공격 대상 IP 확인
5. FortiGate Anomaly 로그 확인

**결과**

정상 Ping은 Wireshark에 표시되었으며, 공격 테스트에서는 ICMP 패킷 미표시 화면이 관찰되었다.

**학습 내용**

정상 통신이 캡처된다는 사실은 캡처 기능 검증에 도움이 된다.

그러나 서로 다른 테스트의 결과를 비교할 때는 캡처 인터페이스, 필터, 시간대 및 패킷 손실 여부를 함께 확인해야 한다.

### 12.3 공격 차단률 해석 문제

**현상**

Kali에서 높은 패킷 손실률이 발생하였다.

**주의사항**

```text
Packet Loss ≠ Firewall Drop Rate
```

예를 들어:

```text
1000 transmitted
150 received
85% packet loss
```

이는 850개의 응답을 수신하지 못했다는 뜻이다.

850개의 공격 패킷이 모두 FortiGate에서 폐기됐다는 의미는 아니다.

정확한 차단률을 확인하려면 동일 시간대의 방화벽 입출력 패킷과 대상 서버 수신 패킷을 비교해야 한다.

## 13. Sophos UTM과 FortiGate NGFW 실습 비교

| 구분 | Sophos UTM | FortiGate NGFW |
|---|---|---|
| 방어 기능 | IPS | DoS Policy |
| ICMP Flood | 탐지 로그 확인 | 탐지 로그 확인 |
| TCP SYN Flood | 탐지 로그 확인 | 탐지 로그 확인 |
| UDP Flood | 탐지 로그 확인 | 탐지 로그 확인 |
| 로그 예시 | SYN/UDP/ICMP Flood detected | tcp_syn_flood/udp_flood/icmp_flood |
| 대응 분석 | IPS 로그 중심 | Anomaly 및 세션 제어 로그 중심 |
| 패킷 분석 | Wireshark | Wireshark 및 FortiGate CLI 스니퍼 |

### 13.1 공통점

- Kali Linux에서 공격 트래픽 발생
- CentOS 서버를 공격 대상으로 설정
- 네트워크 보안 장비에서 이상 트래픽 탐지
- 탐지 로그 및 서버 측 관찰 결과 확보

### 13.2 차이점

Sophos UTM은 IPS 탐지 로그를 중심으로 분석하였다.

FortiGate는 DoS Policy의 임계값을 직접 조정하고, Anomaly 로그와 인터페이스별 패킷 흐름을 추가로 분석하였다.

### 13.3 PPT 자료 재활용 시 주의사항

공격 원리, 명령어 설명 및 공통 시나리오는 재활용할 수 있다.

하지만 UTM 설정 전 화면을 NGFW 설정 전 실제 측정 결과로 표시해서는 안 된다.

각 장비의 실제 탐지 로그와 대응 결과는 구분하여 기록한다.

## 16. 오늘의 핵심 개념 정리

### Q1. DoS Policy의 Threshold란?

특정 유형의 트래픽이 설정된 기준을 초과하는지 판단하기 위한 임계값이다.

실제 동작은 공격 유형, 장비의 집계 방식 및 트래픽 특성에 따라 달라진다.

### Q2. Threshold를 낮추면 무조건 좋은가?

아니다.

더 낮은 트래픽 수준에서 탐지할 수 있지만, 정상적인 트래픽까지 차단할 위험도 증가한다.

### Q3. clear_session이란?

FortiGate가 관련 세션을 정리하는 대응 동작이다.

이 로그만으로 모든 공격 패킷의 차단이 입증되는 것은 아니다.

### Q4. Wireshark에서 공격 패킷이 보이지 않으면 완전 차단인가?

반드시 그렇지는 않다.

방화벽 차단이 원인일 수 있지만 캡처 인터페이스, 필터, 캡처 누락, 테스트 시점도 확인해야 한다.

### Q5. 정상 Ping은 되는데 Flood는 탐지될 수 있는가?

가능하다.

정상적인 ICMP 통신과 임계값을 초과하는 비정상 ICMP 트래픽은 서로 다른 처리 결과를 보일 수 있다.

### Q6. Kali에서 85% Packet Loss가 발생하면 방화벽이 85% 차단한 것인가?

아니다.

응답 손실률과 방화벽의 실제 패킷 차단률은 다른 지표이다.

### Q7. --rand-source 옵션의 의미는?

출발지 IP 주소를 무작위로 위조한다.

따라서 공격 대상의 응답이 실제 Kali로 돌아오지 않을 수 있으며, 로그의 출발지 IP도 Kali의 실제 주소와 다르게 나타날 수 있다.

### Q8. IDS와 IPS, NGFW의 차이는?

- IDS: 이상 트래픽 탐지 및 경고
- IPS: 이상 트래픽 탐지 및 차단
- NGFW: 상태 기반 방화벽 기능과 애플리케이션 제어, 침입 방지 등 다양한 보안 기능을 통합한 방화벽

이번 실습에서는 Sophos UTM의 IPS와 FortiGate NGFW의 DoS Policy를 활용하였다.
