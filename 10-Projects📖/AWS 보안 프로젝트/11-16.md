### 2.2 지난 점검에서 확인한 사항

- `KA-HQ-NACL`을 Public1/2 서브넷에 연결하고 통신을 확인했다.
- HTTP/HTTPS 요청 및 SSH 접속이 가능했다.
- 한 차례 ICMP 요청 4회 중 응답 0회를 관찰했다.
- ALB Healthy 4/4 등 서비스 상태를 함께 확인했다.
- Private 서브넷의 NACL 변경과 RDS 접근제어 변경은 아직 별도 검토가 필요하다.

### 2.3 오늘 ICMP 재검증

KAWeb에서 실행한 명령:

```bash
ping -c 4 -W 2 8.8.8.8
```

오늘 공유한 출력 중 하나:

```text
4 packets transmitted, 4 received, 0% packet loss
rtt min/avg/max ... 약 26.6ms
```

관찰 사항:

1. 앞선 테스트에서는 ping이 실패한 사례가 있었다.
2. 오늘 후속 테스트에서는 동일 목적지로 **4/4 응답, 손실률 0%**가 확인됐다.
3. AWS 콘솔에서 NACL 규칙의 프로토콜 선택 항목에 ICMP가 보이지 않았고, ICMP 타입·코드 입력란도 표시되지 않았다는 점을 확인했다.
4. 따라서 당시 의도한 ICMP 차단 규칙이 실제로 생성·적용됐는지 **확정할 수 없다**.

**중요:** ping 성공만으로 'NACL 전체가 작동하지 않는다'고 단정할 수 없으며, ping 실패만으로 'NACL이 ICMP를 차단했다'고 단정할 수도 없다. 실제 연결 서브넷, 인바운드·아웃바운드 규칙, 규칙 우선순위, 보안 그룹, 라우팅 및 테스트 시점의 상태를 함께 확인해야 한다.

### 2.4 복습 개념

- **Security Group(SG):** 인스턴스·네트워크 인터페이스 등에 적용되는 상태 저장(Stateful) 접근 제어. 허용 규칙을 기반으로 동작한다.
- **Network ACL(NACL):** 서브넷에 연결되는 비상태 저장(Stateless) 접근 제어. 허용·거부 규칙을 번호 순서대로 평가한다.
- **ICMP:** 오류 알림과 네트워크 진단에 사용하는 프로토콜. Echo Request/Reply가 ping에 사용된다.
- **상태 비저장 NACL:** 요청과 응답의 흐름을 각각 검토해야 한다.
- **보안 검증:** 설정 화면과 실제 패킷 흐름을 함께 확인해야 결과의 신뢰도가 높다.

### 3.3 PDF의 설정과 진단 결과를 구분

- PPT에서 SSH를 광범위하게 허용하는 예시가 있더라도 보안 진단에서는 **관리자 접근 출발지 제한** 여부를 점검한다.
- PPT의 NACL 아웃바운드 전체 허용은 실습 구성 예시이며, 보안 적정성까지 자동으로 보장하지 않는다.
- WAF에서 악성 요청이 `403 Forbidden`으로 차단되는 것은 **웹 공격 차단 증빙**이다. 이것만으로 IAM·SG·NACL·암호화 등 전체 보안 진단을 통과했다고 볼 수는 없다.
- PDF 119페이지의 진단 결과 작성 공간은 별도 보완이 필요한 상태로 검토했다.

## 4. 담당 영역: AWS 가상 리소스 관리 보안 진단

PDF 117페이지의 **가상 리소스 관리**를 중심으로 점검한다. 자료에서 다루는 핵심 대상은 다음과 같다.

| 진단 대상 | 핵심 확인 사항 | 선행 의존성 |
|---|---|---|
| Security Group | `0.0.0.0/0` 등 광범위 허용, 불필요한 인바운드·아웃바운드 규칙 | SG 최종 설정 |
| NACL | 규칙의 허용·거부 범위, 우선순위, 실제 서브넷 연결 | NACL 최종 설정 |
| Route Table | Public/Private 서브넷의 경로 적정성 | 네트워크 구축 |
| Internet Gateway | 연결 대상 및 외부 노출 경로 | VPC 구축 |
| NAT Gateway | Private 서브넷의 외부 통신 경로 | NAT·라우팅 구축 |
| S3 | 버킷 공개 접근 및 접근 정책 | 해당 버킷 존재 시 |
| RDS | DB 서브넷 구성과 접근 범위 | RDS 구축 |
| ELB/ALB | 연결 리소스·대상 그룹·노출 상태 | ALB 구축 |

**점검 결과 표현 예시:** 양호 / 취약 / 해당 없음 / 확인 필요

점검 항목의 정확한 번호·판정 기준은 PDF 117페이지 원본을 기준으로 최종 체크리스트에 옮겨 적고, 임의로 항목을 추가해 원본 기준과 혼동하지 않는다.

## 5. 선행 작업과 담당 진단의 의존 관계

```text
본사·지사 AWS 인프라 구축
  ├─ VPC / 서브넷 / 라우팅 / IGW / NAT
  ├─ EC2 / ALB / Auto Scaling
  └─ Aurora RDS / S3(사용 시)
          ↓
보안 설정 확정
  ├─ Public / Private SG
  ├─ NACL 및 서브넷 연결
  └─ AWS WAF (웹 공격 차단 시연)
          ↓
가상 리소스 보안 진단
  ├─ 설정·연결 상태 확인
  ├─ 보안 기준에 따른 판정
  ├─ 취약 설정 개선 요청
  └─ 재점검 및 증빙 정리
```

- **지금 가능한 일:** 기존 리소스 인벤토리, 진단 항목 정리, IAM/일부 운영 항목과 현재 리소스의 사전 점검.
- **구축 확정 후 할 일:** SG·NACL·라우팅·RDS·ALB에 대한 최종 판정과 증빙 수집.
- **팀원 협의 필요:** 공유 환경의 SG/NACL 변경, 웹 서비스 접근 경로 변경, 공격 시연용 설정.

## 7. 주의사항 및 배운 점

1. **PPT를 그대로 복제하는 것과 보안 진단은 다르다.** 구축 자료는 실습 참고로 사용하고, 진단은 기준에 맞춰 독립적으로 평가한다.
2. **NACL은 Stateless다.** 응답 트래픽과 임시 포트 범위를 함께 고려한다.
3. **핑 결과만으로 원인을 확정하지 않는다.** 연결 대상과 실제 규칙이 적용됐는지부터 확인한다.
4. **공유 AWS 환경의 보안 설정은 임의로 변경하지 않는다.** 기존 서비스 정상 동작과 팀원 작업을 우선 고려한다.
5. **비용 관리:** EC2, NAT Gateway, ALB, Aurora, WAF 등은 생성·실행·유지 상태에 따라 비용이 발생할 수 있다. 실습 전후 자원 현황과 과금 여부를 확인한다.
6. **증빙은 설정 + 검증 + 판정의 세 요소를 갖춘다.** 캡처만 모으는 것이 아니라 왜 양호/취약인지 설명한다.
