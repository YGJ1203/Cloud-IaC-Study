## 2.2 AWS Security Group

Security Group은 AWS 리소스 수준에서 네트워크 트래픽을 제어하는 가상 방화벽이다.

특징:

- Stateful 방식
- 허용 규칙 기반
- 인바운드 및 아웃바운드 정책 설정
- 허용된 연결의 응답 트래픽은 연결 상태를 기준으로 처리
- EC2, ALB, RDS 등 지원 리소스에 적용

예시:

```text
Inbound
TCP 80    0.0.0.0/0
TCP 443   0.0.0.0/0
TCP 22    관리자 IP/32
```

위 설정은 개념 설명용 예시이며, 실제 프로젝트의 최종 정책과 동일하다는 의미는 아니다.

### 핵심 개념

Security Group은 Stateful이므로 허용된 요청에 대한 응답 트래픽을 별도의 반대 방향 규칙 없이 처리할 수 있다.

단, 새로운 연결을 시작하는 트래픽은 해당 방향의 규칙에 따라 허용되어야 한다.

## 2.3 Network ACL

NACL은 서브넷 수준에서 네트워크 트래픽을 제어하는 보안 기능이다.

특징:

- Stateless 방식
- Allow / Deny 규칙 지원
- 규칙 번호가 낮은 순서부터 평가
- 인바운드 및 아웃바운드 각각 설정
- 서브넷 단위로 적용

### SG와 NACL 비교

| 항목 | Security Group | NACL |
|---|---|---|
| 적용 범위 | 리소스/ENI 수준 | 서브넷 수준 |
| 상태 추적 | Stateful | Stateless |
| 허용 규칙 | 지원 | 지원 |
| 거부 규칙 | 명시적 Deny 미지원 | 지원 |
| 규칙 평가 | 허용 규칙 종합 평가 | 번호순 평가 |
| 응답 트래픽 | 연결 상태 추적 | 별도 규칙 필요 |

### 주의사항

NACL에서는 응답 패킷을 위한 임시 포트(Ephemeral Port) 범위도 고려해야 한다.

특히 웹 서비스의 TCP 연결은 요청 방향과 응답 방향의 포트 구성이 다를 수 있다.

따라서 단순히 TCP 80 또는 443만 허용하면 정상 통신이 실패할 수 있다.

## 2.4 AWS 통신 검증

이번 주 학습에서는 기존 AWS 환경의 ICMP 통신과 네트워크 정책 적용 결과를 검토하였다.

대표적인 검증 명령어:

```bash
ping -c 4 8.8.8.8
```

```bash
curl -I https://www.google.com
```

확인 항목:

- ICMP Echo Request 송신 여부
- Echo Reply 수신 여부
- 패킷 손실률
- 외부 HTTPS 통신
- SG 및 NACL 적용에 따른 통신 변화

주의:

ICMP 통신 성공은 네트워크 연결성에 대한 일부 증거일 뿐이며, 웹 서비스 정상 동작이나 전체 보안성을 보장하지 않는다.

# 3. AWS 보안 진단 PPT 작성

## 3.1 결과보고서 작성

이번 주에는 AWS 보안 진단 결과를 바탕으로 PPT 내용을 검토하고 수정하였다.

주요 분류:

1. 계정 관리
2. 가상 리소스 관리
3. 운영 관리

기존 진단 자료의 28개 항목을 기준으로 관련 설정과 증빙을 검토하였다.

## 3.2 PPT 작성 시 고려사항

### 진단 항목과 증빙의 일치

각 슬라이드에서 다음 요소를 연결해야 한다.

```text
진단 항목
   ↓
AWS 설정 확인
   ↓
콘솔 화면 캡처
   ↓
진단 결과
   ↓
설명 및 개선사항
```

### 결과보고서의 정확성

- 실제 확인한 설정만 결과에 반영
- 스크린샷과 설명의 내용 일치
- 수행하지 않은 조치를 수행했다고 작성하지 않기
- 보안 설정 확인과 취약점 개선을 구분
- 진단 결과와 자체 평가를 간결하게 작성

## 3.3 실제 검토 내용

이번 주에는 다음과 같은 PPT 편집 작업을 진행하였다.

- 계정 퍼블릭 액세스 차단 관련 항목 검토
- 가상 리소스 관리와 운영 관리의 구분
- PPT 소제목 및 페이지 구성 검토
- AWS 콘솔 증빙 이미지에 맞춘 설명 수정
- 자체 평가 문구 간결화

### 배운 점

보안 진단 보고서는 설정을 나열하는 문서가 아니라, 해당 설정이 보안 기준을 충족하는지 증명하는 문서이다.

따라서 진단 근거와 결과를 일치시키는 것이 중요하다.


위 그림은 논리적 구성도이며, Snort의 실제 패킷 관찰 경로는 미러링 또는 배치 방식에 따라 달라진다.

# 6. FortiGate NGFW 실습

## 6.1 인터페이스 구성

확인된 설정:

```text
port1
IP: 192.168.2.100/24

port2
IP: 192.168.20.100/24

Gateway
192.168.2.254
```

내부 네트워크와 외부 네트워크 사이에 FortiGate를 배치하였다.

## 6.2 NAT 설정

실습에서 사용한 NAT 관련 명칭:

```text
MyNAT
```

NAT는 내부 사설 IP 주소를 외부 통신에 적합한 주소로 변환하는 기능이다.

일반적인 Source NAT 흐름:

```text
내부 PC
192.168.20.200
       |
       v
FortiGate
Source NAT
       |
       v
외부 네트워크
```

### NAT의 목적

- 사설 네트워크의 외부 통신 지원
- 주소 변환
- 내부 및 외부 주소 체계 연결

주의:

NAT 자체가 공격을 탐지하거나 모든 비인가 접근을 차단하는 보안 기능은 아니다.

접근제어는 별도의 방화벽 정책을 통해 구현해야 한다.

## 6.3 외부 통신 확인

CentOS에서 외부 주소로 ICMP 통신을 수행하였다.

```bash
ping -c 4 8.8.8.8
```

확인된 결과:

```text
4 packets transmitted
4 received
0% packet loss
```

### 결과 해석

- CentOS에서 외부 주소로 ICMP 통신 성공
- FortiGate를 경유하는 통신 경로의 연결성 확인
- 네트워크 라우팅 및 정책이 해당 테스트 트래픽을 허용하는 상태

단, ICMP 성공만으로 모든 TCP/UDP 서비스가 정상 동작한다고 판단할 수 없다.

# 7. Snort IDS 실습

## 7.1 Snort 개요

Snort는 네트워크 트래픽을 분석하고 공격 패턴을 탐지하는 IDS/IPS 소프트웨어이다.

IDS 모드에서는 공격으로 의심되는 패킷을 탐지하고 경고를 생성한다.

기본 구조:

```text
네트워크 패킷
      |
      v
Snort 패킷 분석
      |
      v
탐지 룰 비교
      |
      v
경고 및 로그 생성
```

## 7.2 확인된 Snort 환경

```text
IP: 192.168.20.101
Version: 2.9.7.0
```

## 7.3 Snort 설정 검사

```bash
snort -T
```

실습에서는 설정 검사가 성공한 것을 확인하였다.

### -T 옵션

Snort의 설정 파일과 룰을 검사하는 테스트 옵션이다.

다만 실제 서비스 환경에서는 사용하는 설정 파일을 명시하는 것이 더 정확하다.

예시:

```bash
snort -T -c /etc/snort/snort.conf
```

### 설정 검사와 실제 탐지의 차이

```text
설정 검사 성공
    ≠
실제 공격 탐지 성공
```

Snort 설정이 정상이라고 해서 모든 트래픽을 관찰하거나 공격을 탐지하는 것은 아니다.

실제 탐지 확인에는 다음 요소가 필요하다.

- 올바른 인터페이스
- 실제 패킷 수신
- 활성화된 탐지 룰
- 룰과 일치하는 테스트 트래픽
- 탐지 로그 확인

## 7.4 Snort 룰 기본 구조

예시:

```snort
alert icmp any any -> any any (msg:"ICMP Echo Request Detected"; itype:8; sid:3001001; rev:1;)
```

구성 요소:

| 항목 | 의미 |
|---|---|
| alert | 경고 생성 |
| icmp | 프로토콜 |
| any any | 출발지 IP 및 포트 |
| -> | 트래픽 방향 |
| msg | 경고 메시지 |
| itype:8 | ICMP Echo Request |
| sid | 룰 고유 식별자 |
| rev | 룰 개정 번호 |

위 룰은 학습용 예시이며, 이번 주 실제 등록된 룰이라고 단정하지 않는다.

# 8. Kali Linux 및 hping3 패킷 생성

## 8.1 hping3 개요

hping3는 TCP/IP 패킷을 생성하고 전송하는 도구이다.

실습에서는 제한된 수의 패킷을 전송하여 네트워크 동작을 분석하였다.

주요 활용:

- TCP SYN 패킷 생성
- UDP 패킷 생성
- ICMP 통신 분석
- 방화벽 정책 검증
- tcpdump 캡처 결과 확인

## 8.2 TCP SYN 테스트

이번 주 기록된 명령어:

```bash
hping3 -S -p 80 -c 20 -i u100000 <LAB_TARGET_IP>
```

옵션:

| 옵션 | 의미 |
|---|---|
| -S | TCP SYN 플래그 |
| -p 80 | 목적지 포트 80 |
| -c 20 | 20개 패킷 전송 |
| -i u100000 | 패킷 간격 100,000μs(0.1초) |

### 관찰 결과

기록상 20개의 테스트 패킷에 대한 송수신 결과가 확인되었다.

### TCP SYN의 의미

TCP 3-Way Handshake:

```text
Client                  Server
   |                       |
   |-------- SYN --------->|
   |<----- SYN/ACK --------|
   |-------- ACK --------->|
   |                       |
```

SYN 패킷은 TCP 연결을 시작하기 위해 전송된다.

SYN 패킷이 관찰되었다는 사실만으로 완전한 TCP 연결이 성립했다고 볼 수 없다.

## 8.3 UDP 테스트

기록된 명령어:

```bash
hping3 --udp -p 9999 -c 20 <LAB_TARGET_IP>
```

옵션:

- --udp: UDP 패킷 전송
- -p 9999: 목적지 포트 9999
- -c 20: 총 20개 전송

### 관찰 결과

- UDP 테스트 패킷 20개 캡처
- ICMP 오류 응답 7개 관찰

### 결과 해석

UDP는 TCP와 달리 연결 설정 과정이 없는 비연결형 프로토콜이다.

대상 포트에서 서비스가 수신 대기하지 않는 경우 ICMP Destination Unreachable 오류가 발생할 수 있다.

단, 실제 ICMP 오류의 세부 Type/Code를 확인해야 정확한 원인을 판단할 수 있다.

## 8.4 TCP와 UDP 비교

| 구분 | TCP | UDP |
|---|---|---|
| 연결 방식 | 연결 지향 | 비연결형 |
| 연결 설정 | 3-Way Handshake | 없음 |
| 전달 보장 | 재전송 등 지원 | 자체 보장 없음 |
| 순서 보장 | 지원 | 자체 보장 없음 |
| 대표 서비스 | HTTP, HTTPS, SSH | DNS, DHCP, 실시간 스트리밍 등 |

# 9. tcpdump 패킷 분석

## 9.1 tcpdump 개요

tcpdump는 네트워크 인터페이스에서 패킷을 캡처하고 분석하는 명령어 기반 도구이다.

활용 목적:

- 통신 여부 확인
- 출발지/목적지 IP 분석
- 프로토콜 확인
- 포트 번호 분석
- ICMP 요청/응답 확인
- 비정상 패킷 추적

## 9.2 기본 명령어

```bash
tcpdump -nni eth0
```

옵션:

| 옵션 | 설명 |
|---|---|
| -n | 주소 및 포트의 이름 변환 방지 |
| -nn | 주소와 포트 번호를 숫자로 표시 |
| -i eth0 | eth0 인터페이스 지정 |

ICMP 필터:

```bash
tcpdump -nni eth0 icmp
```

TCP 필터:

```bash
tcpdump -nni eth0 tcp
```

UDP 필터:

```bash
tcpdump -nni eth0 udp
```

특정 호스트 필터:

```bash
tcpdump -nni eth0 host 192.168.20.200
```

## 9.3 이번 주 ICMP 패킷 분석

실제 사용한 명령어:

```bash
tcpdump -nni eth0 'icmp and src host 192.168.20.200 and dst host 192.168.20.200'
```

관찰된 출력 일부:

```text
IP 192.168.20.200 > 192.168.20.200:
ICMP echo request, id 9228, seq 0

IP 192.168.20.200 > 192.168.20.200:
ICMP echo request, id 9228, seq 256
```

### 분석

출발지 IP:

```text
192.168.20.200
```

목적지 IP:

```text
192.168.20.200
```

프로토콜:

```text
ICMP
```

메시지:

```text
Echo Request
```

특이사항:

출발지 IP와 목적지 IP가 동일하다.

### 중요 해석

일반적인 원격 Ping 테스트와 다른 형태의 패킷이 관찰되었다.

가능한 원인:

- 의도적으로 출발지 주소를 지정한 테스트
- IP Spoofing
- 패킷 생성 도구의 설정
- 로컬 또는 특수한 네트워크 처리

캡처 결과만으로 원인을 확정할 수는 없다.

특히 tcpdump에서 패킷이 관찰되었다는 사실은 실제 목적지까지 패킷이 전달되었다는 의미가 아니다.

## 9.4 ICMP 기본 개념

| ICMP Type | 의미 |
|---|---|
| 0 | Echo Reply |
| 3 | Destination Unreachable |
| 8 | Echo Request |
| 11 | Time Exceeded |

### Ping 동작

```text
Host A                   Host B
   |                        |
   |--- Echo Request (8) -->|
   |<--- Echo Reply (0) ----|
   |                        |
```

정상적인 Ping 응답을 확인하려면 Echo Request와 Echo Reply를 함께 분석해야 한다.

# 10. 패킷 캡처와 보안 탐지의 차이

이번 주 가장 중요한 개념 중 하나이다.

## 10.1 패킷 생성

hping3로 테스트 패킷을 전송한다.

```text
Kali Linux
    |
    v
hping3
    |
    v
TCP / UDP / ICMP 패킷
```

## 10.2 패킷 관찰

tcpdump로 패킷을 캡처한다.

```text
네트워크 트래픽
      |
      v
tcpdump
      |
      v
패킷 정보 확인
```

## 10.3 공격 탐지

Snort 룰과 일치하는 트래픽이 관찰되면 경고를 생성한다.

```text
네트워크 트래픽
      |
      v
Snort IDS
      |
      v
룰 비교
      |
      v
Alert 생성
```

## 10.4 트래픽 차단

FortiGate 방화벽 정책으로 허용되지 않은 트래픽을 차단한다.

```text
외부 트래픽
      |
      v
FortiGate NGFW
      |
      v
방화벽 정책 확인
      |
      +---- Allow → 전달
      |
      +---- Deny  → 차단
```

### 핵심 정리

**패킷 생성 ≠ 패킷 캡처 ≠ 공격 탐지 ≠ 공격 차단**

각 단계는 별도의 검증이 필요하다.

| 단계 | 도구 | 검증 내용 |
|---|---|---|
| 생성 | hping3 | 테스트 패킷 송신 |
| 캡처 | tcpdump | 인터페이스에서 패킷 관찰 |
| 탐지 | Snort | 룰 일치 및 경고 확인 |
| 차단 | FortiGate | 정책에 따른 전달/차단 확인 |

# 12. 보안 면접 대비 핵심 질문

## Q1. Security Group과 NACL의 차이점은?

Security Group은 리소스 수준에서 적용되는 Stateful 방화벽이며, NACL은 서브넷 수준에서 적용되는 Stateless 접근제어 기능이다.

## Q2. Stateful과 Stateless의 차이는?

Stateful은 연결 상태를 추적하여 응답 트래픽을 처리하고, Stateless는 패킷을 독립적으로 평가하므로 양방향 정책을 고려해야 한다.

## Q3. IDS와 IPS의 차이는?

IDS는 공격을 탐지하고 경고하며, IPS는 인라인으로 배치되어 탐지한 공격 트래픽을 차단할 수 있다.

## Q4. FortiGate와 Snort의 역할은?

FortiGate는 방화벽 정책 및 NAT 등을 통해 네트워크 트래픽을 제어하고, Snort는 패킷을 분석하여 룰에 일치하는 공격 패턴을 탐지한다.

## Q5. TCP 3-Way Handshake란?

TCP 연결을 수립하기 위해 SYN, SYN/ACK, ACK 패킷을 교환하는 과정이다.

## Q6. UDP는 왜 ICMP 오류 응답을 받을 수 있는가?

UDP는 연결 설정 과정이 없으며, 목적지 포트에서 수신 가능한 서비스가 없을 경우 ICMP Destination Unreachable 등이 반환될 수 있다.

## Q7. tcpdump에서 -nn 옵션을 사용하는 이유는?

IP 주소와 포트 번호를 이름으로 변환하지 않고 숫자로 출력하여 패킷 분석을 명확하게 하기 위해서이다.

## Q8. ICMP Echo Request와 Echo Reply의 Type은?

- Echo Request: Type 8
- Echo Reply: Type 0

## Q9. Snort의 sid란?

Snort 룰을 식별하기 위한 고유 식별 번호이다.

## Q10. 패킷 캡처에 성공했다면 공격 탐지도 성공한 것인가?

아니다.

패킷 캡처는 네트워크 인터페이스에서 패킷을 관찰했다는 의미이며, 공격 탐지는 IDS의 탐지 룰과 일치하여 경고가 생성되었는지 별도로 확인해야 한다.
