# 3. AWS Security Group 구성

## 3.1 Security Group 개념

Security Group은 EC2, ALB, RDS 등의 네트워크 인터페이스에 적용하는 가상 방화벽이다.

특징:

- Stateful 방식
- 허용(Allow) 규칙 기반
- 인바운드 및 아웃바운드 규칙 관리
- 허용된 요청에 대한 응답 트래픽은 자동 허용
- 명시적인 Deny 규칙을 설정하지 않음

## 3.2 신규 Security Group

이번 실습에서 다음 SG를 생성하였다.

| SG 이름 | 주요 인바운드 정책 |
|---|---|
| KA-HQ-Public1-SG | HTTP, HTTPS, 내부 ICMP |
| KA-HQ-Public2-SG | HTTP, HTTPS, 내부 ICMP |
| KA-HQ-Private-SG | 내부 HTTP, 내부 ICMP |

### Public1 / Public2 SG

```text
HTTP  TCP 80   0.0.0.0/0
HTTPS TCP 443  0.0.0.0/0
ICMP           10.0.0.0/16
```

### Private SG

```text
HTTP TCP 80    10.0.0.0/16
ICMP           10.0.0.0/16
```

### 주의사항

신규 SG 3개는 생성되었으나, 기존 EC2 및 기타 서비스에 실제로 연결하는 작업은 아직 진행하지 않았다.

따라서 이번 HTTP/HTTPS/SSH/ICMP 검증 결과를 신규 SG의 효과로 해석해서는 안 된다.

기존 EC2에는 KASecugroup이 연결되어 있다.

# 4. AWS Network ACL 구성

## 4.1 NACL 개념

Network ACL은 VPC 서브넷 단위로 적용되는 네트워크 접근 제어 목록이다.

주요 특징:

- Stateless 방식
- Allow 및 Deny 규칙 지원
- 서브넷에 연결하여 적용
- 인바운드와 아웃바운드를 별도로 평가
- 규칙 번호가 작은 순서대로 검사
- 처음 일치하는 규칙 적용
- 어떤 규칙에도 일치하지 않으면 기본 Deny

## 4.2 SG와 NACL 비교

| 구분 | Security Group | Network ACL |
|---|---|---|
| 적용 범위 | 네트워크 인터페이스 | 서브넷 |
| 동작 방식 | Stateful | Stateless |
| Allow | 지원 | 지원 |
| Deny | 명시적 규칙 미지원 | 지원 |
| 응답 트래픽 | 자동 허용 | 별도 규칙 필요 |
| 규칙 처리 | 허용 규칙 종합 평가 | 번호순 첫 일치 규칙 |

## 5.2 인바운드 규칙

| Rule | Type | Protocol | Port | Source | Action |
|---|---|---|---|---|---|
| 100 | HTTP | TCP | 80 | 0.0.0.0/0 | ALLOW |
| 110 | HTTPS | TCP | 443 | 0.0.0.0/0 | ALLOW |
| 120 | SSH | TCP | 22 | 10.0.0.0/16 | ALLOW |
| 125 | SSH | TCP | 22 | 13.209.1.56/29 | ALLOW |
| 130 | Custom TCP | TCP | 1024-65535 | 0.0.0.0/0 | ALLOW |
| 140 | Custom UDP | UDP | 1024-65535 | 0.0.0.0/0 | ALLOW |
| * | All Traffic | ALL | ALL | 0.0.0.0/0 | DENY |

### 주요 규칙 해설

**Rule 100 / 110**

외부 HTTP 및 HTTPS 통신 허용

**Rule 120**

HQ VPC 내부에서 SSH 접근 허용

**Rule 125**

서울 리전 EC2 Instance Connect 접속에 필요한 SSH 출발지 대역 허용

실습 당시 확인된 SSH 접속 출발지:

```text
13.209.1.60
```

**Rule 130**

TCP 1024-65535 범위 허용

일반적인 TCP 응답 트래픽에 필요한 임시 포트 범위를 포함한다.

MySQL의 3306 포트도 해당 범위에 포함된다.

단, 모든 서비스가 이 범위를 필요로 하는 것은 아니며, 실제 운영에서는 출발지와 포트를 더 세밀하게 제한해야 한다.

**Rule 140**

UDP 1024-65535 범위 허용

**기본 Deny**

허용 규칙에 일치하지 않는 인바운드 트래픽 차단

특히 이번 설정에는 ICMP 인바운드 허용 규칙이 없다.

## 5.3 아웃바운드 규칙

| Rule | Protocol | Port | Destination | Action |
|---|---|---|---|---|
| 100 | ALL | ALL | 0.0.0.0/0 | ALLOW |
| * | ALL | ALL | 0.0.0.0/0 | DENY |

아웃바운드 전체 허용 정책을 적용하였다.

### 주의

아웃바운드 전체 허용은 모든 응답 트래픽을 자동으로 허용한다는 뜻이 아니다.

NACL은 Stateless이므로 돌아오는 인바운드 트래픽도 별도의 인바운드 규칙에 의해 평가된다.

# 11. ICMP 통신 검증

## 11.1 테스트 명령어


## 11.3 변경 전후 비교

| 항목 | NACL 적용 전 | NACL 적용 후 |
|---|---|---|
| 전송 패킷 | 4 | 4 |
| 수신 패킷 | 4 | 0 |
| 패킷 손실률 | 0% | 100% |

## 11.4 ICMP 응답이 사라진 이유

현재 NACL 정책:

```text
Outbound:
ALL ALLOW

Inbound:
ICMP 허용 규칙 없음
```

예상 통신 흐름:

```text
KAWeb EC2
10.0.2.37
    |
    | ICMP Echo Request
    v
8.8.8.8
    |
    | ICMP Echo Reply
    v
KA-HQ-NACL
    |
    X 인바운드 ICMP 허용 규칙 없음
    |
    X EC2 응답 수신 실패
```

### 핵심 개념

NACL은 Stateless이다.

따라서 아웃바운드 ICMP 요청을 허용하더라도 인바운드 Echo Reply가 자동으로 허용되지 않는다.

이번 결과는 NACL의 인바운드 ICMP 차단 정책과 일치한다.

단, 패킷 손실만으로 실제 차단 지점을 완전히 입증한 것은 아니다.

추가적인 패킷 캡처 또는 관련 로그를 통해 더 정확한 원인 분석이 가능하다.

6. 서브넷 및 가용 영역별 실제 리소스 배치

### 주의할 점

현재 신규 NACL의 TCP 1024-65535 허용 규칙에는 MySQL 3306이 포함된다.

그러나 해당 규칙이 존재한다는 사실만으로 DB 연결 성공을 보장할 수는 없다.

또한 운영 보안 정책으로는 지나치게 광범위한 허용 규칙이므로 향후 최소 권한 원칙에 따라 개선해야 한다.

# 17. AWS 과금 구조 정리

## 17.1 이번 실습에서 생성한 무료 리소스

| 리소스 | 자체 유지 요금 |
|---|---|
| Security Group | 없음 |
| Security Group 규칙 | 없음 |
| Network ACL | 없음 |
| NACL 규칙 | 없음 |
| NACL 서브넷 연결 | 없음 |

따라서 이번 채팅에서 생성한 SG 및 NACL은 삭제하지 않고 유지해도 해당 설정 자체에 대한 별도 유지 요금은 발생하지 않는다.

## 17.2 기존 AWS 인프라의 과금 가능 항목

| 리소스 | 과금 여부 |
|---|---|
| EC2 | 실행 시간 등 과금 |
| ALB | 사용 시간 및 LCU 과금 |
| Aurora RDS | 인스턴스 및 스토리지 등 과금 |
| NAT Gateway | 사용 시간 및 데이터 처리량 과금 |
| Public IPv4 | 주소 사용에 따른 과금 가능 |
| 일반 VPC / Subnet | 자체 유지 요금 없음 |

### 핵심 정리

```text
Security Group:
FREE

Network ACL:
FREE

EC2:
BILLABLE

ALB:
BILLABLE

Aurora:
BILLABLE

NAT Gateway:
BILLABLE
```

AWS 콘솔을 닫거나 SSH 터미널에서 exit을 실행해도 EC2, ALB, RDS 등의 리소스가 자동으로 중지되지는 않는다.

따라서 기존 인프라의 과금 관리는 별도로 수행해야 한다.

# 18. 오늘 실습에서 배운 핵심 개념

## 18.1 Stateful vs Stateless

### Stateful

Security Group은 연결 상태를 추적한다.

허용된 요청에 대한 응답 트래픽을 자동으로 허용한다.

### Stateless

Network ACL은 연결 상태를 추적하지 않는다.

인바운드와 아웃바운드 트래픽을 독립적으로 검사한다.

## 18.2 Ephemeral Port

TCP/UDP 통신에서 클라이언트가 임시로 사용하는 포트이다.

NACL은 Stateless이므로 응답 트래픽이 사용하는 포트 범위도 고려해야 한다.

## 18.3 최소 권한 원칙

필요한 서비스, 포트, 출발지에 대해서만 접근을 허용해야 한다.

현재의 광범위한 TCP/UDP 허용 정책은 실습 목적에는 활용할 수 있지만 최종 운영 정책에서는 재검토가 필요하다.

## 18.4 단계적 정책 적용

한 번에 모든 서브넷에 NACL을 적용하면 장애 발생 시 원인을 추적하기 어려워진다.

따라서 다음 절차를 따른다.

```text
기존 상태 확인
    ↓
서브넷 1개에 정책 적용
    ↓
서비스 정상 여부 확인
    ↓
통신 검증
    ↓
문제 발생 시 기존 NACL로 복구
    ↓
다음 서브넷 적용
```

## 18.5 Terraform 관리 주의사항

기존 HQ 인프라는 Terraform으로 구축되었다.

반면 이번 NACL 연결 변경은 AWS 콘솔에서 직접 수행하였다.

따라서 이후 Terraform plan/apply 실행 시 코드에서 관리하는 리소스와 콘솔의 실제 설정 사이에 차이가 발생할 수 있다.

다음 Terraform 작업 전에는 plan 결과를 확인하고, 필요하다면 NACL 연결 설정을 Terraform 코드에도 반영해야 한다.

# 22. 실습 소감 및 결론

오늘 실습에서는 기존 Terraform 기반 KAIST HQ 인프라에 AWS 콘솔을 통해 네트워크 보안 정책을 구성하였다.

특히 신규 NACL 적용 전후의 실제 네트워크 통신을 비교하여 다음을 확인하였다.

1. HTTP와 HTTPS 통신은 정상적으로 유지되었다.
2. EC2 Instance Connect를 통한 신규 SSH 접속에 성공하였다.
3. ICMP 통신은 기존 0%에서 100% 패킷 손실로 변화하였다.
4. 퍼블릭 ALB는 NACL 변경 후에도 4/4 Healthy를 유지하였다.
5. 프라이빗 ALB와 Aurora DB의 변경 전 정상 상태를 확보하였다.
6. NACL을 한 번에 적용하지 않고 서브넷별로 점진적으로 적용하였다.

이를 통해 AWS 네트워크 보안 정책의 구성뿐 아니라 실제 서비스에 미치는 영향을 검증하는 과정의 중요성을 학습하였다.

**최종 결론:**

퍼블릭 서브넷 2개에 KA-HQ-NACL 적용을 완료하였으며, 주요 웹 서비스와 SSH 통신은 정상적으로 유지되었다.

프라이빗 서브넷 적용은 실제 DB 연결 경로를 확인한 이후 진행한다.
