## 3. Network ACL 진단

### 3.1 KANACL 인바운드 규칙

| 규칙 번호 | 프로토콜 | 포트 | 소스 | 작업 |
|---|---|---|---|---|
| 100 | HTTP | 80 | 0.0.0.0/0 | Allow |
| 110 | HTTPS | 443 | 0.0.0.0/0 | Allow |
| 120 | SSH | 22 | 0.0.0.0/0 | Allow |
| 130 | TCP | 1024-65535 | 0.0.0.0/0 | Allow |
| 140 | UDP | 1024-65535 | 0.0.0.0/0 | Allow |
| * | 모든 트래픽 | 전체 | 0.0.0.0/0 | Deny |

### 3.2 아웃바운드 규칙

- 규칙 100: 모든 트래픽 허용
- 기본 규칙 (*): 모든 트래픽 거부

### 3.3 서브넷 연결

KANACL에 총 4개의 서브넷 연결 확인.

- KAPublic1Subnet
- KAPublic2Subnet
- KAPrivate1Subnet
- KAPrivate2Subnet

### 진단 결과

- NACL 생성 및 서브넷 연결 확인
- 인바운드와 아웃바운드 규칙 확인
- SSH 및 임시 포트의 광범위한 허용 정책 확인
- 최소 권한 원칙에 따른 추가 검토 필요

> 참고: NACL은 Stateless 방식이므로 응답 트래픽에 필요한 포트도 별도로 허용해야 한다.

## 4. 라우팅 테이블 진단

### 4.1 Public Routing

대상:

- KAPublic1Routing
- KAPublic2Routing

라우팅 구성:

```text
10.0.0.0/16 → local
0.0.0.0/0   → Internet Gateway
```

두 라우팅 테이블 모두 활성 상태 확인.

### 4.2 Private Routing

대상:

- KAPrivate1Routing
- KAPrivate2Routing

라우팅 구성:

```text
10.0.0.0/16 → local
0.0.0.0/0   → NAT Gateway
```

- Private1 → KANatGW1
- Private2 → KANatGW2

### 진단 결과

- Public Subnet의 인터넷 게이트웨이 경로 확인
- Private Subnet의 NAT Gateway 경로 확인
- 라우팅 테이블과 서브넷 연결 확인
- 기본 라우팅 경로 모두 Active 상태

## 6. Security Group 진단

### 6.1 Public Security Group

리소스: `KAPublicSecugroup`

인바운드 규칙:

| 유형 | 포트 | 소스 |
|---|---|---|
| HTTP | 80 | 0.0.0.0/0 |
| HTTPS | 443 | 0.0.0.0/0 |
| SSH | 22 | 0.0.0.0/0 |
| ICMP | 전체 | 0.0.0.0/0 |

아웃바운드:

- 모든 트래픽 허용

### 6.2 Private Security Group

리소스: `KAPrivateSecugroup`

인바운드 규칙:

| 유형 | 포트 | 소스 |
|---|---|---|
| HTTP | 80 | KAPublicSecugroup |
| HTTPS | 443 | KAPublicSecugroup |
| SSH | 22 | KAPublicSecugroup |
| ICMP | 전체 | KAPublicSecugroup |

아웃바운드:

- 모든 트래픽 허용

### 핵심 학습 내용

Security Group의 소스에는 CIDR뿐 아니라 다른 Security Group을 지정할 수 있다.

```text
Public SG → Private SG
```

이는 Public SG가 연결된 리소스에서 발생하는 해당 트래픽을 허용하는 설정이다.

단, Security Group 참조 자체가 모든 외부 접근을 차단하거나 특정 애플리케이션 경로만 허용한다는 의미는 아니다.

### 진단 결과

- Public / Private SG 구분 확인
- Private SG의 Public SG 참조 확인
- Public SG의 SSH 및 ICMP 전체 허용 확인
- 광범위한 아웃바운드 정책에 대한 추가 검토 필요

## 7. Application Load Balancer 진단

리소스: `KAPublicALB`

- 가용 영역: ap-northeast-2a / 2c
- 리스너: HTTP 80
- 대상 그룹: KAPrivateTargetGroup

## 9. EBS 볼륨 암호화 진단

### 9.1 볼륨 구성

EC2에 연결되는 EBS 볼륨 총 6개 확인.

- 볼륨 유형: standard
- 각 볼륨 크기: 8 GiB
- 총 용량: 48 GiB
- 배치 가용 영역: ap-northeast-2a / 2c

### 9.2 암호화 상태

6개 볼륨 모두 다음 상태 확인.

```text
암호화: 암호화되지 않음
KMS 키 ID: -
KMS 키 별칭: -
```

### 진단 결과

**EBS 암호화 미적용 상태 확인**

운영 관리 항목 4.1의 개선 대상으로 기록.

기존 암호화되지 않은 볼륨은 단순히 암호화 옵션만 변경할 수 없으므로, 일반적으로 스냅샷 복사 및 암호화된 볼륨 생성 등의 절차가 필요하다.

## 10. CloudFront 보안 설정 진단

### 10.1 배포 구성

리소스: `KACDN`

대체 도메인:

```text
cdn.example7777.shop
```

- 사용자 정의 SSL 인증서 연결 확인
- 지원 HTTP 버전: HTTP/2, HTTP/1.1, HTTP/1.0
- 보안 정책: TLSv1.2_2021

### 10.2 오리진 구성

- 오리진 유형: Elastic Load Balancing
- 오리진 대상: KAPublicALB
- 오리진 프로토콜: HTTP만 사용
- 오리진 포트: 80

### 10.3 캐시 동작

- 경로 패턴: 기본값 (*)
- 뷰어 프로토콜 정책: HTTP를 HTTPS로 리디렉션
- 캐시 정책: Managed-CachingOptimized
- 오리진 요청 정책: Managed-AllViewer

### 10.4 로깅 및 추가 보안

- 표준 로깅: Off
- Origin Shield: 비활성화
- 오리진 연결 시도: 3회
- 연결 시간 초과: 10초
- 응답 시간 초과: 30초

### 진단 결과

- CloudFront 배포 및 인증서 설정 확인
- 뷰어 HTTP → HTTPS 리디렉션 확인
- CloudFront → ALB 구간은 HTTP 사용
- 표준 로깅 비활성화 확인
- 오리진 통신 암호화 및 로깅 설정 개선 검토 필요

## 13. Terraform 리소스 정리

작업 종료 후 Terraform Destroy 계획 확인.

```text
Plan: 0 to add, 0 to change, 38 to destroy.
```

- 생성 예정: 0
- 변경 예정: 0
- 삭제 예정: 38

해당 계획은 Terraform이 관리하는 리소스 38개의 삭제를 예고한다.

※ 실제 Destroy 완료 여부는 실행 결과를 별도로 확인해야 한다.

### 주의 사항

- Terraform으로 생성한 리소스와 콘솔에서 별도로 생성한 리소스는 관리 범위가 다를 수 있다.
- Terraform Destroy 이후에도 별도 생성 리소스가 남아 있는지 확인해야 한다.
- NAT Gateway, RDS, ALB 등은 과금 가능성이 있으므로 잔여 리소스 확인이 필요하다.

## 14. 오늘 학습한 핵심 개념

### Security Group과 NACL

| 구분 | Security Group | NACL |
|---|---|---|
| 적용 대상 | ENI | Subnet |
| 상태 추적 | Stateful | Stateless |
| 규칙 | Allow | Allow / Deny |
| 규칙 평가 | 허용 규칙 종합 평가 | 번호가 낮은 순서대로 평가 |
| 응답 트래픽 | 자동 허용 | 별도 규칙 필요 |

### Public / Private Subnet

Public Subnet은 Internet Gateway로 향하는 기본 경로를 통해 인터넷 통신을 수행할 수 있다.

Private Subnet은 NAT Gateway를 통해 외부로 나가는 통신을 수행하도록 구성할 수 있다.

### 암호화 구간 구분

```text
Client
   |
   | HTTPS
   v
CloudFront
   |
   | HTTP (현재 확인된 구성)
   v
Public ALB
   |
   v
Web Server
```

클라이언트와 CloudFront 간 HTTPS 적용 여부와 CloudFront에서 오리진까지의 HTTPS 적용 여부는 별도로 점검해야 한다.
