> 주제: Sniffing · Spoofing · MITM · Ettercap DNS Spoofing · hping3 ICMP Flooding · Wireshark 분석

## 1. 오늘의 핵심 요약

1. **ARP Spoofing:** 공격자가 다른 호스트의 IP에 대응하는 MAC 주소를 자신의 MAC으로 속이는 위조 ARP 응답을 전송했다.
2. **MITM:** ARP Spoofing을 이용해 통신 중간에 개입할 수 있는 실습 환경을 구성했다.
3. **DNS Spoofing:** Ettercap의 `dns_spoof` 플러그인과 `etter.dns` 규칙으로 특정 도메인의 조회 결과를 Kali IP `192.168.20.50`으로 유도했다.
4. **가짜 웹페이지:** 실습 브라우저에서 의도한 가짜 웹페이지가 표시되는 결과를 직접 관찰했다.
5. **IP Spoofing + Flooding:** `hping3 --icmp ... --flood --spoof ...`로 출발지 IP를 위조한 대량 ICMP 패킷을 전송했다.
6. **Wireshark:** 수신 측 캡처에서 위조 출발지 IP와 실제 전송 장비의 이더넷 출발지 MAC을 구분해 확인했다.

**학습 핵심:** ARP는 IP↔MAC 대응 관계, DNS는 이름→IP 해석, IP Spoofing은 패킷의 출발지 IP 필드 조작이다. 서로 다른 계층과 대상에 대한 위조라는 점을 구별한다.

## 3. 기초 개념: Sniffing, Spoofing, Flooding

| 개념 | 의미 | 주요 보안 영향 | 오늘의 사례 |
|---|---|---|---|
| Sniffing | 패킷을 수집·관찰 | 기밀성 침해 가능 | Wireshark |
| Spoofing | 주소·신원·응답 정보 위조 | 인증·무결성 침해 가능 | ARP / DNS / IP |
| Flooding | 다량의 패킷을 빠르게 전송 | 가용성 침해 가능 | ICMP Flood |
| MITM | 두 통신 주체 사이에 개입 | 기밀성·무결성 침해 가능 | ARP 기반 실습 |
| DoS | 한 공격원에서 서비스 가용성을 방해 | 가용성 | 단일 Kali에서의 Flood 실습 |
| DDoS | 여러 공격원에서 분산하여 공격 | 가용성 | 개념 학습, 오늘 분산 실행 증거 없음 |

**CIA 3요소:** Confidentiality(기밀성), Integrity(무결성), Availability(가용성).

> **판단 주의:** Flood 패킷이 많이 관찰되었다는 사실만으로 서비스가 실제로 중단되었다고 단정할 수 없다. 응답 시간, 패킷 손실, 서비스 접속 실패 등 별도 가용성 지표가 필요하다.

## 4. ARP Spoofing 실습

### 4.1 공유한 명령

```bash
cat /proc/sys/net/ipv4/ip_forward
# 관찰 결과: 1

wireshark &

arpspoof -i eth1 -t 192.168.20.200 -r 192.168.20.201
```

### 4.2 명령 해석

- `-i eth1`: 내부망과 연결된 Kali 인터페이스 사용
- `-t 192.168.20.200`: 대상 호스트 지정
- `-r 192.168.20.201`: 반대 방향 대상까지 포함하는 양방향 ARP 위조
- `ip_forward = 1`: Kali의 IPv4 포워딩 활성화 상태. 패킷 중계에 관련되지만, 이 값 하나로 실제 중계 성공까지 입증되는 것은 아니다.

### 4.3 관찰된 위조 응답

```text
192.168.20.201 is-at 00:0c:29:b0:67:ba
192.168.20.200 is-at 00:0c:29:b0:67:ba
```

두 IP에 대해 동일한 MAC 주소를 알리는 위조 ARP 응답이 반복 출력되었다.

**의미:** 각 호스트가 상대방의 IP를 Kali의 MAC에 대응시키도록 유도하는 동작이다. 실제 피해 호스트의 ARP 캐시가 변경되었는지, 트래픽이 Kali를 경유했는지는 캐시 및 패킷 캡처로 추가 확인하면 더 확실하다.

## 5. Ettercap DNS Spoofing 실습

### 5.1 오늘 진행한 순서

1. Ettercap에서 **호스트 스캔(Host Scan)** 수행
2. 검색된 호스트를 **Target 1 / Target 2**로 지정
3. 실습 환경의 ARP 기반 MITM 기능을 활용
4. 플러그인 매니저에서 **`dns_spoof`** 활성화
5. `etter.dns`에 도메인별 규칙 설정
6. Windows에서 도메인 조회 또는 웹 접속 확인
7. **실제로 가짜 웹페이지가 표시되는 결과 관찰**

> 위 순서는 사용자가 설명한 실습 흐름을 재구성한 것이다. 모든 세부 클릭 순서나 화면 출력이 별도 로그로 제공된 것은 아니다.

### 5.2 `etter.dns`에 입력한 규칙

```text
demo.testfire.net    A      192.168.20.50
*.testfire.net       A      192.168.20.50
demo.testfire.net    PTR    192.168.20.50
```

동일한 방식으로 다음 도메인에 대한 설정도 만들었다고 공유했다.

- `www.netflix.co.kr`
- `intranet.mega123.com`
- `demo.testfire.net`

**레코드 해석**

- `A`: 도메인 이름을 지정한 IPv4 주소로 해석하도록 하는 규칙
- `*.testfire.net`: `testfire.net` 하위 도메인에 대한 와일드카드 매칭 규칙. 다른 도메인(`netflix.co.kr`, `mega123.com`)까지 자동으로 매칭되는 것은 아님
- `PTR`: 역방향 이름 조회에 관련된 규칙. 일반 DNS의 역방향 조회 개념과 Ettercap 설정 파일의 고유 문법을 구분할 것

### 5.3 확인된 현상과 의미

Windows에서 `www.netflix.co.kr`, `intranet.mega123.com` 등의 이름 조회 시 `192.168.20.50`이 표시되었다고 공유했다. 해당 주소는 **Kali eth1** 주소다. 또한 웹 브라우저에서 **가짜 웹페이지가 실제 표시되었다**고 확인했다.

```text
사용자: demo.testfire.net 접속 시도
        |
        v
DNS 질의에 대해 위조 IP 192.168.20.50 제공
        |
        v
클라이언트가 Kali 측 IP로 연결 시도
        |
        v
해당 IP의 웹 서버가 응답하면 가짜 페이지 표시
```

**해석:** 이름 해석이 조작된 목적지로 유도되었고, 해당 목적지에서 웹 콘텐츠를 제공한 실습 결과로 볼 수 있다. 다만 DNS 응답 패킷과 HTTP 연결의 정확한 상관관계를 패킷 캡처로 검증하면 인과관계를 더 강하게 입증할 수 있다.

**보안 포인트:** 가짜 페이지가 표시되었다고 해서 계정 정보 수집·탈취까지 이루어졌다는 뜻은 아니다. HTTPS에서는 인증서 검증, HSTS 등의 보호로 위조 서버 연결에 경고 또는 차단이 발생할 수 있다.

## 6. hping3: IP Spoofing + ICMP Flooding

### 6.1 실제 실행한 명령

```bash
hping3 --interface eth1 --icmp 192.168.20.200 --flood --spoof 192.168.20.30
```

| 요소 | 역할 |
|---|---|
| `hping3` | 사용자 지정 패킷 생성 도구 |
| `--interface eth1` | Kali 내부망 인터페이스 선택 |
| `--icmp` | ICMP 패킷 생성 |
| `192.168.20.200` | CentOS 목적지 IP |
| `--flood` | 가능한 한 빠른 속도로 연속 전송 |
| `--spoof 192.168.20.30` | IP 헤더의 출발지 주소를 `.30`으로 위조 |

**중요한 구분:** `--spoof`는 이 실습에서 **출발지 IP 위조**를 의미한다. DNS 응답이나 도메인 이름을 위조하는 옵션이 아니다.

### 6.2 Kali 출력

```text
299302 packets transmitted, 0 packets received, 100% packet loss
```

- 대량 패킷 전송을 보여주는 출력이다.
- Flood 모드에서는 수신 응답을 일반적인 ping과 동일하게 해석하기 어렵고, 출발지 IP도 위조되어 있다.
- 따라서 이 출력의 `100% packet loss`만으로 **CentOS가 완전히 다운되었다**고 결론 내릴 수 없다.

### 6.3 수신 측 Wireshark 관찰

공유한 Wireshark 화면에서 확인된 핵심 항목:

```text
Protocol:       ICMP
Info:           Echo (ping) request
Source IP:      192.168.20.30       <- 위조된 출발지 IP
Destination IP: 192.168.20.200      <- CentOS
Ethernet Src:   00:0c:29:b0:67:ba  <- Kali의 MAC으로 관찰
Ethernet Dst:   00:0c:29:14:3b:a5  <- CentOS의 MAC으로 관찰
```

**핵심 분석:** IP 헤더에는 `.30`이 표시되지만, 같은 내부망에서 캡처한 이더넷 프레임의 송신 MAC은 Kali에 해당하는 주소로 보였다. 이 차이는 **IP 주소 위조**를 이해하는 좋은 근거다.

단, 이더넷 출발지 MAC은 캡처 지점과 네트워크 경로에 따라 마지막 홉 장비의 MAC이 보일 수 있으므로, 임의의 네트워크에서 언제나 실제 최초 송신자의 MAC을 알아낼 수 있다는 뜻은 아니다.

### 6.4 시스템 모니터에서 관찰한 변화

- CentOS 메모리 사용량: 약 **905.6~908.2 MiB / 999.9 MiB**, 약 **90.6~90.8%**
- 스왑 사용량: 한 화면에서 **23.2 MiB / 1.0 GiB (2.3%)**
- CPU: 캡처 순간 약 0~1% 수준으로 보인 장면이 있었음
- Wireshark에서 매우 짧은 간격으로 연속된 ICMP 요청 패킷 관찰

**해석상의 한계:** 공격 직후 메모리 사용량이 높아진 것은 의미 있는 관찰이지만, Wireshark 캡처 프로그램의 버퍼·패킷 보관, 다른 프로세스 사용량, 기존 메모리 점유 등을 분리해야 **Flooding 때문에 증가했다**는 원인을 확정할 수 있다.

## 7. ARP / DNS / IP Spoofing 비교

| 종류 | 무엇을 속이는가? | 실습에서 관찰할 것 | 비유 |
|---|---|---|---|
| ARP Spoofing | IP에 대응하는 MAC 주소 | ARP Reply, ARP 캐시 | '저 IP의 장비는 나야' |
| DNS Spoofing | 도메인 이름에 대응하는 IP | DNS Answer, 접속 목적지 | '그 사이트는 여기야' |
| IP Spoofing | 패킷 헤더의 출발지 IP | IP Source와 L2 정보 | '이 패킷은 다른 사람이 보냈어' |

### 계층별 정리

- **ARP:** 같은 링크에서 IP→MAC 해석에 사용되는 프로토콜
- **DNS:** 애플리케이션 계층의 이름 해석 서비스
- **IP:** 네트워크 계층의 주소 지정 및 라우팅
- **ICMP:** IP 네트워크의 제어·오류 메시지 프로토콜
- **HTTP:** 웹 요청·응답 프로토콜. DNS 이름 해석 이후 접속에 이용될 수 있음

## 8. Wireshark 분석 체크리스트

### ARP Spoofing

- [ ] `arp` 필터로 ARP Reply 확인
- [ ] 동일 MAC이 여러 IP의 소유자로 광고되는지 확인
- [ ] 대상 호스트의 ARP 캐시 전후 비교
- [ ] 중계 트래픽이 실제 공격자 인터페이스를 통과하는지 확인

### DNS Spoofing

- [ ] `dns` 필터로 Query / Answer 확인
- [ ] 요청 도메인과 응답 A 레코드 IP 확인
- [ ] 위조 IP가 `192.168.20.50`인지 확인
- [ ] 브라우저가 연결한 목적지 IP 확인
- [ ] 가짜 페이지 표시 화면과 DNS 응답을 함께 기록

### ICMP Flooding / IP Spoofing

- [ ] `icmp` 필터로 Echo Request 연속 수신 확인
- [ ] IP Source `.30`, IP Destination `.200` 확인
- [ ] Ethernet Source MAC과 IP Source 차이 확인
- [ ] 초당 패킷 수 및 수신량 확인
- [ ] 공격 전후 CPU·메모리·서비스 응답 상태 비교

## 9. 방어 관점: 오늘 실습과 연결되는 대응책

> 아래 내용은 **실습 기록 외의 일반 보안 지식 보충**이다. 수업 교재의 설정을 임의로 바꾸라는 뜻이 아니다.

| 위협 | 방어·탐지 예시 | 유의점 |
|---|---|---|
| ARP Spoofing | Dynamic ARP Inspection(DAI), DHCP Snooping 연계, ARP 이상 탐지 | 스위치 지원 및 신뢰 포트 설계 필요 |
| DNS Spoofing | DNSSEC 검증, 신뢰 가능한 DNS 경로, DNS 응답 모니터링 | DNSSEC은 검증 범위와 지원 여부에 따라 효과 차이 |
| 가짜 HTTP 사이트 | HTTPS 인증서 검증, HSTS, 사용자 교육 | HTTPS만으로 모든 피싱이 방지되는 것은 아님 |
| IP Spoofing | Ingress/Egress 필터링, uRPF(환경에 맞게), 비정상 소스 감지 | 비대칭 라우팅 환경에 주의 |
| ICMP Flooding | 트래픽 모니터링, 적절한 Rate Limit, 방화벽/IPS, 상위망 DDoS 완화 | 정상 진단용 ICMP까지 무조건 차단하지 않도록 설계 |

## 10. 시험·면접 예상 질문 (Q&A)

**Q1. ARP Spoofing과 DNS Spoofing은 무엇이 다른가?**  
A. ARP Spoofing은 IP와 MAC의 대응 관계를 위조하고, DNS Spoofing은 도메인 이름에 대한 IP 응답을 조작한다.

**Q2. `hping3 --spoof`로 DNS도 속일 수 있는가?**  
A. 오늘 사용한 `--spoof`는 IP 헤더의 출발지 IP를 위조한다. DNS 응답 위조와는 별개다.

**Q3. IP Spoofing을 했는데 Wireshark에서 Kali MAC이 보인 이유는?**  
A. IP 헤더의 출발지 주소와 이더넷 프레임의 출발지 MAC은 서로 다른 필드이기 때문이다. 같은 링크에서 캡처한 경우 실제 전송 인터페이스의 MAC이 나타날 수 있다.

**Q4. `--flood`를 사용했으면 무조건 DoS 성공인가?**  
A. 아니다. 대량 패킷 전송은 확인할 수 있어도, 서비스 가용성 저하·중단 여부는 별도 지표로 검증해야 한다.

**Q5. DNS Spoofing이 성공하면 HTTPS도 무조건 속일 수 있는가?**  
A. 아니다. 서버 인증서 검증과 HSTS 등으로 위조 목적지에 대한 연결이 경고·차단될 수 있다.

**Q6. `etter.dns`의 와일드카드 A 규칙은 어떤 의미인가?**  
A. 지정한 도메인 패턴에 일치하는 하위 도메인 조회를 동일 IP로 응답하도록 지정하는 규칙이다. 다른 최상위 도메인까지 자동 적용되지는 않는다.

**Q7. ARP Spoofing 시 IP Forwarding이 필요한 이유는?**  
A. 공격자 호스트를 통과하는 패킷을 다음 목적지로 중계하는 데 필요할 수 있기 때문이다. 단, 활성화만으로 MITM 성공이 증명되지는 않는다.

**Q8. 오늘 실습에서 CIA 중 가장 관련 있는 요소는?**  
A. Sniffing은 기밀성, Spoofing과 MITM은 무결성·기밀성, Flooding은 가용성에 직접 연결된다.

**Q9. 가짜 웹페이지가 떴다는 사실은 무엇을 증명하는가?**  
A. 사용자의 접속이 의도한 실습 웹 콘텐츠에 도달했다는 강한 관찰 결과다. 로그인 정보 탈취나 HTTPS 보안 우회 성공을 자동으로 의미하지는 않는다.

**Q10. DoS와 DDoS의 차이는?**  
A. DoS는 단일 공격원에서도 수행될 수 있고, DDoS는 여러 분산된 공격원에서 수행한다. 오늘 확인된 Kali 한 대의 Flooding은 분산 공격 증거가 없다.

## 11. 포트폴리오 / PPT용 추천 캡처

1. **VMware 네트워크 구성도:** Kali `eth1 .50`, CentOS `.200`, Windows `.201/.202` 식별

## 12. 오늘의 학습 결론

오늘 실습은 개별 명령어 암기보다 **네트워크 계층별 신뢰 관계가 어떻게 악용될 수 있는지**를 연결해서 이해한 것이 가장 중요하다.

- ARP: **누구의 MAC인가?**
- DNS: **어느 IP로 접속할 것인가?**
- IP Spoofing: **누가 보낸 패킷으로 보이는가?**
- Flooding: **얼마나 많은 요청을 보내는가?**
- Wireshark: **패킷에 실제로 무엇이 기록되었는가?**
