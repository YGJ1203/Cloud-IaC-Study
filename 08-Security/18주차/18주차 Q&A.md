## 2. 기본 면접 Q&A 12문제

### Q1. SYN Scan과 Idle Scan 차이는?
**답변:** SYN Scan은 TCP 연결을 완성하지 않고 SYN/ACK 또는 RST 응답으로 포트 상태를 판단합니다. Idle Scan은 제3의 Zombie 호스트 IP ID 변화를 이용해 대상 포트 상태를 간접 추론합니다.

### Q2. Nmap open / closed / filtered는?
- **open:** 서비스가 연결을 수락하는 상태
- **closed:** 호스트에 도달할 수 있으나 해당 포트에서 수신 서비스가 없는 상태
- **filtered:** 필터링 등으로 열림 여부를 판단하기 어려운 상태

**주의:** `filtered`는 안전 또는 위험을 확정하는 결과가 아닙니다.

### Q3. Snort와 Nessus 차이는?
**답변:** Snort는 네트워크 트래픽을 규칙과 비교해 침입 징후를 탐지하는 IDS/IPS 도구입니다. Nessus는 알려진 취약점과 잘못된 설정 등을 점검하는 취약점 스캐너입니다.

### Q4. SUID와 보안 위험은?
**답변:** SUID 실행 파일은 실행 시 파일 소유자의 유효 UID로 동작할 수 있습니다. root 소유 SUID 프로그램에 취약점이 있으면 권한 상승으로 이어질 수 있습니다.

### Q5. Meterpreter 프로세스 마이그레이션은?
**답변:** 세션 실행 컨텍스트를 다른 프로세스로 옮기는 기능입니다. 방어자는 비정상 프로세스 접근, 메모리 조작, 자식 프로세스 및 네트워크 연결을 함께 분석합니다.

### Q6. 피싱과 Credential Harvesting의 관계는?
**답변:** 피싱은 사용자를 속여 정보를 입력하거나 행동하게 만드는 사회공학 공격입니다. Credential Harvesting은 그 과정에서 인증 정보를 수집하는 행위입니다.

### Q7. SQL Injection의 근본 원인은?
**답변:** 사용자 입력이 SQL 구문의 구조를 변경할 수 있게 쿼리를 작성하기 때문입니다. SQL 코드와 데이터를 분리하지 않는 동적 문자열 결합이 대표적인 원인입니다.

### Q8. UNION 기반과 Boolean 기반 SQL Injection 차이는?
**답변:** UNION 기반은 다른 SELECT 결과를 결합해 데이터를 노출시키는 방식입니다. Boolean 기반은 참/거짓 조건에 따른 응답 차이로 정보를 추론합니다.

### Q9. information_schema란?
**답변:** DB, 테이블, 컬럼 등의 메타데이터를 조회할 수 있는 시스템 스키마입니다. 조회 가능한 정보는 DBMS와 권한에 따라 달라집니다.

### Q10. SQL Injection 방어의 핵심은?
**답변:** Prepared Statement와 파라미터 바인딩을 우선 사용합니다. 입력값 검증, DB 최소 권한, 오류 메시지 제한 등을 추가합니다.

### Q11. Active Directory의 핵심 기능은?
**답변:** Windows 도메인 환경의 사용자·컴퓨터·그룹 등을 중앙 관리하며 인증·인가 및 그룹 정책을 지원합니다.

### Q12. EDR과 백업·복구 솔루션을 함께 사용하는 이유는?
**답변:** EDR은 위협 탐지·대응에, 백업·복구는 데이터 손상이나 랜섬웨어 피해 이후 복구에 중점을 둡니다. 서로 다른 방어 계층을 보완합니다.

## 3. 심화 면접 3문제와 피드백

### 심화 Q1. Prepared Statement를 써도 SQL Injection이 가능한가?
- **최초 답변:** `?` 바인딩을 하면 발생할 수 있다고 이해함.
- **교정:** 정상적인 `?` 파라미터 바인딩은 SQL Injection을 방어하는 대표적인 방식입니다.
- **예외:** 테이블명·컬럼명·정렬 방향 등 SQL 구조를 사용자 입력과 직접 문자열 결합하면 위험합니다. 해당 구조 요소에는 허용 목록(allowlist)을 사용합니다.

```sql
SELECT * FROM users WHERE id = ?;
```

위 `?`는 SQL 구문이 아니라 데이터 값으로 바인딩됩니다(드라이버별 플레이스홀더 문법은 다를 수 있음).

```python
# Python DB-API 드라이버 예시: 실제 플레이스홀더는 드라이버에 따라 다름
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))

# 위험: 정렬 컬럼명을 검증 없이 SQL 구조에 직접 결합
query = "SELECT * FROM users ORDER BY " + user_input
```

**면접 답변:** "파라미터 바인딩은 일반적인 값에 대한 SQL Injection을 막지만, SQL 구조를 동적으로 결합하는 부분은 별도로 허용 목록 검증이 필요합니다."

### 심화 Q2. 모든 TCP 포트가 filtered이면 서버가 안전한가?
- **실제 답변:** "오히려 위험할 수 있습니다. 판단이 어려운 상황이니까요."
- **평가:** 판단 불가라는 핵심은 정확합니다. 단, filtered 자체가 위험을 뜻하지는 않습니다.

**면접 답변:** "필터링 때문에 포트의 열림 여부를 판단하기 어렵다는 의미입니다. 방화벽이 정상 작동 중일 수도 있으므로 이 결과만으로 안전성을 확정하지 않고, 승인된 범위에서 방화벽 정책과 서비스 노출 상태를 추가 확인하겠습니다."

### 심화 Q3. Snort ICMP Flood 경고 수천 건이 발생하면?
- **실제 답변:** "와이어샤크로 확인해볼 것 같습니다."
- **평가:** 도구 선정은 적절합니다. 무엇을 확인할지도 덧붙이면 좋습니다.

**확인 항목:**
1. 단위 시간당 ICMP 패킷 수 및 증가 추세
2. 출발지·목적지 IP, ICMP Type/Code
3. 대역폭, 서버 CPU, 서비스 응답 상태
4. 정상 모니터링 또는 오탐 가능성
5. 필요 시 방화벽·라우터·서버 로그와 교차 분석

**면접 답변:** "Wireshark로 ICMP 패킷의 빈도와 IP·유형을 분석하고, 서버 자원 사용률 및 서비스 영향 여부를 확인해 실제 공격인지 판단하겠습니다."

## 4. 추가 질문: Prepared Statement 외 SQL Injection 방어 대책 2가지

**실제 답변:** "입력값 검증 및 입력값 이스케이프 등의 방법이 존재합니다."

**피드백:** 둘 다 관련 있는 방어 기법입니다. 다만 이스케이프는 DBMS·인코딩·SQL 문맥에 따라 실수할 수 있으므로 파라미터 바인딩의 대체재로 취급하면 안 됩니다.

| 방법 | 역할 | 주의점 |
|---|---|---|
| Prepared Statement | SQL 코드와 값 분리 | 구조 요소의 동적 결합은 별도 검증 |
| 입력값 검증 | 형식·길이·범위 제한 | 이것만으로 SQLi 완전 차단 불가 |
| 이스케이프 | 특수문자의 구문 해석 방지 | DBMS·문맥 의존, 보조적 사용 |
| 최소 권한 | 취약점 악용 시 피해 범위 제한 | SQLi 자체를 예방하지는 않음 |
| 오류 처리 | 내부 구조 노출 감소 | 상세 오류는 내부 로그에만 기록 |

**최종 면접 답변:** "SQL Injection을 방지하기 위해 파라미터 바인딩을 우선 사용합니다. 추가로 입력값을 허용된 형식으로 검증하고, 필요한 경우 DBMS 문맥에 맞는 이스케이프를 적용합니다. DB 계정에는 최소 권한을 부여해 피해 범위도 제한합니다."
