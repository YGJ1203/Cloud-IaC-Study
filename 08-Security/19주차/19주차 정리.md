## 1. SQL Injection 및 웹 취약점

### 1.1 Blind SQL Injection

SQL 쿼리의 결과가 직접 출력되지 않더라도 참·거짓 응답의 차이를 이용하여 데이터베이스 정보를 추론하는 공격이다.

**실습 예시**

```sql
' OR 1=1 #
' OR LENGTH(DATABASE())=5 #
' OR SUBSTRING(DATABASE(),1,1)='b' #
```

- `LENGTH()` : 문자열 길이 확인
- `SUBSTRING()` : 문자열 일부 추출
- `DATABASE()` : 현재 데이터베이스 이름 확인
- Boolean-based : 참·거짓에 따른 응답 차이 이용
- Time-based : 응답 지연 시간을 이용한 추론

**방어 방법**

- Prepared Statement 및 파라미터 바인딩
- 입력값 검증
- DB 계정 최소 권한 적용
- WAF 탐지 정책 적용

### 1.2 XSS 및 AJAX/JSON

bWAPP 환경에서 AJAX 요청과 JSON 응답을 분석하였다.

- Reflected XSS : 입력한 스크립트가 응답에 반영되어 실행되는 취약점
- DOM-based XSS : 브라우저의 DOM 처리 과정에서 발생하는 취약점
- `innerHTML` : 검증되지 않은 데이터를 삽입하면 XSS 위험 발생
- `textContent` : 일반 텍스트를 안전하게 표시할 때 활용

**실습 관찰**

| 보안 레벨 | 응답 Content-Type |
|---|---|
| Low | text/html |
| Medium | text/json; charset=utf-8 |
| High | text/json; charset=utf-8 |

Content-Type만으로 XSS 방어 여부를 단정할 수 없으며, 브라우저의 실제 데이터 처리 방식까지 확인해야 한다.

## 2. Snort IDS 실습

### 2.1 Snort 기본 개념

Snort는 네트워크 패킷을 분석하고 정의된 규칙에 따라 의심스러운 트래픽을 탐지하는 IDS/IPS 소프트웨어이다.

**기본 룰 구조**

```text
alert tcp any any -> any 80 (
    msg:"SQL Injection Detected";
    content:"union";
    nocase;
    sid:3000001;
    rev:1;
)
```

- `alert` : 탐지 시 경고 발생
- `tcp` : 대상 프로토콜
- `content` : 검사할 문자열
- `nocase` : 대소문자 구분 없이 검사
- `sid` : 규칙 식별 번호
- `rev` : 규칙 버전

### 2.2 웹 공격 탐지

| 공격 유형 | 주요 탐지 요소 |
|---|---|
| SQL Injection | UNION, SELECT, OR, AND |
| XSS | script 태그, URL 인코딩 |
| OS Command Injection | 세미콜론, && |
| iFrame Injection | iframe 태그 |
| Path Traversal | ../, /etc |
| Shellshock | () { 패턴 |

단순 문자열 탐지는 정상 요청까지 오탐할 수 있으므로 HTTP 요청 위치, 정규화, 추가 조건을 고려해야 한다.

### 2.3 네트워크 공격 탐지

11월 11일에는 다음 공격 유형도 실습하였다.

- TCP SYN 기반 Half-Open Scan
- TCP Flooding
- UDP Flooding
- ICMP Flooding
- LAND Attack
- IP Fragmentation
- Ping of Death

**중요:** Snort 경고 발생은 공격 시도 탐지를 의미하며, 공격 성공이나 패킷 차단을 의미하지는 않는다.

### 2.4 Threshold 개념

- `threshold` : 지정된 시간 동안 일정 횟수 이상 발생할 때 경고
- `limit` : 지정된 시간 동안 발생하는 경고 수 제한
- `both` : 임계치 충족과 경고 제한을 함께 적용

이 기능은 반복 공격 탐지 및 과도한 경고 발생을 제어하는 데 활용된다.

## 3. FortiWeb WAF 실습

### 3.1 FortiWeb 구성

**실습 환경**

| 항목 | 설정 |
|---|---|
| 제품 | FortiWeb VM 8.0.5 |
| 운영 방식 | Reverse Proxy |
| 관리 IP | 192.168.20.105 |
| 웹 서버 | 192.168.20.205:80 |
| Server Pool | MyWebPool |
| Virtual Server | MyVS |
| Server Policy | MyWAF |
| 보호 프로파일 | Inline Standard Protection |

### 3.2 Reverse Proxy 동작

```text
Kali Client
     |
     | HTTP Request
     v
FortiWeb WAF
192.168.20.105
     |
     | 허용된 요청 전달
     v
bWAPP Web Server
192.168.20.205:80
```

클라이언트 요청을 WAF가 먼저 검사한 뒤 정상 요청만 백엔드 서버로 전달한다.

### 3.3 공격 차단 결과

**차단 확인**

- OS Command Injection
- SQL Injection (GET/POST)
- Reflected XSS
- iFrame Injection 관련 요청

**추가 점검 사항**

- Directory Traversal은 기본 정책에서 일부 요청이 차단되지 않음
- Custom Signature 적용 여부 확인 필요
- 정상 요청과 공격 요청을 구분하는 정책 튜닝 필요

일부 iFrame 관련 차단은 `robots.txt` 패턴 매칭과 관련되어 있어, 반드시 해당 공격 전용 시그니처가 작동했다고 해석해서는 안 된다.

### 3.4 IDS와 WAF 비교

| 항목 | Snort IDS | FortiWeb WAF |
|---|---|---|
| 주목적 | 네트워크 공격 탐지 | 웹 애플리케이션 보호 |
| 분석 대상 | 패킷 및 트래픽 | HTTP/HTTPS 요청 |
| 탐지 규칙 | Snort Rule | WAF 정책·시그니처 |
| 차단 | IDS 모드에서는 직접 차단하지 않음 | 정책에 따라 차단 |
| 활용 | 공격 분석·경고 | 웹 공격 방어 |

### 4.2 Security Group과 NACL

| 구분 | Security Group | Network ACL |
|---|---|---|
| 적용 대상 | ENI/리소스 | 서브넷 |
| 상태 추적 | Stateful | Stateless |
| 규칙 | Allow | Allow / Deny |
| 반환 트래픽 | 연결 상태에 따라 자동 허용 | 명시적 허용 필요 |
| 평가 방식 | 허용 규칙 종합 평가 | 낮은 규칙 번호부터 평가 |

**핵심 개념**

NACL은 Stateless이므로 요청 트래픽뿐 아니라 응답 트래픽도 고려해야 한다.

특히 ALB와 백엔드 서버 또는 Aurora DB 사이의 통신을 점검할 때 소스·목적지 포트와 반환 경로를 함께 확인해야 한다.

### 4.3 Aurora 상태 점검

11월 12일 실습에서 NACL 변경 전 확인한 상태는 다음과 같다.

```text
Cluster : kadb    Available
Writer  : kadb-1  Available
Reader  : kadb-2  Available
```

**주의사항**

- `Available`은 DB 리소스가 정상 운영 상태임을 의미한다.
- 실제 애플리케이션의 DB 접속 성공을 보장하지는 않는다.
- NACL 변경 이후에는 DB 연결 테스트를 별도로 수행해야 한다.

### 4.4 ALB 및 Target Group

ALB의 Target Group은 등록된 대상의 상태를 Health Check로 판단한다.

점검 순서:

1. ALB Listener 확인
2. Target Group 등록 대상 확인
3. Health Check 경로와 포트 확인
4. Security Group 규칙 확인
5. NACL 양방향 규칙 확인
6. 실제 HTTP 요청 및 응답 확인

## 6. 보안 엔지니어 면접 대비 Q&A

**Q1. IDS와 IPS의 차이는 무엇인가요?**

IDS는 침입 시도를 탐지하고 경고하는 시스템이며, IPS는 인라인으로 배치되어 악성 트래픽을 차단할 수 있는 시스템입니다.

**Q2. WAF와 일반 방화벽은 무엇이 다른가요?**

일반 방화벽은 주로 네트워크 접근을 제어하고, WAF는 HTTP 요청의 구조와 내용을 검사하여 SQL Injection, XSS 등 웹 공격을 방어합니다.

**Q3. NACL이 Stateless라는 의미는 무엇인가요?**

요청과 응답 트래픽을 각각 독립적으로 평가하므로, 통신에 필요한 양방향 규칙을 명시적으로 구성해야 한다는 의미입니다.

**Q4. SQL Injection의 근본적인 방어 방법은 무엇인가요?**

SQL 구문과 사용자 입력을 분리하는 Prepared Statement 및 파라미터 바인딩이 핵심입니다.

**Q5. Snort에서 경고가 발생하면 공격이 성공한 것인가요?**

아닙니다. 경고는 탐지 조건에 일치하는 트래픽이 발생했다는 의미이며, 공격 성공 여부는 대상 시스템과 관련 로그를 추가 분석해야 합니다.

**Q6. ALB Target이 Unhealthy라면 무엇을 확인해야 하나요?**

Health Check 경로·포트, 서버 프로세스, Security Group, NACL, 응답 코드 등을 확인해야 합니다.

**Q7. WAF가 모든 웹 공격을 차단할 수 있나요?**

아닙니다. 우회 기법, 정상 요청과 유사한 공격, 정책 누락 등이 존재하므로 안전한 애플리케이션 개발과 지속적인 정책 튜닝이 필요합니다.
