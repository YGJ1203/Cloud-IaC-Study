# 🐧 Linux Additional Notes

> Linux 수업에서 학습한 명령어, 파일 시스템, 링크, 압축, 권한, Shell 및 Process 내용을 바탕으로
> **추가로 알아두면 이해에 도움이 되는 개념들을 정리한 문서**이다.

# 1. `ls -l`의 첫 번째 문자는 무엇일까?

```bash id="uxgffp"
ls -l
```

예:

```text id="0nfgg4"
-rw-r--r--  1 user user 1024 Aug 17  test.txt
drwxr-xr-x  2 user user 4096 Aug 17  testdir
lrwxrwxrwx  1 user user    8 Aug 17  link
```

맨 앞의 문자는 **파일 종류(File Type)**를 나타낸다.

| 문자  | 의미               |
| --- | ---------------- |
| `-` | 일반 파일            |
| `d` | 디렉터리             |
| `l` | Symbolic Link    |
| `b` | Block Device     |
| `c` | Character Device |

따라서

```text id="zcm1b2"
drwxr-xr-x
│└──────── 권한
│
└─ d = Directory
```

처럼 해석한다.

# 2. Block Device와 Character Device

Linux에서는 하드웨어 장치도 파일처럼 취급한다.

대표적인 위치:

```text id="2h2ozd"
/dev
```

## Block Device

데이터를 **블록 단위**로 처리하는 장치이다.

대표적으로:

```text id="ay6d3z"
Disk
SSD
USB Storage
```

등이 있다.

예:

```text id="v0qmsu"
/dev/sda
/dev/sdb
```

---

## Character Device

데이터를 **연속적인 문자/바이트 흐름**으로 처리한다.

대표적으로 터미널 등의 장치가 있다.

### 핵심

```text id="6wyfhr"
Block Device
→ 데이터를 블록 단위로 처리
→ Disk 계열

Character Device
→ 데이터를 연속적인 흐름으로 처리
→ Terminal 계열
```

# 3. Linux 주요 디렉터리는 왜 나뉘어 있을까?

Linux에서는 파일의 용도에 따라 저장 위치가 어느 정도 정해져 있다.

```text id="1q70l2"
/
├── etc
├── home
├── var
├── tmp
├── dev
├── proc
└── usr
```

대표적인 역할은 다음과 같다.

| 디렉터리    | 주요 역할              |
| ------- | ------------------ |
| `/etc`  | 시스템 및 서비스 설정 파일    |
| `/home` | 일반 사용자 홈 디렉터리      |
| `/root` | root 사용자의 홈 디렉터리   |
| `/var`  | 로그 등 자주 변경되는 데이터   |
| `/tmp`  | 임시 파일              |
| `/dev`  | 장치 파일              |
| `/proc` | 프로세스 및 커널 정보       |
| `/usr`  | 프로그램 및 사용자용 시스템 자원 |

특히 서버 관리에서는 다음 두 곳을 자주 만나게 된다.

```text id="glt7a2"
/etc
→ 설정

/var/log
→ 로그
```

즉,

> **설정 확인 → `/etc`
> 문제 추적 → `/var/log`**

이라는 패턴을 기억해두면 좋다.

# 4. `mkdir`와 `mkdir -p`

일반적인 디렉터리 생성:

```bash id="u6jyyi"
mkdir test
```

하지만 다음과 같이 한 번에 여러 단계의 디렉터리를 만들고 싶다면:

```text id="5vxt7s"
study/linux/basic
```

단순히 실행하면 부모 디렉터리가 없을 경우 실패할 수 있다.

```bash id="7ekc8n"
mkdir study/linux/basic
```

이때 사용하는 옵션:

```bash id="3qqp17"
mkdir -p study/linux/basic
```

`-p`는 필요한 **상위 디렉터리까지 함께 생성**한다.

```text id="qqe5ut"
study
└── linux
    └── basic
```

# 5. `cp -p`와 `cp -r`

## `-r`

디렉터리 내부까지 **재귀적으로(Recursive)** 복사한다.

```bash id="ltn8yx"
cp -r source backup
```

---

## `-p`

가능한 범위에서 원본의 속성을 보존하며 복사한다.

```bash id="tud5c6"
cp -p file1 file2
```

대표적으로 보존하려는 정보:

```text id="03txkm"
권한
소유권
시간 정보
```

### 기억법

```text id="xchx2b"
-r = Recursive
-p = Preserve
```

---

# 6. `rm -r`, `rm -f`, `rm -rf` 💀

## `rm -r`

디렉터리 내부까지 재귀적으로 삭제한다.

```bash id="n7p73m"
rm -r test
```

---

## `rm -f`

확인 질문이나 일부 오류를 최소화하면서 강제로 삭제한다.

```bash id="gzyjhk"
rm -f file
```

`f`:

```text id="juy15w"
force
```

---

## `rm -rf`

두 옵션을 결합한다.

```bash id="5chghd"
rm -rf test
```

즉:

```text id="n42fbp"
r = recursive
f = force

rm -rf
→ 내부까지 재귀적으로 강제 삭제
```

⚠️ 매우 강력한 명령이므로 root 권한에서는 특히 주의한다.

삭제 전 다음 명령으로 위치와 대상을 확인하는 습관이 좋다.

```bash id="r18rbx"
pwd
ls
```

# 7. `touch`는 빈 파일 생성 명령어일까?

흔히 다음과 같이 사용한다.

```bash id="ws5o0r"
touch test.txt
```

파일이 존재하지 않으면 빈 파일이 생성된다.

하지만 `touch`의 중요한 목적 중 하나는 **파일의 시간 정보(timestamp)를 변경하는 것**이다.

```bash id="5bmtxv"
touch -t 202608171500 test.txt
```

따라서:

```text id="uz9azm"
touch
├─ 파일 없음 → 빈 파일 생성
└─ 파일 있음 → 시간 정보 변경 가능
```

# 8. `ls -i`와 `ls -id`

inode 번호 확인:

```bash id="c43o7d"
ls -i
```

디렉터리 자체의 inode를 확인하고 싶을 경우:

```bash id="1qovl0"
ls -id directory
```

여기서 `-d`는 디렉터리의 **내용물이 아니라 디렉터리 자체**를 대상으로 표시하도록 한다.

이 차이는 Hard Link와 inode를 공부할 때 특히 유용하다.

---

# 9. Hard Link의 진짜 핵심

Hard Link는 단순히

> "원본 파일의 복사본"

이 아니다.

두 파일 이름이 **동일한 inode를 가리킨다.**

```text id="u8yt5j"
fileA ───┐
         │
         ├── inode 12345
         │       │
fileB ───┘       ↓
              DATA
```

따라서:

```bash id="vwbh3e"
ls -i
```

를 실행하면 Hard Link끼리는 동일한 inode 번호를 확인할 수 있다.

---

# 10. Symbolic Link는 inode가 다르다

```bash id="f6oj21"
ln -s original link
```

Symbolic Link는 원본의 inode를 직접 공유하지 않는다.

```text id="8r8xjs"
link
 │
 └── "original"이라는 경로를 가리킴
             │
             ▼
          original
             │
             ▼
           inode
```

따라서 원본이 삭제되면 링크가 가리킬 대상이 사라진다.

```text id="nhvb0k"
Hard Link
→ 같은 inode

Symbolic Link
→ 원본의 경로를 참조
```

# 11. tar는 본질적으로 압축이 아니다

초보자가 상당히 헷갈리기 쉬운 부분이다.

```bash id="pdzzzb"
tar -cvf backup.tar directory/
```

`tar`의 기본 역할은 여러 파일을 **하나의 archive로 묶는 것**이다.

```text id="0ar2d7"
A.txt ─┐
B.txt ─┼─→ backup.tar
C.txt ─┘
```

압축까지 하려면 gzip 등의 압축 방식과 함께 사용할 수 있다.

```bash id="zz02au"
tar -czvf backup.tar.gz directory/
```

즉:

```text id="wyk69k"
tar
→ 묶기

gzip
→ 압축

tar + gzip
→ 묶고 압축
```

# 13. PID와 PPID

프로세스에는 고유 번호인 PID가 존재한다.

```text id="cyve6f"
PID
= Process ID
```

하지만 프로세스에는 자신을 생성한 **부모 프로세스**도 존재할 수 있다.

```text id="4brh3e"
PPID
= Parent Process ID
```

확인:

```bash id="xwcf5d"
ps -ef
```

예:

```text id="xnxpfk"
UID    PID    PPID
root     1       0
user  1234       1
```

구조적으로 보면:

```text id="6e8n1s"
Parent Process
      │
      └── Child Process
```

Linux 프로세스는 이런 부모-자식 관계를 형성할 수 있다.

## ps



🎥 영상에 가깝다.

따라서:

```text id="xynbb5"
ps
→ Snapshot 📸

→ Real-time Monitoring 🎥
```

# 15. `kill`은 프로세스를 죽이는 명령어?

이름 때문에 그렇게 보이지만 정확히는:

> **프로세스에 Signal을 전달하는 명령어**

이다.

```bash id="4n8lqg"
kill PID
```

기본적으로 일반적인 종료 요청에 사용되는 `SIGTERM`을 전달한다.

```bash id="nsyphd"
kill -9 PID
```

`SIGKILL`을 전달하여 강제 종료한다.

```text id="sq7ez3"
SIGTERM (15)
→ "정상적으로 종료해 주세요."

SIGKILL (9)
→ "즉시 종료." 💀
```

따라서 일반적으로는 정상 종료를 먼저 시도하고, 필요한 경우에만 강제 종료를 고려한다.

# 16. foreground와 background

일반적인 명령 실행:

```bash id="c2e9oa"
command
```

Shell은 해당 작업이 끝날 때까지 기다린다.

```text id="e3od7r"
Shell
  │
  └── Command 실행
        ↓
      종료
        ↓
Shell 사용 가능
```

반면:

```bash id="ln9rkv"
command &
```

`&`를 붙이면 background에서 실행할 수 있다.

```text id="kr5xku"
Shell ─────────────→ 계속 사용 가능
  │
  └── Process
        └── Background에서 실행
```

이 개념은 이후 서버 프로세스와 서비스를 공부할 때 더욱 중요해진다.

# 17. Shell과 Process는 어떻게 연결될까?

사용자가 Shell에서:

```bash id="vhw5yf"
ls
```

를 입력한다고 생각해보자.

전체적인 흐름은:

```text id="c0ou0j"
사용자
  ↓
Shell
  ↓
명령어 해석
  ↓
Process 생성 및 실행
  ↓
Kernel
  ↓
File System / Hardware
  ↓
결과
  ↓
Shell
  ↓
사용자
```

따라서 Shell은 단순한 검은 명령창이 아니라

> **사용자의 명령을 해석하고 프로그램 실행을 연결하는 인터페이스**

라고 이해할 수 있다.

# 18. 💀 Toy Story 2와 `rm` 사건

Linux의 삭제 명령어가 얼마나 위험할 수 있는지를 설명할 때 자주 언급되는 유명한 일화가 있다.

Pixar에서 **Toy Story 2 제작 과정 중 작업 데이터가 대량으로 삭제되는 사고가 발생했고**, 백업 문제까지 겹치면서 큰 위기로 이어졌다고 알려져 있다.

다행히 작업물의 별도 사본이 존재하여 복구에 큰 도움이 되었다.

이 사례에서 얻을 수 있는 핵심은 특정 명령어 자체보다는 다음과 같다.

```text id="o38ekd"
중요 데이터
   │
   ├── 권한 관리
   ├── 삭제 작업 주의
   ├── Backup
   └── Recovery Plan
```

즉,

> **백업은 "문제가 생길 것 같아서" 하는 것이 아니라
> 문제가 생겼을 때 복구하기 위해 존재한다.**

# 19. Linux에서 명령어보다 중요한 습관

초반에는 다음과 같이 생각하기 쉽다.

```text id="19qt9b"
"명령어를 전부 외워야 하나?"
```

하지만 실제로 중요한 것은:

```text id="c3e6za"
현재 상태 확인
      ↓
명령어 선택
      ↓
옵션 확인
      ↓
실행
      ↓
결과 검증
```

예를 들어 삭제 작업이라면:

```bash id="g3tk8l"
pwd
ls -al
```

로 먼저 위치와 파일을 확인하고,

필요한 삭제 명령을 수행한 후,

```bash id="84qt51"
ls -al
```

로 결과를 다시 확인한다.
